# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AsteriskCraft is a NeoForge mod that brings a StarCraft-style RTS loop (gather → build → produce units → destroy the enemy base) into Minecraft. Mod id `asteriskcraft`, package root `net.bitflora.asteriskcraft`. Targets **Minecraft 26.1.2 + NeoForge 26.1.2.80** (Java 25 toolchain) — a version new enough that a lot of general MC-modding knowledge is stale for it.

**Read [docs/shaping.md](docs/shaping.md) first** for any feature work: it's the living requirements/design doc, listing the shipped/in-progress slices (V1–V5) and the specific decisions behind the architecture (e.g. why faction hostility must never hardcode which side is the enemy). Check its "Slices" table to see what's already `[DONE]` before assuming a feature doesn't exist.

**Read [docs/neoforge-api-notes.md](docs/neoforge-api-notes.md) before calling an unfamiliar NeoForge/MC API.** It documents specific API shapes verified against this exact version's decompiled source (e.g. `Mob.finalizeSpawn` being deprecated in favor of `EventHooks.finalizeMobSpawn`, the Codec-based `ValueOutput`/`ValueInput` save API, sun-burn being tag-gated not class-gated) and where to find the decompiled source jars to verify anything not already listed there. Add to it when you discover another non-obvious API behavior by digging through jars.

## Commands

- `./gradlew test` — run the JUnit test suite. Tests run inside a bootstrapped NeoForge environment (`neoForge.unitTest.enable()` in build.gradle), so real registries/blocks/items/entity types resolve in-test.
  - Single test class: `./gradlew test --tests "net.bitflora.asteriskcraft.building.GatewayEconomyTest"`
  - Single test method: `./gradlew test --tests "net.bitflora.asteriskcraft.building.GatewayEconomyTest.zealotCostMatchesDesign"`
- `./gradlew compileJava` — fast compile-only check.
- `./gradlew runData` — run data generators (see `data` run config in build.gradle; outputs to `src/generated/resources/`).
- Don't try to launch the game as a test, I will do that myself

**Important test-bootstrap limitation:** block/item **tags** are not bound in the JUnit bootstrap environment, so tag-dependent behavior (e.g. which block a Probe's tag-based harvest yields) can't be unit-tested — it's verified via `runClient` instead. See `ProbeEconomyTest`'s javadoc for the pattern: keep unit tests to pure logic/constants, and note in the test class why tag-dependent behavior is excluded.


## Unit Tests
- Never add a test for the value of a constant.
- Never add tests that check unit properties against other units; these are subject to frequent tweaking.
- Don't test private members or private state. If a public method's behavior seems under-covered without reaching into internals, that's a sign a concept wants to be pulled out into its own type with a public API, not a reason to expose internals for testing.
- Judge any proposed test, at any layer, against the "four pillars": protection against regression, resistance to refactoring, fast feedback, and maintainability. This lens doesn't depend on which testing style or layer is involved, so it stays relevant regardless of how the test surface grows.

## Architecture

Faction hostility is the single mechanism all targeting/combat logic must go through, kept deliberately generic so later versions can add race selection and PvP without touching targeting code:
- `faction/Faction` — enum (`NEUTRAL`, `PROTOSS`, `ZERG`) with `isEnemy(other)`: strictly cross-faction, NEUTRAL fights no one.
- `faction/FactionAttachments` — a NeoForge data attachment tagging any entity with its faction; **`isHostile(self, candidate)` is the one function combat code should call** (targeting, retaliation, bounce chains, damage guards). No targeting code should ever check entity class/type directly. `areEnemies(a, b)` is the narrower strict-faction primitive underneath it — reach for it only when wild mobs genuinely must be excluded. The difference matters: vanilla hostiles carry no attachment, so they default to `NEUTRAL`, and `Faction.isEnemy` says NEUTRAL fights no one — so `areEnemies` alone leaves units standing still while a zombie eats them. `isHostile` adds exactly one carve-out (a `NEUTRAL` candidate that is a vanilla hostile), double-gated so the mod's own units — hostile classes themselves — are never caught by it and an unfactioned unit still fights nobody. The class test is vanilla's `Enemy` **marker interface, not `Monster`**: `Monster` is only the `PathfinderMob` branch of the hostiles, so keying off it silently excluded `Slime`/`MagmaCube`, `Ghast`, `Phantom`, `Shulker` and `Hoglin` — units stood still while a slime ate them. That `instanceof Enemy` check lives in this one place and nowhere else.
- `entity/ai/FactionTargetGoal` — a `NearestAttackableTargetGoal<LivingEntity>` parameterized with a `TargetingConditions.Selector` that delegates to `FactionAttachments.isHostile`. Every faction-aware combat unit uses this instead of vanilla player-targeting goals. A unit that engages only part of the battlefield passes an extra predicate to its second constructor, which may only ever **narrow** what `isHostile` already allowed — hostility (and with it the cloak gate) stays decided in the one choke point. The two colonies are its users and are exact complements: the Spore passes `entity/Altitude::isAirborne`, the Sunken its negation (a spike out of the ground can't reach the air). `entity/ai/RetaliateGoal` takes the same filter for the same reason — a unit pinned by an attacker it cannot answer stops fighting the ones it can — so a unit that narrows one narrows both.
- **Two different notions of "air", and they are not interchangeable.** `entity/Altitude.isAirborne` is *positional* — four or more blocks of clear space above solid footing (`isFaceSturdy(UP)`), re-evaluated on every check — and decides which of the two colonies may shoot a given target (Spore: airborne only; Sunken: everything else), which is why a Mutalisk that lands stops being a Spore's target and becomes a Sunken's, and a Zealot falling off a cliff briefly swaps the other way. `entity/Flyer.isAir` is a *unit-type marker* and decides what an anti-air damage bonus (the Scout's) multiplies against, which is a property of the unit regardless of its current altitude. Don't substitute one for the other.
- `faction/Cloaked` + `faction/Cloaking` — **cloak is gated inside `isHostile`**, which is what makes it total for *acquisition*: acquisition, retaliation and splash chains all resolve hostility there, so an undetected cloaked unit cannot even be swung back at. **Acquisition is only half of it, though.** A `TargetingConditions.Selector` is consulted once, when a target is picked, and never again — `TargetGoal.canContinueToUse` re-checks only reach, teams and line of sight (see docs/neoforge-api-notes.md). That is invisible for a permanently cloaked unit like the Dark Templar, which can never be acquired at all, and broken for one whose cloak comes *up* while something already has it targeted — the Lurker. `combat/CloakTargetHandler` is the retention half: it vetoes an about-to-be-set target that is cloaked and unseen, and clears one already held. Any future rule that can start applying to a target mid-fight needs the same two halves. It lives in `faction/` rather than beside `entity/Flyer` because that package is deliberately a leaf (nothing in it imports another of the mod's packages) and the choke point depends on staying that way. Vanilla's invisibility flag is **not** used and cannot be — `TargetingConditions` floors an invisible unit's acquisition range at 2 blocks rather than hiding it (see docs/neoforge-api-notes.md). Visibility is the separate, purely client-side half: `client/CloakRenderStateModifier` rewrites `isInvisible`/`isInvisibleToPlayer` per viewer, so the same unit is a ghost to its own side, nothing to an undetected enemy, and a red-outlined ghost to a detecting one. `entity/Detector` (Photon Cannon, Spore Colony) drives the reveals from `combat/DetectionHandler`. Cloak is opt-in and meant to stay rare — two units have it, one per race, and they have it differently: the Dark Templar always, the Lurker only while burrowed. **`Cloaked.isCloaked` and `entity/Rooted.isRooted` are runtime questions, not `instanceof` tests** — each interface carries a `default` (`isCloakActive()`, `isRootedNow()`) that a permanently-cloaked or permanently-rooted unit takes as-is, so opting in is still one `implements`, while a unit whose answer changes overrides it. Whatever backs an override must be readable on **both** sides, since the cloak gate runs on the server and the render decision on the client. Because that override is the only seam, `combat/DetectionHandler` expires a reveal on anything carrying a live mask rather than on anything currently cloaked — a unit that un-cloaks while revealed would otherwise never count down and would come back already lit.

Production buildings (Nexus, Gateway, and future ones) share a common shape, factored into `building/`:
- `building/ArmyBank` — the shared per-faction resource pool (a level attachment, not owned by any one building): Nexus + Gateway (Protoss) and all three Hives (Zerg) act as "linked chests" onto one `Container` per faction via `building/ArmyLinkedContainer`, instead of each holding its own independent inventory. Sized 27 slots (Protoss) / 81 slots (Zerg).
- `building/ResourceBank` — atomic multi-item cost extraction from a `Container` (e.g. "50 wood AND 50 cobblestone, all or nothing"); operates generically whether that container is a shared `ArmyBank` view or a plain container.
- `building/SpawnSpots` — finds an open, safely-footed spot near a building to place a freshly produced unit. It is given the unit's `EntityType` and clears its whole spawn AABB, not just the column it stands in: units wider than a block overhang their neighbours on every side, and a rooted one (Sunken Colony) placed against a building's wall suffocates with no way to walk out. It also treats a spot already occupied by an `entity/Rooted` unit as taken: the ring search is deterministic, so two callers asking for a spot near the same core get handed the same block, and while two mobile units shove each other apart within a tick, two rooted ones stand inside each other forever (the Hive plants both a Sunken and a Spore Colony). Only `Rooted` counts — a Drone milling around must not push production out to the far rings.
- `building/BuildingTemplates` — places **every** building (Nexus, Gateway, Hive) from the hand-authored `.nbt` structure templates in `src/main/resources/data/asteriskcraft/structure/`, which are the source of truth for their shapes: redesign them in-game with a structure block and re-export, don't write blocks out in Java. A template is anchored on its **core block's column** (looked up via `StructureTemplate.filterBlocks`, never a hardcoded offset), so neither a redesign that moves the core nor an export whose selection box was framed loosely — the Hive's is a block wider on one side — shifts the building off where the game means it to be. It also owns the site prep: `planSitePrep` (pure, so the geometry is unit-testable without a live `ServerLevel`) clears head-room over the template's footprint and optionally fills support beneath it. The Hive fills with mycelium, matching the creep around it; the Protoss buildings pass a null support so nothing foreign is stamped under their own stonework. Server-side only — see the structure-template section of docs/neoforge-api-notes.md.
- `building/BuildingKitItem` — generic "right-click the ground to warp in a building" item; reusable across building types via a template id + core-block supplier. It also carries the template's declared `BuildingTemplates.Footprint` (size + core offset), which exists solely so the **client** can outline the volume the kit needs free (`client/KitPlacementPreview`) — templates live under `data/` and only a server can load one. The `.nbt` stays the source of truth: the server measures the loaded template and never reads the declaration, and `BuildingTemplatesTest` fails the build if a re-export drifts from it.
- `building/WarpScaffold` — what a kit-warped building stands as while it warps in: the stamped layout frozen back into glass, handed out pane by pane over the countdown in a scrambled order (rolled once at raise time, since the order is saved and must survive a reload) so it speckles into place rather than rising in tidy layers. Panes are paced against the time *remaining*, not a fixed schedule, which is what keeps the fill in step with a countdown that penalties can lengthen. Smashing a pane costs the warp twice over: 10 seconds on the countdown, and 20 points of siege damage collected the instant the building stands up — deliberately not while warping, where `WarpInVulnerability`'s halved pools would double them. A smashed pane is left as the hole it became and keeps its slot in the fill order, so its real block arrives exactly when it would have anyway; the flag on it only stops the same square being charged for on every sweep. Only kits raise a scaffold — a pre-placed building (Hive, the starting Nexus) carries the empty one every `BuildingDefense` has.
- `building/BuildingDefense` — what it takes to bring a building down, owned by every `building/SiegeTarget` block entity (Nexus, Gateway, Hive): siege HP, a Protoss shield buffer that soaks damage ahead of HP and recharges on the same delay/rate as a unit's (`combat/ShieldEventHandler`'s constants, not a second set of numbers), and the warp-in phase during which both pools are halved — finishing the warp scales what survived back up, so damage landed mid-warp is sustained twice over (`building/WarpInVulnerability`, shared with the Photon Cannon). A Zerg building passes a zero shield pool and a pre-placed one a zero warp duration; the starting Nexus calls `skipWarpIn()` from `GameBootstrap`. It also owns the `building/WarpScaffold` that fills the layout in over that same phase — the one thing that can *lengthen* a countdown rather than only run it down. **`SiegeTarget` vs `FactionCore`:** `SiegeBlockGoal` batters any enemy `SiegeTarget`, while `FactionCore` is the narrower marker for the buildings whose fall decides the match (Nexus + Hives) and is what `CoreCensus`/`GameOutcome`/`CoreSpoils` key off — so a razed Gateway costs production, not the game. Don't reach for a concrete building class in targeting or damage code.
- Each building is a `BaseEntityBlock` + `BlockEntity` pair (`NexusBlock`/`NexusBlockEntity`, `GatewayBlock`/`GatewayBlockEntity`) with its own production queue, ticking via `createTickerHelper`. A building's `preRemoveSideEffects` deliberately skips `super` (see `ArmyLinkedContainer`) so destroying one building never drops/clears the whole army's shared bank.

Units are plain hostile mobs, not repurposed Zombies/Skeletons: `entity/protoss/ZealotEntity`, `entity/protoss/DarkTemplarEntity` and `entity/zerg/ZerglingEntity` extend `Monster` directly (melee, via `MeleeAttackGoal`), and `entity/protoss/DragoonEntity`/`entity/protoss/ScoutEntity`/`entity/zerg/HydraliskEntity` extend `Monster implements RangedAttackMob` (ranged hitscan, via `RangedAttackGoal`) — not `Zombie`/`Skeleton`, since those vanilla classes carry unwanted baggage (Hard-mode reinforcement spawning and water→Drowned conversion on `Zombie`; a silently-equipped bow and Stray freeze-conversion on `Skeleton`) that was never neutralized in code. See docs/neoforge-api-notes.md for the verified findings. Combat units live in `entity/protoss`/`entity/zerg` subpackages (workers and structures too — `ProbeEntity`/`PhotonCannonEntity` under `protoss`, `DroneEntity` under `zerg`); shared faction-generic contracts (`Shielded`, `TeamColors`, `FactionSpawnEggItem`) and the goal library (`entity/ai`) stay at the neutral top level. Each unit's client renderer/model lives in the matching `client/protoss`/`client/zerg` subpackage — every unit has its own bespoke `MobRenderer`/model (not a reused vanilla `ZombieRenderer`/`SkeletonRenderer`). `entity/TeamColors` dyes a leather chestplate per faction for cheap visual team identity.

**A unit with a mode goes through the goal-priority ladder, never through a goal that knows about other goals.** The Lurker is the worked example: `entity/zerg/BurrowClock` is a pure state machine holding one depth (0 surfaced, 60 buried; the middle is neither mobile nor armed nor hidden), and the *only* thing that stops a dug-in unit being walked away is that `entity/ai/zerg/LurkerBurrowGoal` holds `MOVE`+`JUMP` and sits **below** every goal that needs the unit walking. `GoalSelector` only calls `canUse()` on a goal whose flags it can claim and hands a held flag over only to a strictly *lower* priority number, so the burrow goal never starts while something more important wants the unit, and being preempted is what surfaces it — its `stop()` is the only place that decision is written. Don't add "is it burrowed?" checks to the goal library; the two goals that genuinely needed telling both took the same kind of may-only-add-patience predicate `FactionTargetGoal` and `RetaliateGoal` carry, and for the same underlying reason — **a unit that stops its own navigation makes "standing still" stop meaning "stuck"**. `StuckWanderGoal` would otherwise dig it out to wander every 40s, and `SiegeBlockGoal`'s obstruction branch (which keys off "navigation done and not arrived") would surface it to chew through the first lip of terrain between it and a target it could already shoot over. A Lurker also refuses to be pulled out of the ground by a distant attacker, and that takes **all three** of the goals that can dig asking one shared question — `entity/ai/zerg/LurkerReach`, "is anything strikeable in spine range right now" — rather than reasoning about the current target: `LurkerHoldGroundGoal` sits above `RetaliateGoal` in the target selector and holds the `TARGET` flag so the near enemy is the one being shot, `LurkerApproachGoal` won't start while the answer is yes whoever set the target, and `LurkerBurrowGoal` keeps the unit down — it releases on its own `canContinueToUse` with no other goal involved, which is a dig-out the other two never see. Because the hold goal owns the `TARGET` flag whenever it runs, it owes the unit a *shootable* target on every tick, not just at the moment it claims one: it re-picks a claim that drifts out of spine range rather than holding it, since a held-but-unreachable target blocks re-acquisition and leaves the unit burrowed and silent. That predicate suppresses the dig branch only — building assault still preempts, or a Lurker parked by an enemy core with nothing alive to shoot would sit there. The entity backs the flag up with a hard stop (`customServerAiStep` zeroes horizontal movement, `isPushable`/`knockback` no-op) so physics can't drag a half-buried unit either — and deliberately *not* with `UnitStat.Builder.rooted()`, which is permanent and which `UnitStatsTest.onlyStaticDefenceIsRooted` polices.

Every unit's combat stats and production cost are centralized in `stats/UnitStats` — the single balance table (a `UnitStat` record per unit, built with a fluent builder) to edit for any tuning pass; entity classes hold no stat constants of their own, just a `private static final UnitStat STAT = UnitStats.X` field and a pointer-only javadoc line. `stats/UnitAttributes.apply(base, stat)` is the only place attributes get registered from it — each entity's `createAttributes()` is a one-line call, with the base builder (`Monster`/`Mob`/`PathfinderMob`) chosen by the caller since that's a Java-class fact, not a balance number. Every attribute is set explicitly, never left at a vanilla default: `Attributes.MOVEMENT_SPEED` defaults to 0.7 (not 0), so a rooted unit's `UnitStat.Builder.rooted()` states zero speed and full knockback resistance explicitly rather than relying on zero-as-absent (see docs/neoforge-api-notes.md). Costs are `stats/UnitCost` (interchangeable bundles of `stats/ResourceAmount`, paid via `stats/CostPayment`) — `ZergUnitCatalog` and the Nexus/Gateway block entities all resolve a unit's cost from the table rather than owning their own constants.

Every attacking unit deals its **own** damage type, declared in `combat/AsteriskCraftDamageTypes` and defined by hand-written JSON under `data/asteriskcraft/damage_type/` — `Registries.DAMAGE_TYPE` is a datapack registry, so there is no `DeferredRegister` and nothing fails until a unit swings, which is what `DamageTypeResourceTest` guards. Damage is dealt through exactly two helpers, and new attacks should go through them rather than calling `hurtServer` directly: `entity/ai/HitscanAttacks` (ranged) and `entity/ai/MeleeAttacks` (melee), each taking the attacker's damage type the same way they already take its particle and sound. Both build the source as `damageSources().source(key, attacker)` — **attributed**, which is what sets `getLastHurtByMob()` and so lets `entity/ai/RetaliateGoal` fire; the old shared `damageSources().magic()` carried no entity and nothing shot at range ever fought back. These types are deliberately outside `#minecraft:bypasses_armor` and `#minecraft:no_knockback` (which `magic` is in), so armour reduces hits and hits knock back. The fanged attackers are the awkward ones: a Sunken Colony's spike and each spine of a Lurker's row are vanilla `EvokerFangs`, whose damage is built in a private method, so `combat/FangStrikeDamageHandler` **cancels** vanilla's hit and re-deals it — a `LivingIncomingDamageEvent` can rewrite an amount but never substitute a `DamageSource`. It matches on `entity/zerg/FangStrikeEntity`, the shared base, and takes the type and the amount off the spike rather than naming a unit, so a new fanged attacker needs nothing there; `entity/ai/zerg/GroundStrike` is the footing search both share. See docs/neoforge-api-notes.md.

Air units (`entity/zerg/MutaliskEntity` and `entity/protoss/ScoutEntity`) hover a fixed height above the terrain, and the mechanism is deliberately invisible to the goal library: a vanilla `FlyingMoveControl` plus `entity/ai/HoverFlyingNavigation`, which lifts every destination to `ground + hoverHeight` **before** the path is computed. That altitude has to live in the path itself — `PathNavigation.followThePath` only advances a node when the mob is within 1 block of it on Y, so a flyer over a ground-hugging path re-paths forever (see docs/neoforge-api-notes.md). Because every movement goal reaches the world through `getNavigation().moveTo(...)`, `RangedAttackGoal`/`CommandedMoveGoal`/`GuardGoal`/`SiegeBlockGoal` all fly with no changes of their own; `entity/ai/HoverGoal` only holds altitude in the gaps between orders. Don't reimplement hovering inside a goal or a `MoveControl`.

Unit textures are hand-painted in Blockbench, not generated — see [docs/texturing.md](docs/texturing.md). Every cube owns its own UV island, and `tools/blockbench_export.py` converts a model's `createBodyLayer()` into a `.bbmodel` (packing those islands on first migration). This constrains how model classes may be written: each cube needs its own `texOffs(int, int)` literal, so a model must not build several cubes through one call site (no UV constants, no multiply-called helper, no loop over parts, no shared `CubeListBuilder`). `ModelUvLayoutTest` fails the build if any two islands overlap.

Registration is centralized in `AsteriskCraft.java` (blocks, items, block entities, entity types, creative tab, entity attributes — all via `DeferredRegister`) with a separate client-only companion `client/AsteriskCraftClient.java` (`@Mod(dist = Dist.CLIENT)`) for renderers/model layers, since client-only classes must never load on a dedicated server.

`game/GameBootstrap` places the player's starting base (Nexus + resource chest) on first world join rather than at server start, because the player's chunk is guaranteed loaded with settled terrain height by then; `game/GameAttachments` holds the resulting level-scoped saved state (has-bootstrapped flag, Nexus position).
