# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

AsteriskCraft is a NeoForge mod that brings a StarCraft-style RTS loop (gather → build → produce units → destroy the enemy base) into Minecraft. Mod id `asteriskcraft`, package root `net.bitflora.asteriskcraft`. Targets **Minecraft 26.1.2 + NeoForge 26.1.2.80** (Java 25 toolchain) — a version new enough that a lot of general MC-modding knowledge is stale for it.

**Read [docs/shaping.md](docs/shaping.md) first** for any feature work: it's the living requirements/design doc, listing the shipped/in-progress slices (V1–V5) and the specific decisions behind the architecture (e.g. why faction hostility must never hardcode which side is the enemy). Check its "Slices" table to see what's already `[DONE]` before assuming a feature doesn't exist.

**Read [docs/neoforge-api-notes.md](docs/neoforge-api-notes.md) before calling an unfamiliar NeoForge/MC API.** It documents specific API shapes verified against this exact version's decompiled source (e.g. `Mob.finalizeSpawn` being deprecated in favor of `EventHooks.finalizeMobSpawn`, the Codec-based `ValueOutput`/`ValueInput` save API, sun-burn being tag-gated not class-gated) and where to find the decompiled source jars to verify anything not already listed there. Add to it when you discover another non-obvious API behavior by digging through jars.


## Guidelines

Prefer a Minecraft style where possible. Spherical Starcraft entities should become cubes. Where possible, reuse vanilla models.

**Borrowing a vanilla model means borrowing its texture too, as a second draw — that is the default, not an option.** A model part can only be painted from its own model's texture, so re-authoring vanilla geometry inside a mod model class means hand-copying vanilla pixels into the mod's PNG, which is a copy that goes stale silently the next time vanilla retouches it. Instead, bake the vanilla `ModelLayerLocation`, hang it on an **empty container part** in the mod's model, and draw it in a `RenderLayer` with vanilla's own texture — `client/terran/MarineHeadLayer` (the adult villager head) and `client/terran/ScvPilotLayer` (the baby villager head in the cab) are the two worked examples, and both models expose a `translateToX(PoseStack)` that walks the part chain for the layer. Hide the vanilla sub-parts you don't want by setting `visible = false` on them rather than by re-authoring the mesh around them. Re-author vanilla geometry **only** when the mod needs to modify or replace it — `client/zerg/InfestedVillagerModel` copies villager proportions because it has to graft a Zergling's head onto them.

**Terrans should be based on Villagers**, and the default Terran pose is a villager's: vanilla's 8x12x6 torso, the inflated 20-tall robe, 4x12x4 legs on the same hips, and **arms folded across the belly** at pivot `(0, 3, -1)` tilted `-0.75`. A Terran that needs a limb somewhere else moves one off that pose rather than starting from a different one; whatever the unit carries is cradled in the folded arms unless there is a specific reason it cannot be. `client/terran/MarineModel` is the reference.


## Commands

- `./gradlew test` — run the JUnit test suite. Tests run inside a bootstrapped NeoForge environment (`neoForge.unitTest.enable()` in build.gradle), so real registries/blocks/items/entity types resolve in-test.
  - Single test class: `./gradlew test --tests "net.bitflora.asteriskcraft.building.GatewayEconomyTest"`
  - Single test method: `./gradlew test --tests "net.bitflora.asteriskcraft.building.GatewayEconomyTest.zealotCostMatchesDesign"`
- `./gradlew compileJava` — fast compile-only check.
- `./gradlew runData` — run data generators (see `data` run config in build.gradle; outputs to `src/generated/resources/`).
- Don't try to launch the game as a test, I will do that myself

**Important test-bootstrap limitation:** block/item **tags** are not bound in the JUnit bootstrap environment, so tag-dependent behavior (e.g. which block a Probe's tag-based harvest yields) can't be unit-tested — it's verified via `runClient` instead. See `WorkerEconomyTest`'s javadoc for the pattern: keep unit tests to pure logic/constants, and note in the test class why tag-dependent behavior is excluded.


## Unit Tests
- Never add a test for the value of a constant.
- Never add tests that check unit properties against other units; these are subject to frequent tweaking.
- Don't test private members or private state. If a public method's behavior seems under-covered without reaching into internals, that's a sign a concept wants to be pulled out into its own type with a public API, not a reason to expose internals for testing.
- Judge any proposed test, at any layer, against the "four pillars": protection against regression, resistance to refactoring, fast feedback, and maintainability. This lens doesn't depend on which testing style or layer is involved, so it stays relevant regardless of how the test surface grows.

## Architecture

**Side and race are two different things, they are independent, and there are exactly two tables.**
`faction/Faction` (`NEUTRAL`, `BLUE`, `RED`) is *which side* an army is on — it decides who shoots
whom, and nothing else. `faction/Race` is *what that army is* — it decides what it builds, what it
can produce, and which of the cheap combat traits it has. **A side does not name a race and there is
no bridge between them**: the constants are colours precisely because a "Protoss side" could not
exist in a match where both armies are Protoss. What each side is playing is a fact about *this
match* and is answered in two places — `game/MatchSetup` (a level attachment written once at
bootstrap) for the match as a whole, and `faction/FactionAttachments.RACE`, a synced per-entity
attachment set beside `FACTION` wherever a unit is spawned, for any given army in hand. Set both
together (`FactionAttachments.set(entity, faction, race)`); an entity with a side and no race is an
army that is nothing.

**A mirror match is an ordinary match.** Both game rules may name the same race, both pickers may
show it, and nothing corrects the pair: two sides playing the swarm are two armies, with two banks
(`building/ArmyBank` keys one per *side and race*), that are enemies (`Faction.isEnemy` is strictly
cross-side). That is the whole reason side and race were pulled apart, so don't reintroduce a
side↔race mapping to shorten a call site.

**What the match is written from is a pair of game rules,
`asteriskcraft:player_race` and `asteriskcraft:ai_race`** (`game/AsteriskCraftGameRules`), both picked
at world creation — see the world-creation section below. Two rules rather than one because with a
third race the opponent stopped being derivable: "the faction that isn't yours" was a two-race trick,
and `MatchSetup.forRaces` replaced it with a choice, which it now honours as given. The pair is
frozen at bootstrap rather than read live, because everything downstream (where the AI's bases were
stamped, which bank the director spends, which core losing ends the match) has to keep agreeing with
it. **Nothing may name a faction literal to mean a race, or a race to mean a side.** In particular
there is no "the player is Protoss" anywhere: `command/ControlledFaction.of(player)` answers which
side the human is on and `command/ControlledRace.of(player)` what it is (both off the player's own
synced attachments, so they work client-side and are already per-player for PvP), and
`director/AiDirector` reads `MatchSetup` for the computer. The sides a match uses are
`MatchSetup.PLAYER_SIDE`/`AI_SIDE`, so even those two constants are not spelled out at a call site.

- **Cheap traits live on `Race` itself** — `shields()`, `regen()`, `infests()`, `attacksWild(kind, commanded)`
  — because `faction/` is deliberately a leaf package and a pure rule (`combat/Infestation`,
  `faction/WildKind`) must be able to consult them with no registries loaded. A call site reaches
  them off the unit in hand (`FactionAttachments.raceOf(entity)`, null for the unfactioned world)
  and never off its side — `combat/ShieldEventHandler`, `combat/RegenEventHandler` and
  `combat/InfestationHandler` are the three that do it.
- **Everything registry-bound lives in `race/RaceProfile`, and the table is `race/Races`.** A
  profile holds a race's base core block and structure template, its base's HP/shield/warp-in
  numbers, its bank size, its `race/UnitRoster` (including which unit is its worker), its base's
  command card, its AI build-script path, and its world-gen flavour (ground cover, support fill,
  static defence planted per base, starting bank contents). Registry values are `Supplier`s
  because the table is built at class-init, well before blocks and entity types finish registering
  — **do not put a resolved `Block`, `EntityType` or `ProductionKind` in it.**
- **`race/Races` is the only place in the mod that knows a Hive is a Zerg base or a Drone is a Zerg
  worker.** The Terran (V6a) are what proves it: a Command Center and an SCV went in as one table
  entry each plus assets, and `BaseBlockEntity`, `GameBootstrap`, `ArmyBank`, `AiDirector` and every
  targeting rule needed no edit at all — the only compile error outside the tables was
  `entity/TeamColors`' exhaustive switch, which is what a switch is for. `building/BaseBlockEntity`, `director/AiDirector` and `game/GameBootstrap` all ask a
  profile. Adding a race — or letting the human play the swarm — is an entry in that table plus its
  assets, and no change to any of them. `RacesTest` fails the build if an entry is incomplete.
- **Asset and registry ids stay race-flavoured on purpose**: `nexus_core`, `hive_core`, `probe`,
  `drone`. "Base" and "Worker" are the generic *concepts*; Nexus and Hive are legitimate race names
  for a base, the way Zealot is for a unit. Generic Java code says Base and Worker; data files
  keep the flavour.

Faction hostility is the single mechanism all targeting/combat logic must go through, kept deliberately generic so later versions can add race selection and PvP without touching targeting code:
- `faction/Faction` — enum (`NEUTRAL`, `BLUE`, `RED`) with `isEnemy(other)`: strictly cross-faction, NEUTRAL fights no one. It carries nothing else — no race, no colour rule, no traits. Two playable sides because a match is one army against one army; PvP grows the number of *players*, not of sides, and a third side would be one entry here plus a colour in `entity/TeamColors` (whose colours are per side, not per race, which is what tells two mirror armies apart).
- `faction/FactionAttachments` — the NeoForge data attachments tagging any entity with the army it fights for: its side (`FACTION`) and its race (`RACE`, synced, so the client can answer too); **`isHostile(self, candidate)` is the one function combat code should call** (targeting, retaliation, bounce chains, damage guards). No targeting code should ever check entity class/type directly. `areEnemies(a, b)` is the narrower strict-faction primitive underneath it — reach for it only when wild mobs genuinely must be excluded. The difference matters: everything the mod doesn't own carries no attachment, so it defaults to `NEUTRAL`, and `Faction.isEnemy` says NEUTRAL fights no one — so `areEnemies` alone leaves units standing still while a zombie eats them. `isHostile` adds exactly one carve-out for the unfactioned world, and **the races do not agree on what's in it**, which is why it is a classification rather than a boolean: `faction/WildKind` sorts a neutral entity into `HOSTILE` (vanilla's `Enemy` marker), `CIVILIAN` (villagers, wandering traders, golems) or `PASSIVE` (the player, a cow, everything else), and `isHostile` consults `Race.attacksWild` — the per-race table saying which of those that race picks a fight with, reached through the attacker's own `RACE` attachment — Protoss and Terran `HOSTILE`, Zerg `CIVILIAN`, NEUTRAL (no race) nothing. So the swarm overruns a village and ignores zombies while the Protoss do the opposite, with **no race check anywhere in targeting code**; adding a race, or changing what one hunts, is an edit to that one table. **That table has two columns, not one**: a race declares what it hunts and what it hunts *while a human is commanding it*, and `Race.attacksWild` takes which. The swarm is the reason — "ignore monsters" is right for a scripted opponent parked across the map and wrong for the army you are standing in, where it means a creeper walks into your Hive — so commanded Zerg add `HOSTILE` to the `CIVILIAN` they already hunt, while the Protoss answer is the same either way. Command may only ever *widen* the wild carve-out; it never touches strict cross-faction hostility, and `NEUTRAL` (no race) still fights nobody. Which side is commanded is `FactionAttachments.COMMANDED`, a level attachment holding `MatchSetup.playerFaction()` — a deliberate leaf-package projection of it, since `faction/` may not import `game/` and `MatchSetup.of` answers its default on the client anyway. `game/GameBootstrap` is its single writer, on every login, beside where it writes the player's own faction. The carve-out stays double-gated: on the candidate actually being `NEUTRAL` (the mod's own units are `Enemy` classes themselves and must never be caught by a class check), and on the attacker having a race at all (the unfactioned world plays none, so an unfactioned unit still fights nobody). The hostile test is vanilla's `Enemy` **marker interface, not `Monster`**: `Monster` is only the `PathfinderMob` branch of the hostiles, so keying off it silently excluded `Slime`/`MagmaCube`, `Ghast`, `Phantom`, `Shulker` and `Hoglin` — units stood still while a slime ate them. `HOSTILE` is tested first and wins ties, so a `Shulker` (both `Enemy` and `AbstractGolem`) stays a monster rather than becoming Zerg prey. Every entity-class test in the mod's targeting lives in `WildKind.of` and nowhere else.
- `entity/ai/FactionTargetGoal` — a `NearestAttackableTargetGoal<LivingEntity>` parameterized with a `TargetingConditions.Selector` that delegates to `FactionAttachments.isHostile`. Every faction-aware combat unit uses this instead of vanilla player-targeting goals. A unit that engages only part of the battlefield passes an extra predicate to its second constructor, which may only ever **narrow** what `isHostile` already allowed — hostility (and with it the cloak gate) stays decided in the one choke point. The two colonies are its users and are exact complements: the Spore passes `entity/Altitude::isAirborne`, the Sunken its negation (a spike out of the ground can't reach the air). `entity/ai/RetaliateGoal` takes the same filter for the same reason — a unit pinned by an attacker it cannot answer stops fighting the ones it can — so a unit that narrows one narrows both. **The one deliberate exception is the Infested Villager, and the distinction it draws is the rule to reason with:** the colonies are narrowed by *capability* (a spike out of the ground genuinely cannot reach the air), so narrowing only acquisition would leave one inert while something it can never hit holds its target; the bomber is narrowed by *doctrine* — it passes `FactionAttachments::areEnemies` to subtract the villagers and golems `Faction.attacksWild(CIVILIAN)` would otherwise hand it, but it can blow up an iron golem perfectly well and simply does not go looking for one, so its `RetaliateGoal` is left unfiltered and that is what implements "unless attacked". Narrow both when the unit *cannot* answer; narrow acquisition alone when it merely *should not*.
- **Two different notions of "air", and they are not interchangeable.** `entity/Altitude.isAirborne` is *positional* — four or more blocks of clear space above solid footing (`isFaceSturdy(UP)`), re-evaluated on every check — and decides which of the two colonies may shoot a given target (Spore: airborne only; Sunken: everything else), which is why a Mutalisk that lands stops being a Spore's target and becomes a Sunken's, and a Zealot falling off a cliff briefly swaps the other way. `entity/Flyer.isAir` is a *unit-type marker* and decides what an anti-air damage bonus (the Scout's) multiplies against, which is a property of the unit regardless of its current altitude. Don't substitute one for the other.
- `faction/Cloaked` + `faction/Cloaking` — **cloak is gated inside `isHostile`**, which is what makes it total for *acquisition*: acquisition, retaliation and splash chains all resolve hostility there, so an undetected cloaked unit cannot even be swung back at. **Acquisition is only half of it, though.** A `TargetingConditions.Selector` is consulted once, when a target is picked, and never again — `TargetGoal.canContinueToUse` re-checks only reach, teams and line of sight (see docs/neoforge-api-notes.md). That is invisible for a permanently cloaked unit like the Dark Templar, which can never be acquired at all, and broken for one whose cloak comes *up* while something already has it targeted — the Lurker. `combat/TargetRetentionHandler` is the retention half: it vetoes an about-to-be-set target that is cloaked and unseen, and clears one already held. Any future rule that can start applying to a target mid-fight needs the same two halves, which is why that class is named for the shape rather than for cloak — garrisoning (below) is the second rule to need it, and it needed no new machinery. It lives in `faction/` rather than beside `entity/Flyer` because that package is deliberately a leaf (nothing in it imports another of the mod's packages) and the choke point depends on staying that way. Vanilla's invisibility flag is **not** used and cannot be — `TargetingConditions` floors an invisible unit's acquisition range at 2 blocks rather than hiding it (see docs/neoforge-api-notes.md). Visibility is the separate, purely client-side half: `client/CloakRenderStateModifier` rewrites `isInvisible`/`isInvisibleToPlayer` per viewer, so the same unit is a ghost to its own side, nothing to an undetected enemy, and a red-outlined ghost to a detecting one. `entity/Detector` (Photon Cannon, Spore Colony) drives the reveals from `combat/DetectionHandler`. Cloak is opt-in and meant to stay rare — two units have it, one per race, and they have it differently: the Dark Templar always, the Lurker only while burrowed. **`Cloaked.isCloaked` and `entity/Rooted.isRooted` are runtime questions, not `instanceof` tests** — each interface carries a `default` (`isCloakActive()`, `isRootedNow()`) that a permanently-cloaked or permanently-rooted unit takes as-is, so opting in is still one `implements`, while a unit whose answer changes overrides it. Whatever backs an override must be readable on **both** sides, since the cloak gate runs on the server and the render decision on the client. Because that override is the only seam, `combat/DetectionHandler` expires a reveal on anything carrying a live mask rather than on anything currently cloaked — a unit that un-cloaks while revealed would otherwise never count down and would come back already lit.

- `faction/Garrison` + `entity/Organic` — **a unit riding inside a transport is gated inside `isHostile` exactly the way a cloaked one is**, and for the same reason: everything aimed at it has to go through the shell instead, so acquisition, retaliation, bounce chains and attack orders all follow from the one choke point with nothing written for them. The marker is on the **vehicle** (`Garrison`, carrying `capacity()` and a `rangeBonus()` for the reach a firing slit is worth) and `Garrison.isGarrisoned(entity)` is the runtime question asked about a candidate — the `Cloaked`/`Cloaking` split folded into one interface. It lives in `faction/` and not beside `entity/Rooted` for the leaf-package reason `Cloaked` does. **It takes all three layers, not one**: the gate above, the `combat/TargetRetentionHandler` veto for a unit that boards while something already holds it, and `combat/GarrisonDamageHandler` underneath both — because targeting is not the only way damage arrives (`combat/SuicideBlast` deliberately resolves no hostility, fang strikes hit a spot rather than a target, and a vehicle propagates its own fall damage to its riders). That handler **cancels** at `EventPriority.HIGHEST`, so `ShieldEventHandler`/`RegenEventHandler` never see a hit that did not land. Who may board is the separate, capability-shaped question `entity/Organic` answers — a bare marker beside `Flyer`/`Rooted`/`Detector`/`CreepSource`, carried by the Marine and the SCV, so the boarding rule names no race and no unit class. **The whole boarding rule lives at the door**, on `entity/terran/BunkerEntity.boardable`; nothing else decides who fits.
- **Riding is mostly free and specifically dangerous in three places** — see docs/neoforge-api-notes.md, which has the verified detail. A riding `Mob` runs its **full** goal and target selectors, so "shoot from inside" needed no combat code; passengers persist nested under the vehicle and are re-seated on load; `Entity.setRemoved` dismounts everyone. But: the first `Mob` passenger becomes the vehicle's **driver** unless `getControllingPassenger()` is overridden to null (it re-routes the rider's navigation onto the vehicle); riders stay individually targetable and hittable, which is what the three layers above are for; and **a rider's movement goals still hold their goal flags**, silencing anything below them — which is why `entity/ai/StuckWanderGoal` counts `isPassenger()` as a good reason to be standing still and `entity/ai/SiegeBlockGoal` refuses to run for a passenger at all. Both are facts about riding, not about Bunkers, which is why they are built into those goals rather than passed in as predicates.

Production buildings share a common shape, factored into `building/`:
- **`building/BaseBlockEntity` is every race's base** — Nexus, Hive, whatever comes next — and `building/BaseBlock` is its core block, registered once per race with that race's `Race` in its constructor (which is the only thing the block entity needs from it). One class, because which race a base belongs to changes its numbers and its command card, not what it *is*: it banks the army's resources, produces that race's worker, stands as a `FactionCore`, and lights a beacon beam. That merge is what makes the human and the computer interchangeable — a player-controlled Hive and an AI-controlled Nexus are the same building differently owned. **Whether a base shows a command card is a question about who is holding it, not which race it is:** `BaseBlock.useWithoutItem` opens the menu when `ControlledFaction.of(player)` matches the base's faction *and* that race declares a `ProductionKind`. A race with none simply never queues; the computer never opens a card at all, since `AiDirector` drives its production centrally either way. **The base's queue is a mixed one, of roster ids rather than of workers**, which is what a race with no separate factory building needs: the Hive morphs its combat units itself, so a Mutalisk and a Drone sit in the same line and each takes its own build time. Ids rather than option indices because the queue is saved — a card reordered later must not turn a saved queue into whatever now sits at those positions — and a pre-mixed-queue save (a bare `Queued` count) still reads back as that many workers.
- `building/ProductionKind` — a base's command card, and the per-race table for it. Each `OptionView` carries an `Action` (`TrainWorker(alternative)` / `TrainUnit(rosterId)` / `GiveKit(...)`) that `BaseBlockEntity.trainOption` executes without knowing whose card it is holding, so a second race's card is a new enum entry and no new code. `TrainWorker` names no unit (*which* worker is the base's race's); `TrainUnit` names one by the same `UnitStat.id()` a build script spells, and `RacesTest` fails the build if a card names a unit its own roster can't resolve. The two shipped base cards differ in shape for real reasons and neither is the template: the Nexus splits its buttons into Wood/Stone pairs because Protoss costs offer that choice, while every Zerg cost is a single "any resource" alternative and so gets one button each. `ZERG_BASE` also declares a **27-slot window onto an 81-slot bank** — `ProductionMenu`'s height is laid out around three rows, and the bank fills from the front with only three item types ever in it. A unit factory keeps its own positional dispatch and its buttons carry `Action.FACTORY` (the Gateway).
- `building/ArmyBank` — the shared per-army resource pool (a level attachment, not owned by any one building): every base and factory of one army acts as a "linked chest" onto one `Container` via `building/ArmyLinkedContainer`, instead of each holding its own independent inventory. One bank per **(side, race)** pair, registered by walking `Faction` × `Races` and sized from each profile's `bankSlots()`, so adding a race brings its banks with it. Per side and not per race alone because a mirror match is two armies of one race, which keyed by race would spend one pool between them.
- `building/ResourceBank` — atomic multi-item cost extraction from a `Container` (e.g. "50 wood AND 50 cobblestone, all or nothing"); operates generically whether that container is a shared `ArmyBank` view or a plain container.
- `building/SpawnSpots` — finds an open, safely-footed spot near a building to place a freshly produced unit. It is given the unit's `EntityType` and clears its whole spawn AABB, not just the column it stands in: units wider than a block overhang their neighbours on every side, and a rooted one (Sunken Colony) placed against a building's wall suffocates with no way to walk out. It also treats a spot already occupied by an `entity/Rooted` unit as taken: the ring search is deterministic, so two callers asking for a spot near the same core get handed the same block, and while two mobile units shove each other apart within a tick, two rooted ones stand inside each other forever (the Hive plants both a Sunken and a Spore Colony). Only `Rooted` counts — a worker milling around must not push production out to the far rings.
- `building/BuildingTemplates` — places **every** building from the hand-authored `.nbt` structure templates in `src/main/resources/data/asteriskcraft/structure/`, which are the source of truth for their shapes: redesign them in-game with a structure block and re-export, don't write blocks out in Java. (The one exception is a building that is *only* its core block — the Command Center — whose 1x1x1 template has no shape to design and is emitted by `tools/make_core_template.py`, byte-compatible with a real export so a designed version can be re-exported straight over it.) A template is anchored on its **core block's column** (looked up via `StructureTemplate.filterBlocks`, never a hardcoded offset), so neither a redesign that moves the core nor an export whose selection box was framed loosely — the Hive's is a block wider on one side — shifts the building off where the game means it to be. It also owns the site prep: `planSitePrep` (pure, so the geometry is unit-testable without a live `ServerLevel`) clears head-room over the template's footprint and optionally fills support beneath it. Which support a base fills with is its race's (`RaceProfile.support()`): the Hive fills with mycelium, matching the creep around it, while the Protoss pass a null support so nothing foreign is stamped under their own stonework. Server-side only — see the structure-template section of docs/neoforge-api-notes.md.
- `building/BuildingKitItem` — generic "right-click the ground to warp in a building" item; reusable across building types via a template id + core-block supplier. It also carries the template's declared `BuildingTemplates.Footprint` (size + core offset), which exists solely so the **client** can outline the volume the kit needs free (`client/KitPlacementPreview`) — templates live under `data/` and only a server can load one. The `.nbt` stays the source of truth: the server measures the loaded template and never reads the declaration, and `BuildingTemplatesTest` fails the build if a re-export drifts from it.
- `building/WarpScaffold` — what a kit-warped building stands as while it warps in: the stamped layout frozen back into glass, handed out pane by pane over the countdown in a scrambled order (rolled once at raise time, since the order is saved and must survive a reload) so it speckles into place rather than rising in tidy layers. Panes are paced against the time *remaining*, not a fixed schedule, which is what keeps the fill in step with a countdown that penalties can lengthen. Smashing a pane costs the warp twice over: 10 seconds on the countdown, and 20 points of siege damage collected the instant the building stands up — deliberately not while warping, where `WarpInVulnerability`'s halved pools would double them. A smashed pane is left as the hole it became and keeps its slot in the fill order, so its real block arrives exactly when it would have anyway; the flag on it only stops the same square being charged for on every sweep. Only kits raise a scaffold — a pre-placed building (an AI base, the player's starting base) carries the empty one every `BuildingDefense` has.
- `building/BuildingDefense` — what it takes to bring a building down, owned by every `building/SiegeTarget` block entity: siege HP, a shield buffer that soaks damage ahead of HP and recharges on the same delay/rate as a unit's (`combat/ShieldEventHandler`'s constants, not a second set of numbers), and the warp-in phase during which both pools are halved — finishing the warp scales what survived back up, so damage landed mid-warp is sustained twice over (`building/WarpInVulnerability`, shared with the Photon Cannon). **A base's three numbers come from its `RaceProfile`, not from the block entity**: a race without shields declares a zero pool and a pre-placed base a zero warp duration; the player's starting base calls `skipWarpIn()` from `GameBootstrap`. It also owns the `building/WarpScaffold` that fills the layout in over that same phase — the one thing that can *lengthen* a countdown rather than only run it down. **`SiegeTarget` vs `FactionCore`:** `SiegeBlockGoal` batters any enemy `SiegeTarget`, while `FactionCore` is the narrower marker for the buildings whose fall decides the match (the bases) and is what `CoreCensus`/`GameOutcome`/`CoreSpoils` key off — so a razed Gateway costs production, not the game. Don't reach for a concrete building class in targeting or damage code.
- **`building/PsiField` is the only answer to "may a building be warped in here".** The Pylon
  prerequisite (a Protoss building must stand within 10 blocks of a finished Pylon) is decided
  there and nowhere else, the way hostility is decided in `FactionAttachments.isHostile` — and it
  deliberately **names no building**. Which buildings are exempt is a `requiresPylon` flag on the
  *placing item*, so a Nexus and a Pylon never ask; adding an exemption is a constructor argument,
  not a case in the rule. There are **two** placement call sites and both go through it:
  `building/BuildingKitItem` and — because the Photon Cannon is a building that happens to be an
  entity — `entity/FactionSpawnEggItem`. Those two share no supertype but `Item`, which is what
  `building/PsiDependent` is for: it carries the `requiresPylon` flag so `client/PsiFieldOverlay`
  can ask "does what the player is holding need power" without naming either, and the Cannon is the
  case that needs the overlay most — a kit at least gets a coloured volume outline, a spawn egg
  draws nothing at all. **"Has this Pylon finished warping in" is a blockstate
  (`PylonBlock.ONLINE`), not a field on the block entity**, and that is load-bearing rather than
  incidental: `client/KitPlacementPreview` has to give the same answer as the server's refusal, and
  a blockstate syncs to every client holding the chunk for free where a block-entity field would
  need an update packet nothing else in this mod sends. The flag is **driven off the warp countdown
  on every tick** rather than flipped once when it ends, because a structure template carries the
  captured blockstate *and* block-entity NBT from the design world and a stamped Pylon can arrive
  claiming it is already online — the same trap that makes kit placement call `beginWarpIn`
  explicitly. The preview's one permissiveness is Pylon *ownership*, which is on the block entity;
  it may say yes where the server says no, never the reverse. Finding Pylons is its own step
  (`PsiField.onlinePylons`, a walk over the block entities of the surrounding chunks) rather than a
  sweep of block positions, because `client/PsiFieldOverlay` paints the whole powered area and needs
  one lookup to answer a thousand ground columns.
- **`building/CreepField` is the Zerg answer to the same question `PsiField` answers for the
  Protoss — and deliberately a separate class, not a generalization of it.** A Zerg building may be
  placed within `CreepField.RADIUS` (20) of *any* creep source (a Hive, or a Sunken or Spore
  Colony — the `entity/CreepSource` marker, sitting beside `Rooted`/`Flyer`/`Detector`) or standing
  outright on the race's creep block (mycelium, unowned — a razed base's creep stays buildable for
  whoever reaches it). **Unlike psi, both clauses are deliberately faction-blind**: creep is shared
  territory, not an army-specific resource, so an enemy colony egg (used for testing, or in a
  Zerg mirror match, where the two armies' creep is the same block anyway) may go down beside an
  ally's creep exactly as freely as its own — `CreepField.creepSources` is always walked with a null
  owner, and the `Race` a caller passes in only picks whose ground block counts as creep. It is reached from the same two call sites as
  psi, through the sibling `building/CreepDependent` flag (`requiresCreep`) rather than a second field
  on `PsiDependent`, because the two mechanisms are allowed to diverge later and neither may name the
  other's race. Colonies already spread mycelium in a matching 20-block circle on placement
  (`game/GameBootstrap.spreadCreep`), which is what lets a chain of colonies push creep outward
  across the map. `client/PsiFieldOverlay` and `client/CreepFieldOverlay` share their grid/rendering
  mechanics through `client/GroundGridOverlay`; each still owns its coverage rule and colours.
- `building/CoreCensus` is the **only** answer to "where are this faction's bases". Every base enrols itself from its own tick, so it sees one warped in from a kit, and it is symmetric across the two sides in a way the old bootstrap-written position attachments never were. `game/GameOutcome.decide` is symmetric too: a side is out when its *last* base falls, whichever side that is — so an expansion base buys the player another life exactly the way a second Hive always bought the swarm one.
- Each building is a `BaseEntityBlock` + `BlockEntity` pair (`BaseBlock`/`BaseBlockEntity`, `GatewayBlock`/`GatewayBlockEntity`) with its own production queue, ticking via `createTickerHelper`. A building's `preRemoveSideEffects` deliberately skips `super` (see `ArmyLinkedContainer`) so destroying one building never drops/clears the whole army's shared bank.

Units are plain hostile mobs, not repurposed Zombies/Skeletons: `entity/protoss/ZealotEntity`, `entity/protoss/DarkTemplarEntity` and `entity/zerg/ZerglingEntity` extend `Monster` directly (melee, via `MeleeAttackGoal`), and `entity/protoss/DragoonEntity`/`entity/protoss/ScoutEntity`/`entity/zerg/HydraliskEntity` extend `Monster implements RangedAttackMob` (ranged hitscan, via `RangedAttackGoal`) — not `Zombie`/`Skeleton`, since those vanilla classes carry unwanted baggage (Hard-mode reinforcement spawning and water→Drowned conversion on `Zombie`; a silently-equipped bow and Stray freeze-conversion on `Skeleton`) that was never neutralized in code. See docs/neoforge-api-notes.md for the verified findings. Combat units live in `entity/protoss`/`entity/zerg`/`entity/terran` subpackages (structures too — `PhotonCannonEntity` under `protoss`, `BunkerEntity` under `terran`; both are buildings that happen to be entities, which is what makes them selectable and retaliated-against for free); shared faction-generic contracts (`Shielded`, `TeamColors`, `FactionSpawnEggItem`) and the goal library (`entity/ai`) stay at the neutral top level. **The whole worker harvest economy is one race-generic class, `entity/WorkerEntity`** — find a node, mine it non-destructively, deliver into the nearest friendly core from `CoreCensus` — and a race's worker (`ProbeEntity`, `DroneEntity`) is a thin subclass supplying only its stats and its sounds. It sits at the neutral top level rather than inside one race's package, which is what the Drone used to have to reach into. Each unit's client renderer/model lives in the matching `client/protoss`/`client/zerg` subpackage — every unit has its own bespoke `MobRenderer`/model (not a reused vanilla `ZombieRenderer`/`SkeletonRenderer`). `entity/TeamColors` dyes a leather chestplate per faction for cheap visual team identity.

**A unit with a mode goes through the goal-priority ladder, never through a goal that knows about other goals.** The Lurker is the worked example: `entity/zerg/BurrowClock` is a pure state machine holding one depth (0 surfaced, 60 buried; the middle is neither mobile nor armed nor hidden), and the *only* thing that stops a dug-in unit being walked away is that `entity/ai/zerg/LurkerBurrowGoal` holds `MOVE`+`JUMP` and sits **below** every goal that needs the unit walking. `GoalSelector` only calls `canUse()` on a goal whose flags it can claim and hands a held flag over only to a strictly *lower* priority number, so the burrow goal never starts while something more important wants the unit, and being preempted is what surfaces it — its `stop()` is the only place that decision is written. Don't add "is it burrowed?" checks to the goal library; the two goals that genuinely needed telling both took the same kind of may-only-add-patience predicate `FactionTargetGoal` and `RetaliateGoal` carry, and for the same underlying reason — **a unit that stops its own navigation makes "standing still" stop meaning "stuck"**. `StuckWanderGoal` would otherwise dig it out to wander every 40s, and `SiegeBlockGoal`'s obstruction branch (which keys off "navigation done and not arrived") would surface it to chew through the first lip of terrain between it and a target it could already shoot over. A Lurker also refuses to be pulled out of the ground by a distant attacker, and that takes **all three** of the goals that can dig asking one shared question — `entity/ai/zerg/LurkerReach`, "is anything strikeable in spine range right now" — rather than reasoning about the current target: `LurkerHoldGroundGoal` sits above `RetaliateGoal` in the target selector and holds the `TARGET` flag so the near enemy is the one being shot, `LurkerApproachGoal` won't start while the answer is yes whoever set the target, and `LurkerBurrowGoal` keeps the unit down — it releases on its own `canContinueToUse` with no other goal involved, which is a dig-out the other two never see. Because the hold goal owns the `TARGET` flag whenever it runs, it owes the unit a *shootable* target on every tick, not just at the moment it claims one: it re-picks a claim that drifts out of spine range rather than holding it, since a held-but-unreachable target blocks re-acquisition and leaves the unit burrowed and silent. That predicate suppresses the dig branch only — building assault still preempts, or a Lurker parked by an enemy core with nothing alive to shoot would sit there. The entity backs the flag up with a hard stop (`customServerAiStep` zeroes horizontal movement, `isPushable`/`knockback` no-op) so physics can't drag a half-buried unit either — and deliberately *not* with `UnitStat.Builder.rooted()`, which is permanent and which `UnitStatsTest.onlyStaticDefenceIsRooted` polices.

Every unit's combat stats and production cost are centralized in `stats/UnitStats` — the single balance table (a `UnitStat` record per unit, built with a fluent builder) to edit for any tuning pass; entity classes hold no stat constants of their own, just a `private static final UnitStat STAT = UnitStats.X` field and a pointer-only javadoc line. `stats/UnitAttributes.apply(base, stat)` is the only place attributes get registered from it — each entity's `createAttributes()` is a one-line call, with the base builder (`Monster`/`Mob`/`PathfinderMob`) chosen by the caller since that's a Java-class fact, not a balance number. Every attribute is set explicitly, never left at a vanilla default: `Attributes.MOVEMENT_SPEED` defaults to 0.7 (not 0), so a rooted unit's `UnitStat.Builder.rooted()` states zero speed and full knockback resistance explicitly rather than relying on zero-as-absent (see docs/neoforge-api-notes.md). Costs are `stats/UnitCost` (interchangeable bundles of `stats/ResourceAmount`, paid via `stats/CostPayment`) — `race/UnitRoster` and the base/Gateway block entities all resolve a unit's cost from the table rather than owning their own constants.

Every attacking unit deals its **own** damage type, declared in `combat/AsteriskCraftDamageTypes` and defined by hand-written JSON under `data/asteriskcraft/damage_type/` — `Registries.DAMAGE_TYPE` is a datapack registry, so there is no `DeferredRegister` and nothing fails until a unit swings, which is what `DamageTypeResourceTest` guards. Damage is dealt through exactly three helpers, and new attacks should go through them rather than calling `hurtServer` directly: `entity/ai/HitscanAttacks` (ranged), `entity/ai/MeleeAttacks` (melee) and `combat/SuicideBlast` (detonation), each taking the attacker's damage type the same way they already take its particle and sound. Both build the source as `damageSources().source(key, attacker)` — **attributed**, which is what sets `getLastHurtByMob()` and so lets `entity/ai/RetaliateGoal` fire; the old shared `damageSources().magic()` carried no entity and nothing shot at range ever fought back. These types are all deliberately outside `#minecraft:bypasses_armor` (which `magic` is in), so armour reduces every hit. `#minecraft:no_knockback` is the one tag they split on, along the **melee/ranged** line: melee and the fanged strikes stay out of it and keep their stagger, while every type fired through `HitscanAttacks` is in it, because a shooter that nudges its target back on each shot kites whatever walks at it and an assault never closes. Membership is a data question only — the shove comes from `hurtServer` gated on that tag, and the additive tag file is `data/minecraft/tags/damage_type/no_knockback.json` — so a new attacker opts in or out there rather than in attack code. The fanged attackers are the awkward ones: a Sunken Colony's spike and each spine of a Lurker's row are vanilla `EvokerFangs`, whose damage is built in a private method, so `combat/FangStrikeDamageHandler` **cancels** vanilla's hit and re-deals it — a `LivingIncomingDamageEvent` can rewrite an amount but never substitute a `DamageSource`. It matches on `entity/zerg/FangStrikeEntity`, the shared base, and takes the type and the amount off the spike rather than naming a unit, so a new fanged attacker needs nothing there; `entity/ai/zerg/GroundStrike` is the footing search both share. `combat/SuicideBlast` needs no such dance — `Level.explode` has an overload taking both a `DamageSource` and an `ExplosionDamageCalculator`, so type and amount are substitutable up front — but it is the mod's **one** damage path that does not resolve hostility: it leaves `shouldDamageEntity` at its default, so a detonation catches friendly Zerg and the player too. That is a statement that a blast is not targeting rather than a hole in the choke point; hostility still decides everything up to the moment it goes off, including which enemy `SiegeTarget`s it charges. Buildings are charged explicitly through `damageBuilding` and never ride on the explosion, because a building's health is on its block entity and not on its blocks — cratering the stonework does nothing to the building as a game object. See docs/neoforge-api-notes.md.

Air units (`entity/zerg/MutaliskEntity` and `entity/protoss/ScoutEntity`) hover a fixed height above the terrain, and the mechanism is deliberately invisible to the goal library: a vanilla `FlyingMoveControl` plus `entity/ai/HoverFlyingNavigation`, which lifts every destination to `ground + hoverHeight` **before** the path is computed. That altitude has to live in the path itself — `PathNavigation.followThePath` only advances a node when the mob is within 1 block of it on Y, so a flyer over a ground-hugging path re-paths forever (see docs/neoforge-api-notes.md). Because every movement goal reaches the world through `getNavigation().moveTo(...)`, `RangedAttackGoal`/`CommandedMoveGoal`/`GuardGoal`/`SiegeBlockGoal` all fly with no changes of their own; `entity/ai/HoverGoal` only holds altitude in the gaps between orders. Don't reimplement hovering inside a goal or a `MoveControl`.

Unit textures are hand-painted in Blockbench, not generated — see [docs/texturing.md](docs/texturing.md). Every cube owns its own UV island, and `tools/blockbench_export.py` converts a model's `createBodyLayer()` into a `.bbmodel` (packing those islands on first migration). This constrains how model classes may be written: each cube needs its own `texOffs(int, int)` literal, so a model must not build several cubes through one call site (no UV constants, no multiply-called helper, no loop over parts, no shared `CubeListBuilder`). `ModelUvLayoutTest` fails the build if any two islands overlap.

Registration is centralized in `AsteriskCraft.java` (blocks, items, block entities, entity types, creative tab, entity attributes — all via `DeferredRegister`) with a separate client-only companion `client/AsteriskCraftClient.java` (`@Mod(dist = Dist.CLIENT)`) for renderers/model layers, since client-only classes must never load on a dedicated server.

`game/GameBootstrap` places both sides' starting bases on first world join rather than at server start, because the player's chunk is guaranteed loaded with settled terrain height by then. It is entirely profile-driven — which template is stamped, what ground cover is laid, what static defence is planted, which worker is spawned, what each side's bank is seeded with (`startingBank` for the computer, `playerBank` for the human) and what the player opens their inventory with (`playerKit`; the Command Crystal is the one race-generic item and stays here) all come off each side's `RaceProfile` — so it never names a Hive or a Drone. It is also where the match itself is decided: it freezes `MATCH_SETUP` from the `player_race` and `ai_race` game rules, tags the player with their side *and* race, and records `FactionAttachments.COMMANDED`. `game/GameAttachments` holds the level-scoped saved state (has-bootstrapped flag, `MatchSetup`, game-over flag, the AI interpreter cursor); **base positions are deliberately not among them** — `CoreCensus` owns that.

**World creation.** The race pickers are `client/RacePickerOverlay`, two `CycleButton`s (Race and Enemy Race) added to `CreateWorldScreen` through `ScreenEvent.Init.Post` — that event is the only seam, since the screen's three tabs are private inner classes with no NeoForge hook. They store nothing: they write the `player_race` and `ai_race` game rules on the `GameRules` the screen's `WorldCreationUiState` already carries into the world it builds, so the pickers and More → Game Rules can never disagree, and a dedicated server — where no creation screen runs — sets the same rules. The two pickers are independent — either may show any race, the other's included, since a mirror is a real match and `MatchSetup.forRaces` honours whatever pair it is handed. Anything else that has to be chosen per world before the world exists wants the same shape. **Because the widget belongs to the screen rather than to a tab, it takes two extra pieces to behave like a member of the Game tab it sits in.** It follows the Allow Commands button — found by walking each widget's message for the `selectWorld.allowCommands` translation key, since a `CycleButton`'s message is name-and-value and matching rendered text would break in every language but English — and borrows its x and width so the column lines up. And because `TabManager` *adds and removes* a tab's widgets on every switch, "is the anchor currently one of the screen's children" is exactly "is the Game tab open"; that is applied every frame from `ScreenEvent.Render.Pre`, because `AbstractWidget.extractRenderState` is final and skips an invisible widget outright, so there is no hook on the widget itself. A missing anchor falls back to the footer band rather than to no pickers at all.

The computer player is `director/AiDirector`, and it is race-agnostic: `director/script/` above it (the parser, the pure `ScriptInterpreter`, the `DirectorWorld` seam) always was, and the director itself now reads its side from `MatchSetup` and everything it builds from that side's `RaceProfile`. Build scripts are per race, loaded from `data/asteriskcraft/build_scripts/<race>.txt` (the path each profile declares) and datapack-overridable. Putting the computer on the Protoss is a change to what `GameBootstrap` writes and no change at all to the director — which is now what the race picker does, so both sides of the table are exercised in play.
