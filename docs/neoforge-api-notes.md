# MC 26.1.2 / NeoForge 26.1.2.80 API notes

Project targets Minecraft 26.1.2 + NeoForge 26.1.2.80 (see [gradle.properties](../gradle.properties)). This version is new enough that a lot of general MC-modding knowledge (including model training data) is stale for it. Verify against decompiled source before guessing, using the paths below.

## Where to find real source for this exact version

- Full decompiled + mapped Minecraft source (matches this project's mappings): `~/.gradle/caches/neoformruntime/intermediate_results/mergeWithSources_*_output.jar` — `unzip -l` it, then `unzip -p` specific `net/minecraft/...*.java` paths to read real method signatures instead of guessing.
  - **⚠️ The neoformruntime cache can hold jars from OTHER MC/NeoForge versions** (left by other projects on this machine). Not every `*_output.jar` matches 26.1.2.80 — some `sourcesAndCompiledWithNeoForge_*` / `recompile_*` / `rename_*` jars here are an **older** MC and will silently mislead you (they compile against different APIs). Before trusting a jar, sanity-check a known-26.1.2 signature: the real one's `AbstractContainerScreen` has `protected final int imageWidth` set via a 5-arg constructor and draws through **`GuiGraphicsExtractor`** (see the menus note below); an older jar has a mutable `imageWidth` and `GuiGraphics`/`renderBg`. The jars that carry `.java` sources AND match 26.1.2 are the `mergeWithSources_*` / `preProcessJar_*` family. When in doubt, the ground truth is `./gradlew compileJava` — code against what the compiler accepts, not what a stray jar shows.
- NeoForge-specific classes (`DeferredRegister`, `EventHooks`, attachment API, etc.): `~/.gradle/caches/modules-2/files-2.1/net.neoforged/neoforge/26.1.2.80/*-sources.jar`.
- Vanilla data (tags, recipes) for cross-checking format: `~/.gradle/caches/neoformruntime/artifacts/minecraft_26.1.2_client.jar` under `data/minecraft/...` and `assets/minecraft/...`.

## Concrete API facts (verified while building V2a — Gateway/Zealot/Dragoon)

- **Sun-burn is tag-gated, not class-gated.** `Mob.aiStep()` only calls `burnUndead()` if `this.getType().is(EntityTypeTags.BURN_IN_DAYLIGHT)`. That tag (`data/minecraft/tags/entity_type/burn_in_daylight.json`) is an explicit list of vanilla entity type IDs (`minecraft:zombie`, `minecraft:skeleton`, etc.). Any **custom** `EntityType` (this mod's Zealot/Zergling/Dragoon/Hydralisk included, none of which extend `Zombie`/`Skeleton` — see below) is automatically immune to sun damage — no override needed — because its own registry id was never added to that tag.
- **`Mob.finalizeSpawn(...)` is `@Deprecated`/override-only** in this version. External callers (anything spawning a mob programmatically, not overriding the method) must call `net.neoforged.neoforge.event.EventHooks.finalizeMobSpawn(mob, level, difficulty, spawnType, spawnData)` instead of `mob.finalizeSpawn(...)` directly — it fires `FinalizeSpawnEvent` then delegates.
- **`ValueOutput`/`ValueInput`** (block entity / entity NBT-replacement save API) use `store(String, Codec<T>, T)` and `read(String, Codec<T>) -> Optional<T>` — always Codec-based, no raw-Class overloads. For a custom enum, implement `StringRepresentable` and build `Codec<T> = StringRepresentable.fromEnum(T::values)` (see `Faction`); for a list, `codec.listOf()`.
- **`DyedItemColor` is a single-field record**: `DyedItemColor(int rgb)` — the old boolean "show in tooltip" param is gone. Apply via `stack.set(DataComponents.DYED_COLOR, new DyedItemColor(rgbInt))`.
- **`DeferredRegister.Items.registerItem(String, Function<Item.Properties, ? extends I>)`** is the way to register a plain custom `Item` subclass; `registerSimpleBlockItem` is only for `BlockItem`.
- **`EntityRenderersEvent.RegisterRenderers#registerEntityRenderer`** signature is `<T extends Entity> void registerEntityRenderer(EntityType<? extends T> type, EntityRendererProvider<T> provider)`. In principle a custom `EntityType<MySubclass>` extending a vanilla mob (e.g. `Zombie`/`Skeleton`) could reuse a vanilla renderer constructor reference like `ZombieRenderer::new`/`SkeletonRenderer::new` with no custom model — but this mod doesn't do that for any unit: every unit (Zealot/Dragoon/Probe/PhotonCannon/Zergling/Hydralisk/Drone) has its own bespoke `MobRenderer<X, LivingEntityRenderState, XModel>` and custom model, and none of the combat units extend `Zombie`/`Skeleton` at all (see below). Combine with a dyed leather chestplate (`DyedItemColor`) for cheap team-color visual identity.
- **Extending `Zombie`/`Skeleton` for a reskinned unit carries real behavioral baggage beyond rendering**, verified by reading the decompiled 26.1.2 source (`net/minecraft/world/entity/monster/zombie/Zombie.java`, `.../skeleton/AbstractSkeleton.java`, `.../monster/Monster.java`): `Zombie` still has a live chance to spawn a friendly "reinforcement" on Hard difficulty (`Attributes.SPAWN_REINFORCEMENTS_CHANCE`, baked into `Zombie.createAttributes()`) and will silently convert into a vanilla `Drowned` if left in water long enough (`convertsInWater()`), neither of which a subclass neutralizes just by overriding `registerGoals()`. `AbstractSkeleton.finalizeSpawn`/`populateDefaultEquipmentSlots` always puts a real `Items.BOW` in the main-hand slot (confirmed in source) — invisible only because the renderer isn't a `HumanoidRenderer` — plus unused Stray/powder-snow freeze-conversion machinery. Both vanilla bases already extend the plain `net.minecraft.world.entity.monster.Monster` (hostile sound category, xp reward, `Enemy` interface, `Monster.createMonsterAttributes()`), which has none of this baggage — so a melee reskin should extend `Monster` directly with a generic `MeleeAttackGoal` (not the Zombie-specific `ZombieAttackGoal`, which requires a `Zombie` in its constructor), and a ranged reskin should extend `Monster implements RangedAttackMob` (a plain interface, not `AbstractSkeleton`-only) with a plain `RangedAttackGoal`. Applied in this mod's `entity/protoss/ZealotEntity`, `entity/zerg/ZerglingEntity` (melee → `Monster`) and `entity/protoss/DragoonEntity`, `entity/zerg/HydraliskEntity` (ranged → `Monster implements RangedAttackMob`).
- **`NearestAttackableTargetGoal<T>`** has a constructor overload taking a `TargetingConditions.Selector` (`(LivingEntity target, ServerLevel level) -> boolean`). Prefer subclassing/parameterizing this with `LivingEntity.class` + a custom selector over writing a whole new `TargetGoal` from scratch for custom targeting rules (e.g. faction-based).
- **Recipes moved to singular path**: `data/<namespace>/recipe/*.json` (not `recipes/`), and shaped-recipe `result` is `{"id": "...", "count": n}` (the old `"item"` key is gone).
- **`UseOnContext`** (right-click-on-block item handling) exposes `getLevel()`, `getClickedPos()`, `getClickedFace()`, `getPlayer()`, `getItemInHand()` — enough to implement placement-style items without needing `BlockItem`.

See [BuildingKitItem.java](../src/main/java/net/bitflora/asteriskcraft/building/BuildingKitItem.java), [GatewayBlockEntity.java](../src/main/java/net/bitflora/asteriskcraft/building/GatewayBlockEntity.java), [ZealotEntity.java](../src/main/java/net/bitflora/asteriskcraft/entity/protoss/ZealotEntity.java), and [entity/ai/FactionTargetGoal.java](../src/main/java/net/bitflora/asteriskcraft/entity/ai/FactionTargetGoal.java) for these applied in practice.

## Concrete API facts (verified while planning V2b — command/selection, R5)

- **Ctrl is NOT known to the (dedicated) server.** Vanilla only syncs the sneak (Shift) state; the control key is never transmitted. Any input scheme needing Ctrl-modified clicks (StarCraft-style select-all-of-type) must read the modifier **client-side** and send it in a custom packet. This is the load-bearing reason R5 uses a client input handler + `CommandInputPacket` rather than server-side item callbacks.
- **`InputEvent.MouseButton.Pre`** (client, `net.neoforged.neoforge.client.event.InputEvent`) implements `ICancellableEvent` and exposes `getButton()` (0=left,1=right,2=middle — GLFW codes), `getAction()`, and `getModifiers()` (GLFW modifier bitmask — `GLFW_MOD_CONTROL`/`GLFW_MOD_SHIFT`). This is the right hook to intercept *all* in-world clicks with their modifiers; `setCanceled(true)` suppresses the vanilla attack/use. Gate it on a held marker item + `Minecraft.getInstance().screen == null` so normal play isn't swallowed.
- **`InputEvent.InteractionKeyMappingTriggered`** is the alternative click hook — cancelable, with `isAttack()`/`isUseItem()`/`isPickBlock()`/`getHand()` — but does **not** expose the raw modifier bitmask, so `MouseButton.Pre` is preferred when Ctrl/Shift matter.
- **`IItemExtension.onLeftClickEntity(ItemStack, Player, Entity)`** (return `true` to cancel) exists as a server-side left-click-on-entity callback, but it carries no modifier info and no raycast for empty clicks — insufficient alone for R5's Ctrl/air cases; the client-packet path covers all cases uniformly.
- **Client→server packets**: register in a `RegisterPayloadHandlersEvent` listener via `event.registrar("1").playToServer(Type<T>, StreamCodec<RegistryFriendlyByteBuf,T>, IPayloadHandler<T>)`. The payload is a `CustomPacketPayload` (needs a `Type<T>` id + `StreamCodec`). In the handler, `IPayloadContext.player()` returns the `ServerPlayer`; the handler runs on the network thread unless you enqueue to main — use `context.enqueueWork(...)` for world mutation, or `registrar.executesOn(HandlerThread.MAIN)`.
- **Client crosshair target**: `Minecraft.getInstance().hitResult` is the vanilla pick result (entity/block/miss) but only out to reach distance. For R5.7 ("move to farthest point in view") do a longer manual raycast — `level.clip(new ClipContext(...))` for blocks plus an entity sweep along `player.getViewVector(1f)` up to a chosen max (e.g. 64 blocks) — to classify ENTITY/BLOCK/MISS and capture the far point.

## Concrete API facts (verified while building the production GUI — container menus/screens)

This version has a **render-state extraction** GUI pipeline — screens don't draw with `GuiGraphics.render*` anymore. See [ProductionMenu.java](../src/main/java/net/bitflora/asteriskcraft/building/ProductionMenu.java), [ProductionScreen.java](../src/main/java/net/bitflora/asteriskcraft/client/ProductionScreen.java), and the block entities implementing [ProductionBuilding.java](../src/main/java/net/bitflora/asteriskcraft/building/ProductionBuilding.java).

- **`MenuType` with client data**: register a `DeferredRegister<MenuType<?>>` on `Registries.MENU`; build the type with `net.neoforged.neoforge.common.extensions.IMenuTypeExtension.create((windowId, playerInv, RegistryFriendlyByteBuf buf) -> new MyMenu(...))`. Bind the screen **client-side only** in a `RegisterMenuScreensEvent` handler: `event.register(MY_MENU.get(), MyScreen::new)`.
- **Opening a menu** server-side: `player.openMenu(MenuProvider, buf -> buf.writeVarInt(...))` — the `Consumer<RegistryFriendlyByteBuf>` extra data is read back by the client menu constructor. The block entity implements `MenuProvider` (`getDisplayName()` + `createMenu(int, Inventory, Player)`).
- **Buttons need NO custom packet**: override `AbstractContainerMenu.clickMenuButton(Player, int id)` (runs server-side) and, in the screen's button `onPress`, call `minecraft.gameMode.handleInventoryButtonClick(menu.containerId, id)`. Vanilla routes it. `menu.containerId` and `menu.slots` are `public`.
- **Live server→client sync of ints** (progress bars, counts): implement `ContainerData` on the BE (compute values live in `get(int)`), call `addDataSlots(data)` in the menu; the client menu uses a mirror `SimpleContainerData(n)`. Vanilla broadcasts deltas each tick.
- **A BE as a menu container**: implement `Container` directly on the block entity over a `NonNullList<ItemStack>`; persist with `ContainerHelper.saveAllItems(ValueOutput, list)` / `loadAllItems(ValueInput, list)` (they take the ValueOutput/ValueInput API — no manual codec). `stillValid` → `Container.stillValidBlockEntity(this, player)`. **Drop-on-break is automatic**: `BlockEntity.preRemoveSideEffects` already calls `Containers.dropContents` for any BE that `implements Container` — no block override needed.
- **`AbstractContainerScreen` is now extraction-based** (this is the big departure from older MC and from stale training data):
  - Constructor is `super(menu, inv, title, imageWidth, imageHeight)` — `imageWidth`/`imageHeight` are **`final`**, passed in (you can NOT assign them in the body). `inventoryLabelY` is still a mutable field.
  - Drawing methods take **`net.minecraft.client.gui.GuiGraphicsExtractor`**, not `GuiGraphics`. There is **no `renderBg`/`render(GuiGraphics,…)`** to override. Override `extractBackground(GuiGraphicsExtractor, mouseX, mouseY, float)` for the background (absolute coords; call `super` first) and `extractLabels(GuiGraphicsExtractor, mouseX, mouseY)` for the foreground (coords already translated to `leftPos/topPos`; call `super` for the title/inventory labels). Hovered-slot item tooltips are handled by the base `extractTooltip` — don't re-add them.
  - `GuiGraphicsExtractor` primitives: `fill(x1,y1,x2,y2,argb)`, `text(Font, Component, x, y, argb, boolean shadow)`, `centeredText(Font, Component, centerX, y, argb)`, `item(ItemStack, x, y)`, `blit(RenderPipeline, Identifier, …)`, and deferred tooltips via `setTooltipForNextFrame(...)`.
  - Widgets still work the classic way: `Button.builder(Component, onPress).bounds(x,y,w,h).tooltip(Tooltip.create(cost)).build()` added via `addRenderableWidget`; they render in absolute coords, so position them with `leftPos + …`.
  - **Blitting an arbitrary-resolution PNG scaled into a fixed on-screen size**: use the overload `blit(RenderPipeline, Identifier, int x, int y, float u, float v, int width, int height, int srcWidth, int srcHeight, int textureWidth, int textureHeight)` — `width`/`height` are the *destination* size in screen pixels, `srcWidth`/`srcHeight` is the region sampled from the texture (pass the source PNG's actual pixel dimensions for "whole image"), and `textureWidth`/`textureHeight` (pass the same source dimensions again) is only used to normalize UVs — so it works for any source resolution, no atlas/power-of-two requirement. Pipeline is `net.minecraft.client.renderer.RenderPipelines.GUI_TEXTURED`. No manual texture registration needed: any PNG under `assets/<modid>/textures/...` loads lazily by `Identifier` the same way vanilla GUI background textures do (see `ProductionKind.Icon.FromTexture`, `ProductionScreen#drawIcon`).

## Concrete API facts (verified while building V3 — Zerg AI, win/lose)

- **`BlockEvent.BreakEvent` is GONE in 26.1.2.** The old Forge break event no longer exists (`unzip -p neoforge-sources.jar net/neoforged/neoforge/event/level/BlockEvent.java` lists only `EntityPlaceEvent`, `EntityMultiPlaceEvent`, `NeighborNotifyEvent`, `FluidPlaceBlockEvent`, `FarmlandTrampleEvent`, `PortalSpawnEvent`, `BlockToolModificationEvent` — no `BreakEvent`). Do **not** try to detect block destruction with it.
- **Detect a block being removed via `BlockEntity.preRemoveSideEffects(BlockPos, BlockState)`** (override on the BE). `LevelChunk.setBlockState` calls it server-side whenever a BE's block is replaced by a *different* block with side effects enabled (i.e. all normal breaks: player mining, `level.destroyBlock`, explosions, overwrites) — **not** on a suppressed-update set (flag `256`). The vanilla base impl already drops a `Container` BE's contents, so `super.preRemoveSideEffects(...)` keeps drop-on-break; add your logic after. This is the single clean hook for "this core was destroyed → resolve the match" (see `NexusBlockEntity`/`HiveBlockEntity`). There is also a block-level `BlockBehaviour.affectNeighborsAfterRemoval(BlockState, ServerLevel, BlockPos, boolean)` if you need the *block* rather than the BE.
- **Expose a `Container` block entity as an item handler** for the transfer/capability API: register in a `RegisterCapabilitiesEvent` listener (mod bus) with `event.registerBlockEntity(Capabilities.Item.BLOCK, MY_BE_TYPE.get(), (be, side) -> VanillaContainerWrapper.of(be))`. `net.neoforged.neoforge.transfer.item.VanillaContainerWrapper.of(Container)` returns a `ResourceHandler<ItemResource>` — this is what lets a Probe/Drone's existing `Capabilities.Item.BLOCK` insert deposit into a custom building inventory (a plain vanilla `Container` BE is **not** auto-exposed; chests are only handled because vanilla registers them).
- **Server tick handler**: subscribe a game-bus `@EventBusSubscriber(modid = MODID)` class's static method to `net.neoforged.neoforge.event.tick.ServerTickEvent.Post` (or `.Pre`); `event.getServer()` gives the `MinecraftServer` (→ `.overworld()`, `.getPlayerList().getPlayers()`). Fires only on the logical server. Used for the `ZergDirector` wave scheduler.
- **`AttachmentType.builder(...)` is ambiguous with a method reference** like `List::of` — it matches both `builder(Supplier<T>)` and `builder(Function<IAttachmentHolder,T>)`. Use an explicit no-arg lambda (`() -> List.of()`) so it resolves to the `Supplier` overload. A list attachment serializes with `BlockPos.CODEC.listOf().fieldOf("...")`.
- **`DustParticleOptions(int color, float scale)` takes a packed RGB int, not a `Vector3f`** (older-version knowledge/memory training data suggests a `Vector3f` ctor — that's stale here; `getColor()` is what returns a `Vector3f`, derived from the stored int via `ARGB.vector3fFromRGB24`). Spawn with `ServerLevel.sendParticles(ParticleOptions, x, y, z, count, dx, dy, dz, speed)`.

## Concrete API facts (verified while building beacon behavior for Nexus/Hive)

- **`canSeeSky` lives on `BlockAndLightGetter`, not `LevelReader` directly.** `default boolean canSeeSky(BlockPos)` returns `getBrightness(LightLayer.SKY, pos) >= 15` — an O(1) read of cached sky-light, no raycast/column scan. Available identically on `ServerLevel` and `ClientLevel` (both reach it via `LevelReader extends BlockAndLightGetter`). A solid block's *own* position reads 0 sky light, so check `pos.above()` for "is this building under open sky". Sky-light is synced to clients, so a client-side check agrees with the server without any extra network state.
- **Reuse the vanilla beacon beam with zero custom renderer code.** Implement `net.minecraft.world.level.block.entity.BeaconBeamOwner` (single method `List<Section> getBeamSections()`) on a block entity, then register `net.minecraft.client.renderer.blockentity.BeaconRenderer::new` for its `BlockEntityType` via `EntityRenderersEvent.RegisterRenderers#registerBlockEntityRenderer` (`BeaconRenderer<T extends BlockEntity & BeaconBeamOwner>` is generic over any such BE). No subclass, no custom render class. See `NexusBlockEntity`/`HiveBlockEntity` + `AsteriskCraftClient.onRegisterRenderers`.
- **`getBeamSections()` runs per render frame** (`BeaconRenderer.extract` reads it each frame), so beam on/off can be computed live from `level.canSeeSky(...)` client-side — no ticking, saved state, or sync flag needed for the visual. Return `List.of()` for no beam, or `List.of(new BeaconBeamOwner.Section(packedRgb))` for a beam of that color.
- **A single `Section` renders a full-height beam.** `BeaconRenderer.submit` clamps the *last* section's height to `MAX_RENDER_Y = 2048` regardless of its stored height (which starts at 1), and `getRenderBoundingBox` extends the AABB to Y=2048 so the beam isn't frustum-culled. So one `Section` = one solid beam to the render ceiling; multiple sections stack as colored runs.

## Concrete API facts (verified while porting 1.12 unit models — Zealot/Zergling/Hydralisk/Probe)

- **Porting a 1.12 `ModelBase`/`ModelRenderer` model is a mechanical box translation** into this version's data-driven mesh API. `tools/model_convert.py` parses an old `Model*.java` and emits a modern `createBodyLayer()`; `tools/make_model_class.py` wraps it into a full `EntityModel<LivingEntityRenderState>`. The mapping:
  - `new ModelRenderer(this, u, v)` → `CubeListBuilder.create().texOffs(u, v)`
  - `addBox(x,y,z,w,h,d, inflate)` → `.addBox(x,y,z,w,h,d[, new CubeDeformation(inflate)])` (all args are `float` now; old int w/h/d are fine widened)
  - `setRotationPoint(x,y,z)` [+ `setRotation(part,rx,ry,rz)` or `part.rotateAngleX=…` in the ctor] → `PartPose.offset(x,y,z)` / `PartPose.offsetAndRotation(x,y,z,rx,ry,rz)`
  - `part.mirror = true` → `CubeListBuilder.create().texOffs(u,v).mirror().addBox(...)`
  - `parent.addChild(child)` → `parent.addOrReplaceChild("child", builder, pose)` (nest in tree order; roots go under `mesh.getRoot()`)
  - `textureWidth/textureHeight` → `LayerDefinition.create(mesh, w, h)`
  - **Only parse the constructor** — the old `render()`/`setRotationAngles()` methods also assign `rotateAngle*`, but those are animation and must not be baked into the static mesh. (Also: some of these old models omit the `this.` prefix; the converter handles both.)
- **`LayerDefinition.create(mesh, texW, texH)` sizes are UV coordinate space, not the PNG's pixel size.** A higher-res PNG works as long as it's an integer multiple with the same aspect ratio (the ported Zealot uses a 768×384 PNG against a declared 256×128 UV space — free HD skin). A wrong ratio / non-multiple gives scrambled UVs.
- **`Model.setupAnim(state)`'s base impl calls `resetPose()`** (restores every part to its `PartPose`), so an override should `super.setupAnim(state)` first, then *add* swing deltas onto the baked pose (`part.xRot += …`). Head-look uses the vanilla `HumanoidModel` convention: `head.yRot = state.yRot * (π/180)`, `head.xRot += state.xRot * (π/180)` where `LivingEntityRenderState.yRot/xRot` are the net head yaw/pitch in degrees; walk uses `state.walkAnimationPos`/`walkAnimationSpeed`.
- **Headless mesh smoke test**: `SomeModel.createBodyLayer().bakeRoot()` builds part geometry in memory (no GL), and constructing the model runs its `getChild(...)` animation lookups — so a JUnit test that does `new SomeModel(createBodyLayer().bakeRoot())` deterministically catches malformed hierarchies and misspelled part paths without `runClient`. See `client/ModelBakeTest`. (Visual pivots/UVs/animation still need `runClient`.)
- **Emissive glow + detail overlay as `RenderLayer`s** (the modern `submit(...)`/`SubmitNodeCollector` pipeline, not the old immediate-mode `doRenderLayer`):
  - Glow: extend `EyesLayer<S,M>` and return `RenderTypes.eyes(glowTexture)` from `renderType()` — full-bright, ignores world light. `EyesLayer.submit` re-submits the parent model for you. See `client/UnitGlowLayer`.
  - Overlay: extend `RenderLayer<S,M>` and in `submit(...)` call the inherited `coloredCutoutModelCopyLayerRender(getParentModel(), overlayTexture, pose, collector, light, state, -1 /*color*/, 1 /*order*/)` (uses `RenderTypes.entityCutout`). See `client/UnitOverlayLayer`.
  - Attach in the renderer ctor via `this.addLayer(new UnitOverlayLayer<>(this, OVERLAY))`. `RenderTypes` (plural) is the factory class in `net.minecraft.client.renderer.rendertype`; it also has `entityTranslucentEmissive(...)` if a translucent glow is wanted.
- **Per-entity render scale** goes in an override of `LivingEntityRenderer#scale(S state, PoseStack poseStack)` — `poseStack.scale(f,f,f)` (replaces the old `preRenderCallback` + `GlStateManager.scale`).
- **A `PartPose` xRot's *visible* direction depends on which way the cube grows from its pivot**, and getting this backwards silently produces a plausible-looking-but-wrong pose rather than an error. Rotation about x sends a local point `(0,y,z)` to `(0, y·cosθ − z·sinθ, y·sinθ + z·cosθ)`. Since "up" is `−y` here, a **positive** xRot tips a part's own long axis *forward* (toward `−z`). So for the same `+0.5`:
  - a box growing **up** from its pivot (a spine, a hood, a torso) leans **forward**, and negative rakes it **back**;
  - a box growing **down** (an arm hanging off a shoulder) swings **back**, and negative throws it **forward**;
  - a box growing along **+z** (a tail segment) tips **down**, and negative lifts it **up**;
  - a box growing along **−z** (a jaw, a snout, a mandible) tips **down** too — same sign as `+z`, since it is the part's axis and not the world that rotates.

  Chains compound: a limb's real angle is the sum down the parent chain, which is how a curve gets faked out of straight boxes (`ZerglingModel`'s kaiser blades, `HydraliskModel`'s scythes). Worth checking each rotation against its box's growth direction before trusting a pose — `HydraliskModel` was authored once with the up-growing convention applied to everything and came out with the tail buried in the ground and the arms reaching backwards.

## Concrete API facts (verified while porting 1.12 unit sounds — Zealot/Zergling/Hydralisk/Probe)

- **Registering a custom `SoundEvent`**: `DeferredRegister<SoundEvent> SOUND_EVENTS = DeferredRegister.create(Registries.SOUND_EVENT, MODID)`, then `SOUND_EVENTS.register("entity.zealot.ambient", () -> SoundEvent.createVariableRangeEvent(id("entity.zealot.ambient")))` (`createFixedRangeEvent(id, range)` also exists for a hardcoded audible radius). Register the `DeferredRegister` on the mod bus like any other (`SOUND_EVENTS.register(modEventBus)`).
- **Override the standard `LivingEntity`/`Mob` sound hooks** to point at it: `protected SoundEvent getAmbientSound()`, `protected SoundEvent getHurtSound(DamageSource source)`, `protected SoundEvent getDeathSound()` — same signatures as vanilla (e.g. `Zombie`/`Skeleton` already override these for their own sounds; just override again in the subclass to replace them).
- **Multiple ambient variants don't need multiple `SoundEvent`s.** `assets/<modid>/sounds.json` lets one event name list several `.ogg` files under `"sounds"`; the client sound system already picks one at random per play (this is how vanilla mobs like Villagers get varied ambient barks). So a single registered `SoundEvent` per ambient/hurt/death category is enough even when the source had 4 idle-line files.
- **`sounds.json`'s `"subtitle"` field is a literal translation-key string, not auto-derived from the event's own path** (confirmed in `SoundEventRegistrationSerializer`: `GsonHelper.getAsString(object, "subtitle", null)` reads it verbatim). Set it explicitly per entry and define the matching key in `lang/en_us.json` (e.g. `"subtitles.entity.asteriskcraft.zealot.hurt"`) — omitting the field just means no subtitle shows, no error.
- **An entity subclass with no sound override inherits its Java superclass's sounds**, not its sibling's — e.g. `DroneEntity extends ProbeEntity` picks up the Probe ambient/hurt/death overrides for free (matching the shared-model precedent), while `DragoonEntity extends Skeleton` directly still gets vanilla skeleton sounds since the old mod had no Dragoon/Drone sound assets to port (consistent with those two having no ported geometry either).

## Concrete API facts (verified while building the shared per-army `ArmyBank`)

- **`AttachmentHolder.getData(AttachmentType)` is compute-once-and-cache, not compute-every-call.** Confirmed in `AttachmentHolder.java` (neoforge sources jar): on first access it calls the default-value supplier, `put`s the result straight into the holder's own attachment map, and every later `getData` call for that type returns that *same* stored instance. So a **mutable** default value (e.g. a `NonNullList<ItemStack>`) genuinely aliases across every caller sharing the same holder — this is what lets `ArmyBank.of(level, faction)` back a real "linked chest" for multiple block entities, with no separate cache needed. `serializeAttachments` reads whatever is currently in that map at save time, so in-place mutations persist correctly with zero extra plumbing.
- **`AttachmentType.Builder.serialize(...)` takes a `MapCodec<T>`, not a plain `Codec<T>`** — wrap with `.fieldOf("name")` (same pattern already used by `GameAttachments`, e.g. `Codec.BOOL.fieldOf("value")`).
- **`BlockEntity.preRemoveSideEffects`'s vanilla body is exactly**: `if (this instanceof Container container && this.level != null) Containers.dropContents(this.level, pos, container);` (confirmed in the decompiled source) — nothing else. If a BE's `Container` is backed by data shared with other buildings (like `ArmyLinkedContainer`), overriding this method to skip `super` entirely is the correct way to opt out of that auto-drop-and-clear; don't call `super.preRemoveSideEffects(...)` in that case.
- **`preRemoveSideEffects` is called from `LevelChunk.setBlockState`, *after* the new state is already written into the section** (and only server-side, and only when the caller didn't pass flag `256` to suppress side effects). So it fires for every ordinary removal route — mining, `destroyBlock`, explosions, `/setblock` — and anything it drops lands in open air, not inside the block that is going away.
- **`Containers.dropItemStack(Level, double x, double y, double z, ItemStack)` is public** and is the vanilla "chest broke" drop: it **consumes** the stack you hand it, `split`ting it into piles of 10–30 with a small random spread. `dropContents(Level, BlockPos, Container)` is just a loop over it. Pass a stack you're happy to see emptied, and don't bother pre-splitting to max stack size.
- **There is no `BlockEntity.onLoad` in 26.1.2** — the lifecycle methods are `setLevel`, `clearRemoved`, `setRemoved`, `preRemoveSideEffects`. For "run once when this BE comes into the world, however it got there", the cheapest reliable hook is a transient boolean checked in the BE's own server ticker (this is how `CoreCensus` enrolment works).

## Concrete API facts (verified while building the data-driven Zerg build scripts — `director/script`)

- **The datapack reload-listener event is `net.neoforged.neoforge.event.AddServerReloadListenersEvent`, not `AddReloadListenerEvent`** (that older name doesn't exist here — confirmed by `unzip -l` on the neoforge sources jar, which lists only `AddServerReloadListenersEvent` + `AddClientReloadListenersEvent`, both extending `SortedReloadListenerEvent`). It's a **game-bus** event, so subscribe with a `@EventBusSubscriber(modid = MODID)` static `@SubscribeEvent`. Register a listener with `event.addListener(Identifier key, PreparableReloadListener listener)` (the `key` is a dependency-sort id, any unique `Identifier` — not the resource path). `addRetainedListener(ListenerKey, T)` is the variant for listeners that should survive a partial reload.
- **`SimplePreparableReloadListener<T>` signatures take `ProfilerFiller`** (`net.minecraft.util.profiling.ProfilerFiller`): `protected T prepare(ResourceManager, ProfilerFiller)` (runs off-thread) and `protected void apply(T, ResourceManager, ProfilerFiller)` (runs on the game thread). Do heavy IO/parsing in `prepare`, mutate live state in `apply`.
- **`ResourceManager` uses `Identifier`, not `ResourceLocation`** (matches this project's convention): `Map<Identifier, Resource> listResources(String directory, Predicate<Identifier> filter)` and `List<Resource> getResourceStack(Identifier)`. For a single canonical file with datapack-override semantics, `getResourceStack(id)` returns matching resources **low→high priority — take the last** (highest-priority pack wins). `Resource.openAsReader()` gives a UTF-8 `BufferedReader`.
- **Data pack (server) resources live under `data/<namespace>/<dir>/...`** and are read by these server reload listeners; a plain-text (non-JSON) format works fine — just read the reader's lines yourself instead of using `SimpleJsonResourceReloadListener`. Example: `data/asteriskcraft/build_scripts/zerg.txt`.

## Concrete API facts (verified while building the Sunken Colony — Evoker Fangs, custom render states)

- **`EvokerFangs` damage is hardcoded and un-overridable.** `net/minecraft/world/entity/projectile/EvokerFangs.java` deals its hit from a **private** `dealDamageTo(LivingEntity)` with a literal `6.0F`, called from `tick()` at `warmupDelayTicks == -8`, against *every* `LivingEntity` in `getBoundingBox().inflate(0.2, 0.0, 0.2)` except the owner and `owner.isAlliedTo(target)` (vanilla scoreboard teams — it knows nothing about a custom faction attachment). A subclass can't change either rule from inside: overriding `tick()` wholesale would strand the private `warmupDelayTicks`/`lifeTicks`/`sentSpikeEvent` fields and the client-side `getAnimationProgress` bite animation with them. **Correct it from outside instead** — a `LivingIncomingDamageEvent` listener keyed on `event.getSource().getDirectEntity() instanceof MySubclass` can both `setAmount(...)` and `setCanceled(true)`. Use `EventPriority.HIGHEST` if another listener (here `ShieldEventHandler`) also rewrites the amount and must see the corrected value. See `combat/SunkenSpikeDamageHandler`.
- **`EvokerFangs`' public convenience constructor hardcodes `EntityType.EVOKER_FANGS`** (`this(EntityType.EVOKER_FANGS, level)`), so a subclass must *not* delegate to it — it would register the entity under the wrong type. Rebuild it from the `(EntityType, Level)` constructor plus the public `setOwner`/`setYRot`/`setPos`. The one thing that can't be reproduced is the `warmupDelayTicks` argument (private field, no setter), so a subclass is limited to a 0-tick delay; that only matters for staggering a marching line of fangs.
- **A subclass of a vanilla entity gets the vanilla renderer for free.** `EvokerFangsRenderer` is declared `EntityRenderer<EvokerFangs, EvokerFangsRenderState>` and `EntityRenderersEvent.RegisterRenderers#registerEntityRenderer` takes `EntityType<? extends T>`, so `event.registerEntityRenderer(MY_FANGS.get(), EvokerFangsRenderer::new)` compiles and works with no model, texture, or render state of our own. Same trick applies to any vanilla renderer whose generic bound is the class being extended.
- **`LivingEntityRenderState` has no attack/swing field in this version** — it carries only `bodyRot/yRot/xRot/deathTime/walkAnimation*/scale/pose/...` (attack timing lives on the humanoid states). A custom attack animation therefore needs a `class MyRenderState extends LivingEntityRenderState` with its own field, returned from `createRenderState()` and filled in an override of `EntityRenderer#extractRenderState(T entity, S state, float partialTicks)` (call `super` first). `EntityRenderState` does expose `ageInTicks` and `partialTick`, which are enough for idle cycles and smooth interpolation of a tick-counted animation.
- **Sync an animation trigger as a `SynchedEntityData` int, not a `broadcastEntityEvent` byte**, unless you've checked the byte against `LivingEntity.handleEntityEvent`'s crowded switch. `SynchedEntityData.defineId(MyEntity.class, EntityDataSerializers.INT)` + `defineSynchedData(SynchedEntityData.Builder)` gives the client the animation's *remaining* ticks (not just its start), which is what lets the renderer interpolate with `partialTicks`.

## Concrete API facts (verified while animating the Zealot's melee strike)

- **`LivingEntity#swing(InteractionHand, boolean)` is the single hook for "this mob just attacked".** `MeleeAttackGoal.checkAndPerformAttack` calls `this.mob.swing(InteractionHand.MAIN_HAND)` immediately before `this.mob.doHurtTarget(...)` (`net/minecraft/world/entity/ai/goal/MeleeAttackGoal.java:128-129`), and the one-argument `LivingEntity.swing(InteractionHand)` is just `this.swing(hand, false)` (`LivingEntity.java:2066`). So overriding the **two-argument** form catches every swing — vanilla melee goals and our own `SiegeBlockGoal` block-battering alike — without either goal knowing an animation exists. Overriding the one-argument form instead would miss any caller that uses the two-argument one. Prefer this over `doHurtTarget`, which never fires when the mob is hitting a *block* rather than an entity.
- **A model part's rotation compounds with every ancestor's, and the sign is easy to get backwards.** Under `ModelPart.translateAndRotate` a part's own down-axis `(0,1,0)` maps to `(sin zRot, -cos zRot)` in the XY plane, so it swings toward **+x only for a positive net zRot** — and "net" includes the parent's. A child hung off an already-tilted parent (the Zealot's pauldron horns, on pauldrons tilted `-0.45`) needs a local rotation large enough to flip the *sum*, not just its own sign; otherwise it sweeps back across the body and disappears inside the parent. Verify with world-space AABBs rather than by eye.

## Concrete API facts (verified while building the Mutalisk — flight and hovering)

- **A hovering flyer must have its altitude baked into the *path*, not applied at the move control.** The obvious approach — leave the path on the ground and raise the wanted Y inside a `FlyingMoveControl` — deadlocks. `PathNavigation.followThePath()` advances to the next node only when `|mob.y − node.y| < 1.0` (`isCloseEnoughToCurrentNode`), and its fallback `shouldTargetNextNodeInDirection` first requires `mobPosition.closerThan(currentNode, 2.0)`. A mob flying six blocks above a ground-hugging path satisfies neither, so `doStuckDetection`/`timeoutPath` tears the path down and rebuilds it forever. Lifting the *destination* instead puts every node in open air, where advancement behaves normally. See `entity/ai/HoverFlyingNavigation`.
- **Every path-creating entry point funnels into one protected method**: `protected Path createPath(Set<BlockPos> targets, int radiusOffset, boolean above, int reachRange, float maxPathLength)`. `moveTo(x,y,z,speed)`, `moveTo(Entity,speed)`, `createPath(BlockPos,int)`, `createPath(Stream,int)` and `FlyingPathNavigation.createPath(Entity,int)` all reach it. Overriding that single overload to rewrite the target positions therefore changes pathing for *all* callers — which is what lets a whole goal library (`RangedAttackGoal`, `CommandedMoveGoal`, `GuardGoal`, `SiegeBlockGoal`) fly without any of those goals being touched, since they all move through `getNavigation().moveTo(...)`.
- **`FlyingMoveControl(mob, maxTurn, hoversInPlace)` owns the gravity flag.** It calls `mob.setNoGravity(true)` itself on every `MOVE_TO` tick, and with `hoversInPlace = true` it never calls `setNoGravity(false)` again — so a unit that has flown once stays weightless even when idle. The corollary: a freshly spawned flyer that has never been given a destination still has gravity and will drop to the ground, which is why an idle "hold altitude" goal is needed rather than optional. No `travel` override is required (vanilla `Bee` has none); `LivingEntity.travel`'s no-gravity path handles it.
- **`Attributes.FLYING_SPEED` is what actually governs an airborne mob.** `FlyingMoveControl.tick` picks `MOVEMENT_SPEED` only while `mob.onGround()` and `FLYING_SPEED` otherwise, so a flyer needs both registered or it crawls the moment it lifts off.
- **`PathNavigation.setRequiredPathLength(float)` needs raising for long-range flyers.** The default is far shorter than a 32-block `FOLLOW_RANGE`, so a flyer gives up mid-approach on distant targets; vanilla `Bee` sets 48 for the same reason.
- **`FlyingPathNavigation.isStableDestination(BlockPos)` requires a block that can be stood on below the destination** (`entityCanStandOn`), which is never true of a point in open air. Override it to `true` on a hovering navigation.
- **`level.getHeightmapPos(Heightmap.Types.MOTION_BLOCKING_NO_LEAVES, pos)`** is the cheap way to ask "where is the ground in this column" — a cached heightmap read, no raycast, available on both `ServerLevel` and `ClientLevel` (same family as the `canSeeSky` note above).
- **No heightmap answers "where is the ground" precisely enough to place a structure on; you need a downward scan, and its stop condition must be a positive test for ground.** `WORLD_SURFACE` counts *any* non-air block, so it lands on the canopy. `MOTION_BLOCKING_NO_LEAVES` discounts leaves and anything that doesn't block motion (vines included), but still counts logs and fluids, so it lands on a trunk top or a water surface — it's the right *start* for the scan, not the answer. Descending until "not air and not a log or leaves" then fails in a jungle, where the canopy is draped in vines and cocoa that are neither. The robust stop condition is `BlockState.isSolidRender() && !state.is(BlockTags.LOGS)`: per `BlockBehaviour.BlockStateBase` (`solidRender = Block.isShapeFullBlock(occlusionShape)`, and `occlusionShape` is empty whenever `canOcclude` is false), that one call rejects vines, cocoa, glow lichen, undergrowth, bamboo, snow layers, leaves and water without naming any of them, because `Properties.noCollision()`/`noOcclusion()` both clear `canOcclude`. Logs and mud *are* full-cube occluders, hence the explicit tag exclusion for logs. Caveat: farmland, dirt paths and soul sand aren't full-cube either, so a scan passes through them to the block below. See `game/GameBootstrap.isGround`.

## Concrete API facts (verified while building the Jade shield addon — `compat/jade`)

- **A modid-only Maven build of [Jade](https://jademc.readthedocs.io) for 26.1.2 doesn't exist yet** (checked CurseForge/Modrinth Maven); the only working build is a direct CurseForge file download (`Jade-mc26.1-NeoForge-26.1.8.jar`), dropped into `./libs/` and referenced via `compileOnly files(...)` / `localRuntime files(...)` — no `flatDir` repo needed for a `files()` dependency, and none was added.
- **Jade's own API already uses `net.minecraft.resources.Identifier`, not `ResourceLocation`**, confirmed by decompiling the jar's `snownee.jade.api.*` classes directly (`javap` against the extracted jar) — the official [Jade plugin docs](https://jademc.readthedocs.io/en/latest/plugins22/getting-started/) still show `new ResourceLocation(...)` snippets, which are stale for this MC version (matches this project's own convention: `AsteriskCraft.id(String)` already returns `Identifier.fromNamespaceAndPath(...)`).
- **`@WailaPlugin` needs no explicit value** — `WailaPlugin.value()` defaults to `""`; Jade's own bundled plugins (`VanillaPlugin`, `CorePlugin`) use the bare annotation. Jade discovers plugins via NeoForge's normal annotation/mod-file scan, not a `META-INF/services` entry or a `neoforge.mods.toml` entrypoint — nothing beyond an optional `jade` mods.toml dependency is needed for discovery.
- **`IWailaClientRegistration.registerEntityComponent(IComponentProvider<EntityAccessor>, Class<? extends Entity>)`** takes a plain `Class`, not an `EntityType`. Registering broadly on `LivingEntity.class` and guarding inside the provider (as Jade's own bundled `StatusEffectsProvider` does) is the established pattern for a component that only applies to some entities, rather than registering once per concrete subclass.
- **Jade's class lookup walks superclasses only — never interfaces.** `snownee.jade.impl.lookup.HierarchyLookup.getInternal` recurses through `Class.getSuperclass()` and nothing else (read off the bytecode), so registering a provider against an *interface* (`SiegeTarget.class`, a capability marker, …) matches nothing at all — silently, with no warning. Register concrete classes (`NexusBlockEntity.class`, `GatewayBlock.class`, …) or a shared superclass, and guard inside the provider. `registerBlockDataProvider` takes a plain `Class<?>` and accepts either the block or the block-entity class (it feeds a `PairHierarchyLookup` holding one lookup for each); `registerBlockComponent` is `Class<? extends Block>` only.
- **A block entity's own state is not client-visible, so a block tooltip needs an `IServerDataProvider`** — unlike an entity data attachment with `.sync(...)`, which the client already has (that's why `ProtossShieldProvider` needs no data provider but `BuildingDefenseProvider` does). The tidy shape is `StreamServerDataProvider<BlockAccessor, D>`: implement `streamData` + `streamCodec` and the default `appendServerData`/`decodeFromData` handle the NBT round-trip, keyed by `getUid().toString()`. Returning `null` from `streamData` sends nothing. **The client half is a separate provider that must return the same uid** — `decodeFromData` looks the data up under the server provider's uid — which is Jade's own pattern (`EntityHealthAndArmorProvider` + its nested `Client`, both returning `JadeIds.MC_ENTITY_HEALTH`). Sharing a uid across the pair is safe: `PriorityStore` is a plain map keyed by uid, so the second registration just overwrites the same priority entry.
- **Every registered component/data provider needs a lang entry for Jade's config screen, or the game throws on startup.** Jade auto-adds a per-provider toggle to its plugin config screen (from `IToggleableProvider`, which every `IComponentProvider` extends) and asserts a translation exists for it at `config.jade.plugin_<modid>.<uid path>` (confirmed via a live `runClient` crash log: `java.lang.AssertionError: Missing config translation: config.jade.plugin_asteriskcraft.protoss_shield` thrown from `JadeClient.onGui`, which aborted the initial resource-pack load). Add the key to `assets/<modid>/lang/en_us.json` — e.g. `"config.jade.plugin_asteriskcraft.protoss_shield": "Protoss Shield"` — matching `getUid()`'s path exactly (see `JadeAddons`' own `en_us.json` for the naming convention: `config.jade.plugin_<addonmodid>.<uid path>`).

## Concrete API facts (verified while building the Blockbench export pipeline — `tools/blockbench_export.py`)

- **A cube's box-UV footprint on the atlas is `2 * (width + depth)` wide by `depth + height` tall**, confirmed by reading `ModelPart.Cube`'s constructor in the decompiled source: its UV columns run `u0 = xTexOffs`, `u1 = +depth`, `u2 = +depth+width`, up to `u4 = xTexOffs + depth + width + depth + width`, and its rows run `v0 = yTexOffs`, `v1 = +depth`, `v2 = yTexOffs + depth + height`. **`grow`/`CubeDeformation` does not affect UVs at all** — it only offsets the vertex positions — so inflate can be ignored entirely when computing texture layout.
- **Within that footprint, the six faces are NOT the layout you would guess, and two of the traps bite when painting a texture by script.** From the same constructor (columns `u0=u`, `u1=+d`, `u2=+d+w`, `u22=+d+2w`, `u3=+2d+w`, `u4=+2d+2w`; rows `v0=v`, `v1=+d`, `v2=+d+h`): the top row holds `DOWN` at `[u1,u2]` and `UP` at `[u2,u22]` — **both `w` wide**, so the second one ends at `u+d+2w`, *not* at `u3`. Painting the underside into `[u2,u3]` silently paints it over the `EAST` side instead whenever `w != d`. The bottom row is `WEST [u0,u1]`, `NORTH [u1,u2]`, `EAST [u2,u3]`, `SOUTH [u3,u4]`. Second trap: `ModelPart.Polygon`'s constructor assigns UVs by vertex index (`v[0]→(u1,v0)`, `v[1]→(u0,v0)`, `v[2]→(u0,v1)`, `v[3]→(u1,v1)`), which flips or rotates several faces relative to the naive corner order — on the `DOWN` (visually **top**, since these models are authored y-down) face the texture's *top* row is the cube's `maxZ`/back edge and its left column is `minX`. Any asymmetric detail — the Probe's chevron is the live example — comes out pointing backwards if this is assumed rather than read.
- **The `MeshDefinition`/`PartDefinition`/`CubeDefinition` builder API is write-only; reading geometry back requires reflection.** `PartDefinition.getChildren()` (returning `Set<Map.Entry<String, PartDefinition>>`) is public and `PartPose` is a public record with accessors, but `PartDefinition.cubes`/`.partPose` are private, every `CubeDefinition` field (`origin`, `dimensions`, `grow`, `mirror`, `texCoord`, `texScale`) is private, and `CubeDeformation.growX/Y/Z` plus `MaterialDefinition.xTexSize/yTexSize` are package-private with no getters. Plain `setAccessible(true)` works in the NeoForge JUnit bootstrap — **no `--add-opens` needed**. See `src/test/java/.../tools/ModelGeometry.java`.
- **`PartDefinition.children` is a `HashMap`, so its iteration order is NOT source order.** Anything that needs to correlate the baked tree back to the Java source (or produce a stable file) must sort children by name and key parts by their full slash-joined path, never by traversal index.
- **Building a `LayerDefinition` touches no registries** — it is pure geometry math — so `createBodyLayer()` and `bakeRoot()` can be called from a plain unit test without any world/registry setup (this is what `ModelBakeTest` and `ModelGeometryDumpTest` rely on).
- **The NeoForge JUnit bootstrap runs tests with the working directory set to `build/minecraft-junit`, not the project directory.** A test that writes output files must resolve the project root itself (e.g. walk up to the directory containing `gradle.properties`) or its output lands somewhere unexpected.
- **Blockbench's Java-entity space is the Minecraft one rotated 180° about the vertical axis, not merely mirrored in Y** — *both* X and Y are negated. Verified by reading Blockbench's own exporter (`js/formats/java/modded_entity.js`), which with the format defaults (`modded_entity_version: "1.17"`, `modded_entity_flip_y: true`) writes `rx = degToRad(-rotation[0])`, `ry = degToRad(-rotation[1])`, `rz = degToRad(rotation[2])`, and `origin[0] *= -1; origin[1] *= -1` (`+24` only at the root). Group origins are absolute in a `.bbmodel` and the codec subtracts the parent's, which also confirms only *translations* accumulate down the tree — rotations stay on their own group, exactly as `ModelPart` applies them at render time. `tools/blockbench_export.py` re-implements this export path and asserts it round-trips, so a convention drift fails loudly instead of producing a subtly skewed model.

## Concrete API facts (item models — verified while adding the Nexus Kit item)

- **A registered item needs an `assets/<modid>/items/<name>.json` file, not just `models/item/<name>.json`.** This version's item-model system is two layers: `items/<name>.json` is the per-item *definition* (`{"model": {"type": "minecraft:model", "model": "<modid>:item/<name>"}}`) that the item registry actually looks up; `models/item/<name>.json` is just the model geometry/texture it points to (`{"parent": "minecraft:item/generated", "textures": {"layer0": "..."}}`) and is inert without the definition file referencing it. Forgetting the `items/` file gives a **silently missing icon everywhere** (inventory, GUI slots drawn via `graphics.item(stack, x, y)`, item frames) rather than an error or the purple/black missing-texture checkerboard — there's no fallback because the item has no model source at all. Every existing kit item (`gateway_kit`, `photon_cannon_kit`) has both files; copy the pattern exactly for new items.

## Concrete API facts (structure templates — verified while moving the Nexus/Gateway onto `.nbt`)

- **`data/<namespace>/structure/<name>.nbt` in a mod's resources is loaded by the vanilla `StructureTemplateManager` with no registration at all.** Its constructor adds a `ResourceManagerTemplateSource` over `FileToIdConverter("structure", ".nbt")` (singular `structure` — the 1.19-era rename), behind the world-save `generated/` directory in priority order. Reach it with `ServerLevel.getStructureManager().get(Identifier)` → `Optional<StructureTemplate>` (`getOrCreate` is a trap: it returns a **blank** template rather than failing when the id is missing). Templates are server-side only, so nothing about them resolves in the JUnit bootstrap environment — see `BuildingTemplatesTest` for the raw-NBT workaround.
- **`StructureTemplate.placeInWorld(ServerLevelAccessor, BlockPos position, BlockPos referencePos, StructurePlaceSettings, RandomSource, int updateFlags)`** — `position` is the template's **min corner** (template-local `0,0,0` lands there), not its center. Air blocks stored in the template **are** placed over whatever was there (there is no default block-ignore processor; that's `BlockIgnoreProcessor`, opt-in), and block-entity NBT captured by the structure block is applied through `blockEntity.loadWithComponents(TagValueInput.create(...))`, so an exported custom core BE comes back with the field values it had in the design world. **That is a live trap for any state a freshly placed building is supposed to start with**, because the design world's copy was standing finished: `gateway.nbt` carries `WarpTicks: 0` and `nexus.nbt` carries a `CoreHealth` from an older balance pass, so a stamped building silently arrives fully warped in at stale HP rather than at its constructor's values. Anything that must be true of a *new* building has to be set explicitly after the stamp (`BuildingDefense.beginWarpIn` / `skipWarpIn`), never assumed from a fresh block entity.
- **`template.filterBlocks(minCorner, settings, block)` returns absolute world positions** (the 4-arg overload takes `boolean absolute` to opt out) and applies the settings' rotation/mirror to both position and state. It is also the only way to read *anything* out of a template before placing it: `BuildingTemplates` calls the `absolute = false` form with `BlockPos.ZERO` to find where the core block sits in template-local space, and anchors the whole structure on that column. That beats anchoring on the bounding box's center, which silently shifts the building when a structure-block export was framed a block wider on one side (this mod's `hive.nbt` is 8 wide with its core at local x=4).
- **`StructurePlaceSettings` defaults to `LiquidSettings.APPLY_WATERLOGGING`**, which re-applies the fluid it replaced to any waterloggable block (stairs, slabs, fences). A structure stamped at a shoreline therefore warps in flooded unless you `setLiquidSettings(LiquidSettings.IGNORE_WATERLOGGING)`.
- **`StructureTemplate` exposes no way to enumerate its blocks generically** — `palettes` is private and the only reader is `filterBlocks`, which needs the `Block` you're looking for. Anything wanting "all the solid blocks" (e.g. a precise footprint-clear check) has to work off `getSize()`'s bounding box instead. The workaround when you genuinely need the block list (`building/WarpScaffold`, which has to know what each square of the layout will become) is to **stamp the template for real and then read the world back** over its bounding box — placement is the only enumerator there is. Safe here because only the core block of `nexus.nbt`/`gateway.nbt` carries block-entity NBT, which the scaffold leaves alone; a template with other block entities in it (`hive.nbt` has sculk sensors) would lose their data to the round trip.
- **Templates are loaded only by the *server's* `StructureTemplateManager`.** They live under `data/`, and the client's `ResourceManager` only serves `assets/` — so no client-side code (a placement preview, a HUD) can ask a template for its size. Either sync it or declare it; this mod declares it (`BuildingTemplates.Footprint`) and pins the declaration to the `.nbt` with a unit test that reads the raw NBT, since the file is the source of truth and a re-export is the only thing that can move those numbers.

## Concrete API facts (entity spawn placement — verified while fixing wide units suffocating)

- **`EntityType.getSpawnAABB(double x, double y, double z)`** builds the box an entity of that type would occupy standing at those coordinates: `x/z ± (spawnDimensionsScale * width / 2)`, `y` to `y + spawnDimensionsScale * height`. This is the only thing that knows a unit's real footprint before the entity exists, so any "is this spot free" check for a *not-yet-spawned* mob has to go through the `EntityType`, not through the entity.
- **A mob wider than 1.0 overhangs its block on *both* sides.** Centred on a block centre (`x + 0.5`), a 1.4-wide unit spans `x - 0.2 .. x + 1.2` and therefore intersects three block columns per axis — nine columns in total. A placement check that only looks at the unit's own column (plus the one above it) passes happily while burying the unit in the wall beside it. `SpawnSpots` checks the whole spawn AABB for this reason; the mod's 1.4-wide units are the Sunken Colony and the Mutalisk, and the Photon Cannon is 2.6.
- **`CollisionGetter.noBlockCollision(@Nullable Entity, AABB)`** is the right free-space test for placement: block shapes only, no entities, no world border, and a null entity is accepted. `noCollision(AABB)` additionally sweeps entities, which makes a spot look occupied just because another unit is standing there. Deflate the box by a hair first — a unit exactly as wide as its block sits flush against the neighbouring column's face, which otherwise reads as a collision.
- **Suffocation itself is checked at eye height, not over the whole body** (`Entity.isInWall()`: an `AABB.ofSize(getEyePosition(), width * 0.8, 1.0E-6, width * 0.8)` against blocks whose `isSuffocating` is true). So a full-box clearance check at spawn time is strictly stronger than what suffocation requires — which is what you want for a rooted unit like the Sunken Colony, since it has no way to walk out of a bad spot.

## Concrete API facts (attribute defaults — verified while centralizing unit stats into `stats/UnitStats`)

- **`Attributes.MOVEMENT_SPEED` defaults to 0.7, not 0.** `LivingEntity.createLivingAttributes()` pre-registers `MOVEMENT_SPEED` (along with `MAX_HEALTH`, `ARMOR`, `KNOCKBACK_RESISTANCE`, and others) with no explicit value, so it sits at the attribute's own default — which for movement speed is 0.7. A rooted unit (Photon Cannon, Sunken Colony) that merely *skips* setting `MOVEMENT_SPEED` does not end up stationary; it ends up walking at the vanilla default. Zero must always be stated explicitly. `ARMOR` and `KNOCKBACK_RESISTANCE` default to 0.0, so those two are safe to leave unset if 0 is intended.
- **`FOLLOW_RANGE`'s attribute default (32) is not what a bare `Monster`/`Mob` actually gets.** `Mob.createMobAttributes()` = `LivingEntity.createLivingAttributes().add(Attributes.FOLLOW_RANGE, 16.0)` — it explicitly overrides the attribute to 16. So every unit's `.add(Attributes.FOLLOW_RANGE, 32.0)` is load-bearing despite the number matching the attribute's own default; leaving it out silently halves the unit's aggro range.
- **`Monster.createMonsterAttributes()` = `Mob.createMobAttributes().add(Attributes.ATTACK_DAMAGE)`** — i.e. it adds `ATTACK_DAMAGE` at the attribute's own default (2.0), with no explicit value. `PathfinderMob` (the Probe/Drone's base) adds nothing beyond `Mob.createMobAttributes()`, so a `PathfinderMob`-based unit has no `ATTACK_DAMAGE` attribute at all unless something explicitly registers one.
- **`AttributeSupplier.Builder.add(...)` keys a `HashMap`,** so calling it twice for the same attribute (e.g. a shared helper re-adding what the base builder already added) simply overwrites — the later call wins, with no "attribute already added" exception. This is what makes a single `UnitAttributes.apply(base, stat)` helper safe to layer on top of any of the three base builders.
- **`LivingEntity.getAttributeValue(Attribute)` throws, it does not fall back to a default, when the attribute was never registered on that entity.** `AttributeMap.getValue` delegates to `AttributeSupplier.getValue` → `getAttributeInstance`, which throws `IllegalArgumentException("Can't find attribute ...")` for an attribute the entity's `createAttributes()` never added. Concretely: the Photon Cannon registered no `ATTACK_DAMAGE` before this stats-centralization work, so `CannonFireGoal` had to read a static constant rather than `getAttributeValue(Attributes.ATTACK_DAMAGE)` — switching a goal to read the attribute is only safe once you've confirmed `createAttributes()` actually registers it.

## Concrete API facts (damage types — verified while giving every unit its own attack type)

- **`Registries.DAMAGE_TYPE` is a *datapack* registry, not a `DeferredRegister` one.** There is no registration code to write: drop a JSON at `data/<ns>/damage_type/<id>.json` and `RegistryDataLoader` picks it up from the mod's own resources. It's listed in `RegistryDataLoader.SYNCHRONIZED_REGISTRIES`, so it syncs to clients with no networking of your own. In Java you only declare the key: `ResourceKey.create(Registries.DAMAGE_TYPE, id)` (see `combat/AsteriskCraftDamageTypes`). The consequence is that a typo'd key compiles and boots fine and only fails when something actually attacks — hence `DamageTypeResourceTest`.
- **`ResourceKey`'s accessor is `identifier()`, not `location()`** in this version (it returns `Identifier`, matching `AsteriskCraft.id`). A lot of older modding material uses `location()`.
- **JSON shape** is the `DamageType` record: `message_id` (required), `scaling` (required — `never` / `when_caused_by_living_non_player` / `always`), `exhaustion` (required float), plus optional `effects` (`hurt`/`thorns`/`drowning`/`burning`/`poking`/`freezing`, default `hurt`) and `death_message_type` (`default`/`fall_variants`/`intentional_game_design`).
- **`message_id` is the death-message stem**: `DamageSource.getLocalizedDeathMessage` builds `death.attack.<message_id>`, with a `.player` variant used when the kill is attributed to a player. Write both or a raw key leaks into chat.
- **`minecraft:magic` silently carries tag memberships that a custom type does not inherit.** It is in `bypasses_armor`, `no_knockback`, `panic_causes`, `witch_resistant_to`, `bypasses_wolf_armor`, `always_triggers_silverfish` and `avoids_guardian_thorns`. Swapping away from it therefore turns armour reduction *on* and knockback *on* — the two that matter for balance — and stops animals panicking unless you re-add the type to `panic_causes`. Vanilla tags merge additively across packs, so a mod file at `data/minecraft/tags/damage_type/<tag>.json` adds to them rather than replacing (only `"replace": true` wipes).
- **`DamageSources.source(ResourceKey, Entity cause)` sets *both* `directEntity` and `causingEntity`** to that entity (it delegates to the 3-arg form). This matters twice over: `LivingEntity.resolveMobResponsibleForDamage` sets `lastHurtByMob` from `getEntity()` — which is what makes `entity/ai/RetaliateGoal` fire — and knockback direction comes from `getSourcePosition()`, which falls back to `directEntity.position()`. The cached no-arg accessors (`damageSources().magic()` and friends) carry **no** entity, so anything using them gets no kill credit, no aggro attribution, and no knockback regardless of tags.
- **`LivingIncomingDamageEvent` can rewrite the amount but cannot substitute the `DamageSource`.** To change the type of damage that some vanilla entity deals (the Sunken Colony's `EvokerFangs`-derived spike), cancel the event and re-deal with your own source. That is safe: `LivingEntity.hurtServer` fires the event through `CommonHooks.onEntityIncomingDamage` and, on cancel, pops its damage container and returns **before** touching `invulnerableTime` — so the cancelled hit leaves no i-frames to block the replacement. Attribute the replacement to something the handler's own guard won't match, or it recurses (see `combat/SunkenSpikeDamageHandler`, which attributes to the colony rather than the spike).
- **A cancelled event skips its remaining listeners** — NeoForge's default is `receiveCanceled = false` — so cancelling at `EventPriority.HIGHEST` keeps lower-priority handlers (`ShieldEventHandler`, `ZergRegenEventHandler`) from acting on a hit that never lands.
- **`Mob.doHurtTarget(ServerLevel, Entity)` builds its damage source inline** — `weaponItem.getDamageSource(this, () -> damageSources().mobAttack(this))` — with no seam to substitute a type, so a melee unit that wants its own type has to reimplement the method (`entity/ai/MeleeAttacks`). Two of vanilla's steps are safely droppable for this mod's units: the weapon/enchantment branches (units carry no main-hand item, only a dyed chestplate) and `playAttackSound()`, which is an **empty method** on `LivingEntity`. `causeExtraKnockback` reads `ATTACK_KNOCKBACK`, which `stats/UnitAttributes` never registers, so it was already being passed 0 — the 0.4 base shove comes from `hurtServer` itself, gated on the `no_knockback` tag.

## Concrete API facts (mob pathfinding — verified while fixing Dragoons sticking on group move orders)

- **A pathfinding node's footprint is `floor(width + 1)` x `floor(height + 1)` x `floor(width + 1)`, not `ceil`** (`NodeEvaluator.prepare`). Two silent traps fall out of this. A unit **exactly 2.0 tall needs three blocks of vertical clearance** while 1.99 needs two, so a flat-2.0 unit quietly refuses doorways and 2-high tunnels its 1.99-tall squadmates walk through. And **anything 1.0 or wider takes two nodes**, so it needs a clear 2x2 footprint per node and can never path through a one-block gap. Neither failure surfaces as an error — the mob just declines routes. `entity/UnitFootprintTest` pins both bounds.
- **A mob wider than one node aims at a block *seam*, not a block centre.** `Path.getEntityPosAtNode` computes `node.x + (int)(bbWidth + 1.0F) * 0.5`, and NeoForge's MC-94054 fix in `PathNavigation.followThePath` uses the matching cast, so a 1.1-wide mob targets `node + 1.0` while a 0.8-wide one targets `node + 0.5`. Combined with `maxDistanceToWaypoint = bbWidth > 0.75 ? bbWidth / 2 : 0.75 - bbWidth / 2` (0.55 at width 1.1), compared **per axis** with `<=`, and `WalkNodeEvaluator.getStart()` seeding the start node from `mob.blockPosition()` (the block under the mob's *centre*), a 1.1-wide mob standing on a block centre sits 0.50 from its own first waypoint against a 0.55 tolerance. Five hundredths of a block of margin, on X and on Z — one shove from a neighbouring unit stops node advancement. This is why the Dragoon needed crowd-avoidance (`command/MoveFormation`) that narrower units never did.
- **A wide mob can't climb hills at the default step height, and the pathfinder is not what's stopping it.** `Attributes.STEP_HEIGHT` is a `RangedAttribute(default 0.6, max 10.0)` read by `LivingEntity.maxUpStep()`, so an ordinary mob cannot *step* a full block — it has to **jump** every 1-block rise. `MoveControl.tick` only fires that jump when `yd > maxUpStep() && xd*xd + zd*zd < Math.max(1.0F, getBbWidth())` — note the horizontal term is compared against the **width itself, not its square**, so the trigger radius is `sqrt(max(1, width))`: 1.0 for a narrow mob, only 1.095 at width 1.2. Meanwhile a wide mob halts half its width from the ledge face (0.6 vs 0.3) and, per the seam note above, aims at 2x2 corners rather than block centres. The margin that comfortably fits a 0.6-wide unit nearly vanishes, and the mob grinds against the hillside instead of climbing. The path itself is fine throughout — `getNeighbors` derives `jumpSize = floor(max(1, maxUpStep))` = 1 and `findAcceptedNode` rejects only above `getMobJumpHeight() = max(1.125, maxUpStep)`, so a 1-block rise is always planned. **Fix by raising `STEP_HEIGHT` to ≥ 1.0 so the unit walks the rise and never consults the jump trigger.** Keep it **under 2.0**: at 2.0 `jumpSize` becomes 2 and the pathfinder starts routing up sheer two-block walls. Anything in `[1.0, 2.0)` changes only how a path is executed, never which paths exist. Applied to the Dragoon and Ultralisk via `UnitStat.stepHeight`; both bounds pinned by `entity/UnitFootprintTest`.
- **`WalkNodeEvaluator`'s large-mob branch is a leniency, not a penalty.** `boolean isLargeMob = this.entityWidth > 1` caps the node's type at `PathType.BIG_MOBS_CLOSE_TO_DANGER` (default malus 4.0F, `PathType:30`) when that is *cheaper* than the worst type in the mob's bounding box — so a wide mob is more willing to path near hazards, not less. Easy to misread as the cause when a wide mob won't move; it isn't.
- **`GoalSelector.tick()` never re-calls `start()` on a goal that is already running.** Cleanup only `stop()`s goals whose `canContinueToUse()` returns false; `start()` fires exclusively in the `!isRunning() && canUse()` branch. So any baseline a goal captures in `start()` — a cached destination, a progress record — goes stale the moment the underlying data changes while the goal keeps running, and **must be re-checked in `tick()`**. This bit `CommandedMoveGoal`: a second move order never restarted it, so it kept measuring progress against the previous destination and dropped the new order almost immediately. A general trap for the whole goal library. Corollary from the same read: `goalUpdate` (every goal's `canUse`) runs *before* `tickRunningGoals`, which is what lets a priority-0 goal observe `navigation.isDone()` before a lower-priority goal's `tick()` re-paths.
- **`PathNavigation.requiredPathLength` defaults to 16.0**, and `getMaxPathLength()` is `max(FOLLOW_RANGE, requiredPathLength)` — so a unit with `FOLLOW_RANGE 32` can never plan more than 32 blocks ahead however far it is ordered, and walks longer distances in re-pathed hops. The same value sets the A* visited-node budget via `updatePathfinderMaxVisitedNodes` = `floor(length * 16)`, which matters more: a two-node-wide mob exhausts the smaller budget quickly and gets a truncated path. Raise it with `setRequiredPathLength` to match the range orders can reach (`entity/ai/CommandableGoals.configureNavigation`).
- **`Entity.getPickRadius()` returns 0.0F**, so `ProjectileUtil.getEntityHitResult` picks against the raw hitbox. Shrinking a hitbox for pathfinding reasons directly shrinks the click target used to select that unit.
- **`GoalSelector` only calls `canUse()` on a goal whose flags it could actually claim.** `goalUpdate`'s condition is `!isRunning() && !goalContainsAnyFlags(g, disabledFlags) && goalCanBeReplacedForAllFlags(g, lockedFlags) && g.canUse()`, and `WrappedGoal.canBeReplacedBy` is `isInterruptable() && other.getPriority() < this.getPriority()` — **strictly** lower number. Two consequences for any goal that watches for a condition rather than waiting to be asked: it can only preempt a running goal from a lower priority number (equal priority never takes over), and while a higher-priority goal holds its flags its `canUse()` is **not called at all**, so any clock ticked there silently stops. `StuckWanderGoal` sits at -1 for exactly this reason: at priority 1 its stuck-detection clock would freeze precisely while a priority-0 goal had the unit pinned. Ticking a cooldown/clock inside `canUse()` is otherwise fine and is what `GuardGoal`/`SiegeBlockGoal` already do — `canUse()` runs every tick on a non-running goal, there is no polling interval.
- **Vanilla `RangedAttackGoal` neither strafes nor swings** (unlike `RangedBowAttackGoal`, which strafes): its `tick` calls `navigation.stop()` once the target is inside `attackRadius` with 5 ticks of line of sight, then fires through `performRangedAttack`. So a ranged unit in a firefight is perfectly motionless and never sets `LivingEntity.swinging` — "hasn't moved and hasn't swung" is not a sound stuck test for one. (`swinging` itself is a public field, set by `Mob.swing(hand)` and cleared by `updateSwingTime()` after `getCurrentSwingDuration()` ticks, both server-side.)

## Concrete API facts (drawing in the world — verified while building the kit placement outline)

- **`RenderLevelStageEvent` is no longer where custom geometry goes.** Its own javadoc points at **`SubmitCustomGeometryEvent`** (game bus, client only, fired between particle submission and opaque rendering) for anything that draws its own vertices — this version's level renderer is submit-based, and the stage events exist for code that needs a hook *point* rather than a buffer. The call is `event.getSubmitNodeCollector().submitCustomGeometry(poseStack, RenderType, (pose, buffer) -> …)`.
- **The submitted geometry is drawn later in the frame, so the lambda must not close over the live `PoseStack`.** `SubmitNodeCollection` stores the submit and replays it during the feature pass; the `PoseStack.Pose` handed to the callback is the snapshot taken at submit time. Emit vertices against that `pose` (`buffer.addVertex(pose, x, y, z)`) — calling `poseStack.last()` from inside the callback reads whatever the stack happens to hold when it runs. This is also why `ShapeRenderer.renderShape` (which takes a whole `PoseStack`) can't be used from inside one.
- **The pose stack for a level submit is identity, and world coordinates are camera-relative** — vanilla's own `renderBlockOutline` subtracts `levelRenderState.cameraRenderState.pos` from the block position rather than translating the stack. `CameraRenderState` is plain public fields, reachable from either event via `getLevelRenderState().cameraRenderState`.
- **The lines pipeline (`RenderTypes.lines()`, in `net.minecraft.client.renderer.rendertype`) needs a per-vertex normal *and* a per-vertex width**, both on every vertex: `addVertex(pose, x, y, z).setColor(argb).setNormal(pose, nx, ny, nz).setLineWidth(w)`. The normal is the segment's own direction, normalized (read straight off `ShapeRenderer.renderShape`, which is the whole of vanilla's box-outline drawing). Omitting either doesn't error — the line just comes out wrong or invisible.
