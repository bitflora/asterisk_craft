# MC 26.1.2 / NeoForge 26.1.2.80 API notes

Project targets Minecraft 26.1.2 + NeoForge 26.1.2.80 (see [gradle.properties](../gradle.properties)). This version is new enough that a lot of general MC-modding knowledge (including model training data) is stale for it. Verify against decompiled source before guessing, using the paths below.

## Where to find real source for this exact version

- Full decompiled + mapped Minecraft source (matches this project's mappings): `~/.gradle/caches/neoformruntime/intermediate_results/mergeWithSources_*_output.jar` — `unzip -l` it, then `unzip -p` specific `net/minecraft/...*.java` paths to read real method signatures instead of guessing.
  - **⚠️ The neoformruntime cache can hold jars from OTHER MC/NeoForge versions** (left by other projects on this machine). Not every `*_output.jar` matches 26.1.2.80 — some `sourcesAndCompiledWithNeoForge_*` / `recompile_*` / `rename_*` jars here are an **older** MC and will silently mislead you (they compile against different APIs). Before trusting a jar, sanity-check a known-26.1.2 signature: the real one's `AbstractContainerScreen` has `protected final int imageWidth` set via a 5-arg constructor and draws through **`GuiGraphicsExtractor`** (see the menus note below); an older jar has a mutable `imageWidth` and `GuiGraphics`/`renderBg`. The jars that carry `.java` sources AND match 26.1.2 are the `mergeWithSources_*` / `preProcessJar_*` family. When in doubt, the ground truth is `./gradlew compileJava` — code against what the compiler accepts, not what a stray jar shows.
- NeoForge-specific classes (`DeferredRegister`, `EventHooks`, attachment API, etc.): `~/.gradle/caches/modules-2/files-2.1/net.neoforged/neoforge/26.1.2.80/*-sources.jar`.
- Vanilla data (tags, recipes) for cross-checking format: `~/.gradle/caches/neoformruntime/artifacts/minecraft_26.1.2_client.jar` under `data/minecraft/...` and `assets/minecraft/...`.

## Concrete API facts (verified while building V2a — Gateway/Zealot/Dragoon)

- **Sun-burn is tag-gated, not class-gated.** `Mob.aiStep()` only calls `burnUndead()` if `this.getType().is(EntityTypeTags.BURN_IN_DAYLIGHT)`. That tag (`data/minecraft/tags/entity_type/burn_in_daylight.json`) is an explicit list of vanilla entity type IDs (`minecraft:zombie`, `minecraft:skeleton`, etc.). A **custom** `EntityType` that extends `Zombie`/`Skeleton` (like this mod's `ZealotEntity`/`DragoonEntity`) is automatically immune to sun damage — no override needed — because its own registry id was never added to that tag.
- **`Mob.finalizeSpawn(...)` is `@Deprecated`/override-only** in this version. External callers (anything spawning a mob programmatically, not overriding the method) must call `net.neoforged.neoforge.event.EventHooks.finalizeMobSpawn(mob, level, difficulty, spawnType, spawnData)` instead of `mob.finalizeSpawn(...)` directly — it fires `FinalizeSpawnEvent` then delegates.
- **`ValueOutput`/`ValueInput`** (block entity / entity NBT-replacement save API) use `store(String, Codec<T>, T)` and `read(String, Codec<T>) -> Optional<T>` — always Codec-based, no raw-Class overloads. For a custom enum, implement `StringRepresentable` and build `Codec<T> = StringRepresentable.fromEnum(T::values)` (see `Faction`); for a list, `codec.listOf()`.
- **`DyedItemColor` is a single-field record**: `DyedItemColor(int rgb)` — the old boolean "show in tooltip" param is gone. Apply via `stack.set(DataComponents.DYED_COLOR, new DyedItemColor(rgbInt))`.
- **`DeferredRegister.Items.registerItem(String, Function<Item.Properties, ? extends I>)`** is the way to register a plain custom `Item` subclass; `registerSimpleBlockItem` is only for `BlockItem`.
- **`EntityRenderersEvent.RegisterRenderers#registerEntityRenderer`** signature is `<T extends Entity> void registerEntityRenderer(EntityType<? extends T> type, EntityRendererProvider<T> provider)`. This means a custom `EntityType<MySubclass>` (e.g. `EntityType<ZealotEntity>` where `ZealotEntity extends Zombie`) can directly reuse a vanilla renderer constructor reference like `ZombieRenderer::new`/`SkeletonRenderer::new` — no custom renderer/model needed for a reskinned vanilla-mob-alike. Combine with a dyed leather chestplate (`DyedItemColor`) for cheap team-color visual identity.
- **`NearestAttackableTargetGoal<T>`** has a constructor overload taking a `TargetingConditions.Selector` (`(LivingEntity target, ServerLevel level) -> boolean`). Prefer subclassing/parameterizing this with `LivingEntity.class` + a custom selector over writing a whole new `TargetGoal` from scratch for custom targeting rules (e.g. faction-based).
- **Recipes moved to singular path**: `data/<namespace>/recipe/*.json` (not `recipes/`), and shaped-recipe `result` is `{"id": "...", "count": n}` (the old `"item"` key is gone).
- **`UseOnContext`** (right-click-on-block item handling) exposes `getLevel()`, `getClickedPos()`, `getClickedFace()`, `getPlayer()`, `getItemInHand()` — enough to implement placement-style items without needing `BlockItem`.

See [BuildingKitItem.java](../src/main/java/net/bitflora/asteriskcraft/building/BuildingKitItem.java), [GatewayBlockEntity.java](../src/main/java/net/bitflora/asteriskcraft/building/GatewayBlockEntity.java), [ZealotEntity.java](../src/main/java/net/bitflora/asteriskcraft/entity/ZealotEntity.java), and [entity/ai/FactionTargetGoal.java](../src/main/java/net/bitflora/asteriskcraft/entity/ai/FactionTargetGoal.java) for these applied in practice.

## Concrete API facts (verified while planning V2b — command/selection, R5)

- **Ctrl is NOT known to the (dedicated) server.** Vanilla only syncs the sneak (Shift) state; the control key is never transmitted. Any input scheme needing Ctrl-modified clicks (StarCraft-style select-all-of-type) must read the modifier **client-side** and send it in a custom packet. This is the load-bearing reason R5 uses a client input handler + `CommandInputPacket` rather than server-side item callbacks.
- **`InputEvent.MouseButton.Pre`** (client, `net.neoforged.neoforge.client.event.InputEvent`) implements `ICancellableEvent` and exposes `getButton()` (0=left,1=right,2=middle — GLFW codes), `getAction()`, and `getModifiers()` (GLFW modifier bitmask — `GLFW_MOD_CONTROL`/`GLFW_MOD_SHIFT`). This is the right hook to intercept *all* in-world clicks with their modifiers; `setCanceled(true)` suppresses the vanilla attack/use. Gate it on a held marker item + `Minecraft.getInstance().screen == null` so normal play isn't swallowed.
- **`InputEvent.InteractionKeyMappingTriggered`** is the alternative click hook — cancelable, with `isAttack()`/`isUseItem()`/`isPickBlock()`/`getHand()` — but does **not** expose the raw modifier bitmask, so `MouseButton.Pre` is preferred when Ctrl/Shift matter.
- **`IItemExtension.onLeftClickEntity(ItemStack, Player, Entity)`** (return `true` to cancel) exists as a server-side left-click-on-entity callback, but it carries no modifier info and no raycast for empty clicks — insufficient alone for R5's Ctrl/air cases; the client-packet path covers all cases uniformly.
- **Client→server packets**: register in a `RegisterPayloadHandlersEvent` listener via `event.registrar("1").playToServer(Type<T>, StreamCodec<RegistryFriendlyByteBuf,T>, IPayloadHandler<T>)`. The payload is a `CustomPacketPayload` (needs a `Type<T>` id + `StreamCodec`). In the handler, `IPayloadContext.player()` returns the `ServerPlayer`; the handler runs on the network thread unless you enqueue to main — use `context.enqueueWork(...)` for world mutation, or `registrar.executesOn(HandlerThread.MAIN)`.
- **Client crosshair target**: `Minecraft.getInstance().hitResult` is the vanilla pick result (entity/block/miss) but only out to reach distance. For R5.7 ("move to farthest point in view") do a longer manual raycast — `level.clip(new ClipContext(...))` for blocks plus an entity sweep along `player.getViewVector(1f)` up to a chosen max (e.g. 64 blocks) — to classify ENTITY/BLOCK/MISS and capture the far point.

## Concrete API facts (verified while building the production GUI — container menus/screens)

This version has a **render-state extraction** GUI pipeline — screens don't draw with `GuiGraphics.render*` anymore. See [ProductionMenu.java](../src/main/java/net/bitflora/asteriskcraft/building/ProductionMenu.java), [ProductionScreen.java](../src/main/java/net/bitflora/asteriskcraft/client/ProductionScreen.java), and the block entities implementing [ProductionBuilding.java](../src/main/java/net/bitflora/asteriskcraft/building/ProductionBuilding.java).

- **`MenuType` with client data**: register a `DeferredRegister<MenuType<?>>` on `Registries.MENU`; build the type with `net.neoforged.neoforge.common.extensions.IMenuTypeExtension.create((windowId, playerInv, RegistryFriendlyByteBuf buf) -> new MyMenu(...))`. Bind the screen **client-side only** in a `RegisterMenuScreensEvent` handler: `event.register(MY_MENU.get(), MyScreen::new)`.
- **Opening a menu** server-side: `player.openMenu(MenuProvider, buf -> buf.writeVarInt(...))` — the `Consumer<RegistryFriendlyByteBuf>` extra data is read back by the client menu constructor. The block entity implements `MenuProvider` (`getDisplayName()` + `createMenu(int, Inventory, Player)`).
- **Buttons need NO custom packet**: override `AbstractContainerMenu.clickMenuButton(Player, int id)` (runs server-side) and, in the screen's button `onPress`, call `minecraft.gameMode.handleInventoryButtonClick(menu.containerId, id)`. Vanilla routes it. `menu.containerId` and `menu.slots` are `public`.
- **Live server→client sync of ints** (progress bars, counts): implement `ContainerData` on the BE (compute values live in `get(int)`), call `addDataSlots(data)` in the menu; the client menu uses a mirror `SimpleContainerData(n)`. Vanilla broadcasts deltas each tick.
- **A BE as a menu container**: implement `Container` directly on the block entity over a `NonNullList<ItemStack>`; persist with `ContainerHelper.saveAllItems(ValueOutput, list)` / `loadAllItems(ValueInput, list)` (they take the ValueOutput/ValueInput API — no manual codec). `stillValid` → `Container.stillValidBlockEntity(this, player)`. **Drop-on-break is automatic**: `BlockEntity.preRemoveSideEffects` already calls `Containers.dropContents` for any BE that `implements Container` — no block override needed.
- **`AbstractContainerScreen` is now extraction-based** (this is the big departure from older MC and from stale training data):
  - Constructor is `super(menu, inv, title, imageWidth, imageHeight)` — `imageWidth`/`imageHeight` are **`final`**, passed in (you can NOT assign them in the body). `inventoryLabelY` is still a mutable field.
  - Drawing methods take **`net.minecraft.client.gui.GuiGraphicsExtractor`**, not `GuiGraphics`. There is **no `renderBg`/`render(GuiGraphics,…)`** to override. Override `extractBackground(GuiGraphicsExtractor, mouseX, mouseY, float)` for the background (absolute coords; call `super` first) and `extractLabels(GuiGraphicsExtractor, mouseX, mouseY)` for the foreground (coords already translated to `leftPos/topPos`; call `super` for the title/inventory labels). Hovered-slot item tooltips are handled by the base `extractTooltip` — don't re-add them.
  - `GuiGraphicsExtractor` primitives: `fill(x1,y1,x2,y2,argb)`, `text(Font, Component, x, y, argb, boolean shadow)`, `centeredText(Font, Component, centerX, y, argb)`, `item(ItemStack, x, y)`, `blit(RenderPipeline, Identifier, …)`, and deferred tooltips via `setTooltipForNextFrame(...)`.
  - Widgets still work the classic way: `Button.builder(Component, onPress).bounds(x,y,w,h).tooltip(Tooltip.create(cost)).build()` added via `addRenderableWidget`; they render in absolute coords, so position them with `leftPos + …`.

## Concrete API facts (verified while building V3 — Zerg AI, win/lose)

- **`BlockEvent.BreakEvent` is GONE in 26.1.2.** The old Forge break event no longer exists (`unzip -p neoforge-sources.jar net/neoforged/neoforge/event/level/BlockEvent.java` lists only `EntityPlaceEvent`, `EntityMultiPlaceEvent`, `NeighborNotifyEvent`, `FluidPlaceBlockEvent`, `FarmlandTrampleEvent`, `PortalSpawnEvent`, `BlockToolModificationEvent` — no `BreakEvent`). Do **not** try to detect block destruction with it.
- **Detect a block being removed via `BlockEntity.preRemoveSideEffects(BlockPos, BlockState)`** (override on the BE). `LevelChunk.setBlockState` calls it server-side whenever a BE's block is replaced by a *different* block with side effects enabled (i.e. all normal breaks: player mining, `level.destroyBlock`, explosions, overwrites) — **not** on a suppressed-update set (flag `256`). The vanilla base impl already drops a `Container` BE's contents, so `super.preRemoveSideEffects(...)` keeps drop-on-break; add your logic after. This is the single clean hook for "this core was destroyed → resolve the match" (see `NexusBlockEntity`/`HiveBlockEntity`). There is also a block-level `BlockBehaviour.affectNeighborsAfterRemoval(BlockState, ServerLevel, BlockPos, boolean)` if you need the *block* rather than the BE.
- **Expose a `Container` block entity as an item handler** for the transfer/capability API: register in a `RegisterCapabilitiesEvent` listener (mod bus) with `event.registerBlockEntity(Capabilities.Item.BLOCK, MY_BE_TYPE.get(), (be, side) -> VanillaContainerWrapper.of(be))`. `net.neoforged.neoforge.transfer.item.VanillaContainerWrapper.of(Container)` returns a `ResourceHandler<ItemResource>` — this is what lets a Probe/Drone's existing `Capabilities.Item.BLOCK` insert deposit into a custom building inventory (a plain vanilla `Container` BE is **not** auto-exposed; chests are only handled because vanilla registers them).
- **Server tick handler**: subscribe a game-bus `@EventBusSubscriber(modid = MODID)` class's static method to `net.neoforged.neoforge.event.tick.ServerTickEvent.Post` (or `.Pre`); `event.getServer()` gives the `MinecraftServer` (→ `.overworld()`, `.getPlayerList().getPlayers()`). Fires only on the logical server. Used for the `ZergDirector` wave scheduler.
- **`AttachmentType.builder(...)` is ambiguous with a method reference** like `List::of` — it matches both `builder(Supplier<T>)` and `builder(Function<IAttachmentHolder,T>)`. Use an explicit no-arg lambda (`() -> List.of()`) so it resolves to the `Supplier` overload. A list attachment serializes with `BlockPos.CODEC.listOf().fieldOf("...")`.
- **`DustParticleOptions(int color, float scale)` takes a packed RGB int, not a `Vector3f`** (older-version knowledge/memory training data suggests a `Vector3f` ctor — that's stale here; `getColor()` is what returns a `Vector3f`, derived from the stored int via `ARGB.vector3fFromRGB24`). Spawn with `ServerLevel.sendParticles(ParticleOptions, x, y, z, count, dx, dy, dz, speed)`.

## Concrete API facts (verified while building beacon behavior for Nexus/Hive)

- **`canSeeSky` lives on `BlockAndLightGetter`, not `LevelReader` directly.** `default boolean canSeeSky(BlockPos)` returns `getBrightness(LightLayer.SKY, pos) >= 15` — an O(1) read of cached sky-light, no raycast/column scan. Available identically on `ServerLevel` and `ClientLevel` (both reach it via `LevelReader extends BlockAndLightGetter`). A solid block's *own* position reads 0 sky light, so check `pos.above()` for "is this building under open sky". Sky-light is synced to clients, so a client-side check agrees with the server without any extra network state.
- **Reuse the vanilla beacon beam with zero custom renderer code.** Implement `net.minecraft.world.level.block.entity.BeaconBeamOwner` (single method `List<Section> getBeamSections()`) on a block entity, then register `net.minecraft.client.renderer.blockentity.BeaconRenderer::new` for its `BlockEntityType` via `EntityRenderersEvent.RegisterRenderers#registerBlockEntityRenderer` (`BeaconRenderer<T extends BlockEntity & BeaconBeamOwner>` is generic over any such BE). No subclass, no custom render class. See `NexusBlockEntity`/`HiveBlockEntity` + `AsteriskCraftClient.onRegisterRenderers`.
- **`getBeamSections()` runs per render frame** (`BeaconRenderer.extract` reads it each frame), so beam on/off can be computed live from `level.canSeeSky(...)` client-side — no ticking, saved state, or sync flag needed for the visual. Return `List.of()` for no beam, or `List.of(new BeaconBeamOwner.Section(packedRgb))` for a beam of that color.
- **A single `Section` renders a full-height beam.** `BeaconRenderer.submit` clamps the *last* section's height to `MAX_RENDER_Y = 2048` regardless of its stored height (which starts at 1), and `getRenderBoundingBox` extends the AABB to Y=2048 so the beam isn't frustum-culled. So one `Section` = one solid beam to the render ceiling; multiple sections stack as colored runs.

## Concrete API facts (verified while porting 1.12 unit models — Zealot/Zergling/Hydralisk/Probe)

- **Porting a 1.12 `ModelBase`/`ModelRenderer` model is a mechanical box translation** into this version's data-driven mesh API. `tools/model_convert.py` parses an old `Model*.java` and emits a modern `createBodyLayer()`; `tools/make_model_class.py` wraps it into a full `EntityModel<LivingEntityRenderState>`. The mapping:
  - `new ModelRenderer(this, u, v)` → `CubeListBuilder.create().texOffs(u, v)`
  - `addBox(x,y,z,w,h,d, inflate)` → `.addBox(x,y,z,w,h,d[, new CubeDeformation(inflate)])` (all args are `float` now; old int w/h/d are fine widened)
  - `setRotationPoint(x,y,z)` [+ `setRotation(part,rx,ry,rz)` or `part.rotateAngleX=…` in the ctor] → `PartPose.offset(x,y,z)` / `PartPose.offsetAndRotation(x,y,z,rx,ry,rz)`
  - `part.mirror = true` → `CubeListBuilder.create().texOffs(u,v).mirror().addBox(...)`
  - `parent.addChild(child)` → `parent.addOrReplaceChild("child", builder, pose)` (nest in tree order; roots go under `mesh.getRoot()`)
  - `textureWidth/textureHeight` → `LayerDefinition.create(mesh, w, h)`
  - **Only parse the constructor** — the old `render()`/`setRotationAngles()` methods also assign `rotateAngle*`, but those are animation and must not be baked into the static mesh. (Also: some of these old models omit the `this.` prefix; the converter handles both.)
- **`LayerDefinition.create(mesh, texW, texH)` sizes are UV coordinate space, not the PNG's pixel size.** A higher-res PNG works as long as it's an integer multiple with the same aspect ratio (the ported Zealot uses a 768×384 PNG against a declared 256×128 UV space — free HD skin). A wrong ratio / non-multiple gives scrambled UVs.
- **`Model.setupAnim(state)`'s base impl calls `resetPose()`** (restores every part to its `PartPose`), so an override should `super.setupAnim(state)` first, then *add* swing deltas onto the baked pose (`part.xRot += …`). Head-look uses the vanilla `HumanoidModel` convention: `head.yRot = state.yRot * (π/180)`, `head.xRot += state.xRot * (π/180)` where `LivingEntityRenderState.yRot/xRot` are the net head yaw/pitch in degrees; walk uses `state.walkAnimationPos`/`walkAnimationSpeed`.
- **Headless mesh smoke test**: `SomeModel.createBodyLayer().bakeRoot()` builds part geometry in memory (no GL), and constructing the model runs its `getChild(...)` animation lookups — so a JUnit test that does `new SomeModel(createBodyLayer().bakeRoot())` deterministically catches malformed hierarchies and misspelled part paths without `runClient`. See `client/ModelBakeTest`. (Visual pivots/UVs/animation still need `runClient`.)
- **Emissive glow + detail overlay as `RenderLayer`s** (the modern `submit(...)`/`SubmitNodeCollector` pipeline, not the old immediate-mode `doRenderLayer`):
  - Glow: extend `EyesLayer<S,M>` and return `RenderTypes.eyes(glowTexture)` from `renderType()` — full-bright, ignores world light. `EyesLayer.submit` re-submits the parent model for you. See `client/UnitGlowLayer`.
  - Overlay: extend `RenderLayer<S,M>` and in `submit(...)` call the inherited `coloredCutoutModelCopyLayerRender(getParentModel(), overlayTexture, pose, collector, light, state, -1 /*color*/, 1 /*order*/)` (uses `RenderTypes.entityCutout`). See `client/UnitOverlayLayer`.
  - Attach in the renderer ctor via `this.addLayer(new UnitOverlayLayer<>(this, OVERLAY))`. `RenderTypes` (plural) is the factory class in `net.minecraft.client.renderer.rendertype`; it also has `entityTranslucentEmissive(...)` if a translucent glow is wanted.
- **Per-entity render scale** goes in an override of `LivingEntityRenderer#scale(S state, PoseStack poseStack)` — `poseStack.scale(f,f,f)` (replaces the old `preRenderCallback` + `GlStateManager.scale`).

## Concrete API facts (verified while porting 1.12 unit sounds — Zealot/Zergling/Hydralisk/Probe)

- **Registering a custom `SoundEvent`**: `DeferredRegister<SoundEvent> SOUND_EVENTS = DeferredRegister.create(Registries.SOUND_EVENT, MODID)`, then `SOUND_EVENTS.register("entity.zealot.ambient", () -> SoundEvent.createVariableRangeEvent(id("entity.zealot.ambient")))` (`createFixedRangeEvent(id, range)` also exists for a hardcoded audible radius). Register the `DeferredRegister` on the mod bus like any other (`SOUND_EVENTS.register(modEventBus)`).
- **Override the standard `LivingEntity`/`Mob` sound hooks** to point at it: `protected SoundEvent getAmbientSound()`, `protected SoundEvent getHurtSound(DamageSource source)`, `protected SoundEvent getDeathSound()` — same signatures as vanilla (e.g. `Zombie`/`Skeleton` already override these for their own sounds; just override again in the subclass to replace them).
- **Multiple ambient variants don't need multiple `SoundEvent`s.** `assets/<modid>/sounds.json` lets one event name list several `.ogg` files under `"sounds"`; the client sound system already picks one at random per play (this is how vanilla mobs like Villagers get varied ambient barks). So a single registered `SoundEvent` per ambient/hurt/death category is enough even when the source had 4 idle-line files.
- **`sounds.json`'s `"subtitle"` field is a literal translation-key string, not auto-derived from the event's own path** (confirmed in `SoundEventRegistrationSerializer`: `GsonHelper.getAsString(object, "subtitle", null)` reads it verbatim). Set it explicitly per entry and define the matching key in `lang/en_us.json` (e.g. `"subtitles.entity.asteriskcraft.zealot.hurt"`) — omitting the field just means no subtitle shows, no error.
- **An entity subclass with no sound override inherits its Java superclass's sounds**, not its sibling's — e.g. `DroneEntity extends ProbeEntity` picks up the Probe ambient/hurt/death overrides for free (matching the shared-model precedent), while `DragoonEntity extends Skeleton` directly still gets vanilla skeleton sounds since the old mod had no Dragoon/Drone sound assets to port (consistent with those two having no ported geometry either).

## Concrete API facts (verified while building the shared per-army `ArmyBank`)

- **`AttachmentHolder.getData(AttachmentType)` is compute-once-and-cache, not compute-every-call.** Confirmed in `AttachmentHolder.java` (neoforge sources jar): on first access it calls the default-value supplier, `put`s the result straight into the holder's own attachment map, and every later `getData` call for that type returns that *same* stored instance. So a **mutable** default value (e.g. a `NonNullList<ItemStack>`) genuinely aliases across every caller sharing the same holder — this is what lets `ArmyBank.of(level, faction)` back a real "linked chest" for multiple block entities, with no separate cache needed. `serializeAttachments` reads whatever is currently in that map at save time, so in-place mutations persist correctly with zero extra plumbing.
- **`AttachmentType.Builder.serialize(...)` takes a `MapCodec<T>`, not a plain `Codec<T>`** — wrap with `.fieldOf("name")` (same pattern already used by `GameAttachments`, e.g. `Codec.BOOL.fieldOf("value")`).
- **`BlockEntity.preRemoveSideEffects`'s vanilla body is exactly**: `if (this instanceof Container container && this.level != null) Containers.dropContents(this.level, pos, container);` (confirmed in the decompiled source) — nothing else. If a BE's `Container` is backed by data shared with other buildings (like `ArmyLinkedContainer`), overriding this method to skip `super` entirely is the correct way to opt out of that auto-drop-and-clear; don't call `super.preRemoveSideEffects(...)` in that case.

## Concrete API facts (verified while building the Jade shield addon — `compat/jade`)

- **A modid-only Maven build of [Jade](https://jademc.readthedocs.io) for 26.1.2 doesn't exist yet** (checked CurseForge/Modrinth Maven); the only working build is a direct CurseForge file download (`Jade-mc26.1-NeoForge-26.1.8.jar`), dropped into `./libs/` and referenced via `compileOnly files(...)` / `localRuntime files(...)` — no `flatDir` repo needed for a `files()` dependency, and none was added.
- **Jade's own API already uses `net.minecraft.resources.Identifier`, not `ResourceLocation`**, confirmed by decompiling the jar's `snownee.jade.api.*` classes directly (`javap` against the extracted jar) — the official [Jade plugin docs](https://jademc.readthedocs.io/en/latest/plugins22/getting-started/) still show `new ResourceLocation(...)` snippets, which are stale for this MC version (matches this project's own convention: `AsteriskCraft.id(String)` already returns `Identifier.fromNamespaceAndPath(...)`).
- **`@WailaPlugin` needs no explicit value** — `WailaPlugin.value()` defaults to `""`; Jade's own bundled plugins (`VanillaPlugin`, `CorePlugin`) use the bare annotation. Jade discovers plugins via NeoForge's normal annotation/mod-file scan, not a `META-INF/services` entry or a `neoforge.mods.toml` entrypoint — nothing beyond an optional `jade` mods.toml dependency is needed for discovery.
- **`IWailaClientRegistration.registerEntityComponent(IComponentProvider<EntityAccessor>, Class<? extends Entity>)`** takes a plain `Class`, not an `EntityType`. Registering broadly on `LivingEntity.class` and guarding inside the provider (as Jade's own bundled `StatusEffectsProvider` does) is the established pattern for a component that only applies to some entities, rather than registering once per concrete subclass.
- **Every registered component/data provider needs a lang entry for Jade's config screen, or the game throws on startup.** Jade auto-adds a per-provider toggle to its plugin config screen (from `IToggleableProvider`, which every `IComponentProvider` extends) and asserts a translation exists for it at `config.jade.plugin_<modid>.<uid path>` (confirmed via a live `runClient` crash log: `java.lang.AssertionError: Missing config translation: config.jade.plugin_asteriskcraft.protoss_shield` thrown from `JadeClient.onGui`, which aborted the initial resource-pack load). Add the key to `assets/<modid>/lang/en_us.json` — e.g. `"config.jade.plugin_asteriskcraft.protoss_shield": "Protoss Shield"` — matching `getUid()`'s path exactly (see `JadeAddons`' own `en_us.json` for the naming convention: `config.jade.plugin_<addonmodid>.<uid path>`).
