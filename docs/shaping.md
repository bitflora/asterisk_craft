# AsteriskCraft — StarCraft RTS gameplay in Minecraft (NeoForge)

## Context

Mod in `C:\Users\timja\code\asterisk-craft` (formerly `star-mine`). Goal: bring the StarCraft loop — gather → build → produce units → destroy the enemy base — into Minecraft. The player (Protoss) starts with a Nexus; an AI Zerg starts with 3 Hives a few hundred blocks away. Both gather resources and produce units. Destroy all Hives to win; lose the Nexus and you lose. Later versions add race selection and PvP, so nothing may hardcode "player = Protoss".

**Target:** Minecraft 26.1 + NeoForge 26.1 (current stable modding line, successor to 1.21.1). Mod id: `asteriskcraft`. Package root: `net.bitflora.asteriskcraft`.

### R5 detail — select + orders

Expanded from the top-level R5 to pin down the exact control scheme (see shape A8, plan in [R5-command-plan.md](R5-command-plan.md)). "Friendly" means a unit whose `Faction` attachment equals the commanding player's controlled faction (PROTOSS for the human in MVP) — resolved generically, never by player/entity class.

**Hitbox sizes are pathfinding-load-bearing.** A unit's `.sized(width, height)` is not just a silhouette: the pathfinder derives a node's footprint from it as `floor(w + 1)` x `floor(h + 1)`, so 2.0 tall needs three blocks of clearance where 1.99 needs two, and 1.0+ wide takes two nodes and can no longer fit a one-block gap. Widening a model for looks can therefore break navigation invisibly — `entity/UnitFootprintTest` guards the bounds, and docs/neoforge-api-notes.md has the derivation. The Dragoon's 1.1 width is the one deliberate exception; the crowding it caused is handled by R5.13 rather than by shrinking it.

## Selected shape (A, with decided alternatives)

| Part | Mechanism |
|------|-----------|
| **A1** | **Faction system** — NeoForge data attachments tag entities + block entities with a `Faction`; a single `FactionAttachments.isHostile(a,b)` used by all targeting. Landed in V5a as a *pair* of tables rather than one registry: `Faction` is the side (who shoots whom), `faction/Race` is what that army is (what it builds and which combat traits it has), with `game/MatchSetup` saying which side plays which and `race/Races` holding everything registry-bound per race. V6b finished the split: a side is a colour (`BLUE`/`RED`) and names no race at all, an army's race rides on a second synced attachment beside its faction, and the two sides may therefore be playing the same race — a mirror match |
| **A2** | **Warp-in kits** (chosen: A2-B) — each building is a craftable kit item; right-click ground → validates footprint → structure template materializes over ~10s with particles/sound. One generic `WarpInHandler` + per-building structure template `.nbt`. **Shipped as:** `BuildingKitItem` + `BuildingTemplates`, stamping `data/asteriskcraft/structure/{nexus,gateway,hive}.nbt` — every building is authored in-game with a structure block and re-exported, not written out in Java. Holding a kit **outlines the volume it needs free** before anything is committed (`client/KitPlacementPreview`), green while the site is clear and red once anything is in the way — the same test the server refuses placement on. The layout is stamped instantly, then immediately frozen back into a **glass scaffold** (`building/WarpScaffold`) that the core block entity hands out pane by pane, in scrambled order, as its own countdown runs — **2 minutes** for a Nexus, **1 minute** for a Gateway, 10s for a Photon Cannon — so a building speckles itself into place instead of blinking in finished. A kit-placed core arrives carrying the block-entity NBT its structure block captured in the *design* world, spent countdown and all, so placement calls `BuildingDefense.beginWarpIn` rather than trusting the stamped state — the inverse of the `skipWarpIn` a pre-placed building gets. Throughout that countdown the building is inert (no production, no fire) and stands at **half its HP and shields**; finishing the warp scales what survived back up (`building/WarpInVulnerability`), so a building caught mid-warp comes out having sustained twice the damage — and one warped in under fire can be killed before it ever opens. The scaffold is the second way to interfere: **smashing a pane costs the warp 10 seconds and books 20 points of siege damage**, the damage landing the instant the building stands up rather than during the warp, where the halved pools would double it. The delay paces itself, since the remaining panes are spread over the remaining time rather than a fixed schedule. A smashed pane is left as the hole it became and keeps its slot in the fill order, so its real block turns up when it always would have and the same square can't be charged for twice — which bounds what an attacker can wring out of a warp by its pane count: 40 panes for a Gateway (of which ~25 smashed is enough to collapse it as it comes online), 95 for a Nexus. The starting Nexus and the Hives raise no scaffold at all, since they are simply standing when the world begins (R1) |
| **A3** | **Nexus** — controller block entity + GUI with Probe production queue; defeat trigger when core block is destroyed; gates crafting of other kits (recipes unlock via advancement granted at game start). The toughest thing on the map, as the building you lose the game with should be: **325 HP behind 325 shields** (`building/BuildingDefense`) |
| **A4** | **Probe** — small custom entity; goal chain: find nearest block in `#asteriskcraft:harvestable` tag **of the resource it is assigned to** → mine-beam N seconds → block enters depleted/cooldown state (never removed) → carry drops straight into the home Nexus's inventory. The assignment is a hard filter, not a preference: it is set by a MINE order (or, for a worker never given one, by its own first pick) and a worker whose nodes are all depleted walks to the nearest one and **waits for the regen** (`AwaitRegenGoal`) rather than taking up a different resource. The one release valve is a resource that has left the base entirely — none standing and none regenerating — where the assignment would be a wait for something that is never coming back, so it is dropped and the search re-run unfiltered |
| **A5** | **Vanilla-item economy** (chosen: user variant of A5-B) — resources are real items in building inventories; kits are crafted normally; production buildings consume items from a shared per-army inventory (`ArmyBank`), which workers deliver into directly. Every building in an army — Nexus + Gateway for Protoss, all three Hives for Zerg — acts as a "linked chest" (`ArmyLinkedContainer`) onto one pooled `Container` per faction rather than each holding its own independent stock |
| **A6** | **Gateway** — production block entity; spawns **Zealots** (repurposed Zombie, melee) and **Dragoons** (repurposed Skeleton, ranged) with goal selectors replaced (faction targeting, no sunburn, no player aggression) + colored leather armor for team identity; rally point support. **250 HP behind 250 shields**, and a `building/SiegeTarget` but deliberately not a `FactionCore` — an enemy army can raze it, which costs the player their unit production but not the match |
| **A7** | **Photon Cannon** — a stationary `PhotonCannonEntity` (a `Mob`, not a block entity) rather than blocks: being a `LivingEntity` it reuses the whole unit-combat stack instead of duplicating it — HP as an attribute, Protoss shields for free (`implements Protoss`), and **automatic retaliation** (units target/hit it back via the normal `RetaliateGoal`/`FactionTargetGoal`, so no building-aggro special case). It never moves (no move goals, zero speed, unpushable), warps in over 200t — inert but **not** invulnerable: a warping structure stands at half its HP and shields (`building/WarpInVulnerability`), and finishing the warp scales both pools back up, so whatever fraction an attacker shot off the half pool is missing from the full one — i.e. damage landed mid-warp is sustained twice over, and a cannon warping in under fire can be killed before it ever fires. Once warped in, a `CannonFireGoal` auto-fires an instant bolt at the nearest enemy-faction unit — or any wild vanilla hostile (anything marked `Enemy`, slimes and ghasts included, not just `Monster` subclasses) — in range, reusing the pure `PhotonCannonTargeting` rule. Warped in by the crafted `photon_cannon_kit` (a `FactionSpawnEggItem`). No power system in MVP |
| **A8** | **Command Crystal + StarCraft click semantics** (chosen; revised from the earlier "command wand" sketch — see R5 detail + [R5-command-plan.md](R5-command-plan.md)) — a held marker item enables command mode; **left-click = select** (plain / Shift-toggle / Ctrl-all-of-type-in-radius / Ctrl+Shift-toggle-all-of-type), **right-click = order** (enemy = attack, block = move, air = move toward look). All input captured client-side (Ctrl is not server-known) and sent as one `CommandInputPacket`; selection is a per-player attachment; orders are a `CommandOrder` attachment read by commanded goals on each unit. Probes are commandable too: they honor MOVE and a **MINE** order (right-click a harvestable block) that reuses their existing harvest logic |
| **A9** | **AI director with literal workers** (chosen: A9-B) — one race-agnostic `AiDirector`: maintains worker count, Drones mine `#asteriskcraft:harvestable` blocks into the shared Zerg `ArmyBank` (all three Hives are linked chests onto the same pool, exposed as an item capability so the existing Probe/Drone delivery reuses verbatim), a global `AiDirector` (`ServerTickEvent.Post`, state in level attachments) spends the pooled resources on escalating mixed waves and issues attack-move at the player's bases; killing Drones starves it, killing all three Hives removes production. **Building destruction:** every building is a `building/SiegeTarget` holding its HP (and, for a Protoss one, shields) in a shared `building/BuildingDefense`; all combat units carry a faction-generic `SiegeBlockGoal` that batters down whichever enemy building it reaches (and digs through blocks that stall their path). `FactionCore` is the narrower marker for the buildings whose fall decides the match — the bases, but not a Gateway — and the removal fires the win/lose via the core BE's `preRemoveSideEffects` (which deliberately skips the vanilla Container-drop, since that would dump the whole army's shared bank just because one building died). So both outcomes are reached through real combat. **Spoils:** a razed core instead spills `1 / (that faction's still-standing cores + 2)` of the shared `ArmyBank` onto the ground where it stood (`building/CoreSpoils`) — a quarter, then a third, then a half across the three Hives, i.e. an equal quarter of the original pool each time, with the last quarter left to the survivors. The count comes from `building/CoreCensus`, a level attachment every core enrols itself in from its own ticker, so an expansion Nexus really does cushion the loss of the first one. |
| **A10** | **Cloak is two halves that never meet** — a server-side targeting rule and a client-side render decision, sharing only one synced flag. Vanilla's invisibility flag is *not* used, because it does not hide anything from mob AI: `TargetingConditions` merely scales acquisition range by `getVisibilityPercent` (0.07 for an unarmoured mob) and then floors the result at **2 blocks**, so an invisible unit is still attacked by whatever is standing on it. The gate therefore lives in `FactionAttachments.isHostile(Entity, Entity)` — the choke point every targeting path already goes through, which is what makes it total: acquisition, **retaliation** and splash chains all resolve hostility there, so an undetected cloaked attacker cannot even be swung back at. Visibility is the mirror image: `client/CloakRenderStateModifier` rewrites `isInvisible` / `isInvisibleToPlayer` per viewer per frame, so the same unit is a 15%-alpha ghost to the player who commands it (clickable and orderable — selection is a hitbox raycast and the server never stops tracking the entity), nothing at all to an enemy without detection, and a ghost body under a **red outline** to an enemy with it. That red is written straight into `EntityRenderState.outlineColor`, which both colours the outline and switches the outline pass on — no scoreboard team (16 `ChatFormatting` colours only), no mob effect, and no collision with the white selection glow, which is still driven server-side by `setGlowingTag`. Detection is faction-generic and cheap: a `Detector` (each race's dedicated detector — Photon Cannon for Protoss, Spore Colony for Zerg, both on a 16-block / 20-tick / 60-tick envelope) sweeps once a second for cloaked enemies and stamps a per-faction countdown, exposed as a **bitmask over factions** so a second detector's reveal can never be cancelled by the first one timing out. Reveal outlasts the sweep interval so consecutive windows overlap — a detected unit never strobes, and one that has just slipped out of range stays lit for the 2-second remainder |
| **A11** | **The Bunker is vanilla passengers, and almost all of it is free** — a `BunkerEntity` (a `Mob`, like the Photon Cannon, for the same "it reuses the whole combat stack" reason) that units `startRiding`. Verified against the decompiled 26.1.2 source: a riding `Mob` runs its **full** goal and target selectors (`Mob.serverAiStep` is `final` and has no passenger check; `LivingEntity.isImmobile` is `isDeadOrDying()` and nothing else), so *shooting from inside* needed no combat code at all; passengers are saved nested under the vehicle and re-seated on load, so a garrison survives a reload with no save code; and `Entity.setRemoved` dismounts everyone, so a destroyed Bunker spills its garrison without being asked. Multi-seat is declarative — four `passengerAttachments` on the `EntityType` plus a `canAddPassenger` cap, the Happy Ghast's shape. What is *not* free is three things: the first `Mob` passenger becomes the vehicle's **driver** by default (`Mob.getControllingPassenger`), which re-routes the rider's navigation onto the Bunker and would have a garrisoned Marine trying to steer the building at its target; riders stay individually **targetable and hittable**, which is `faction/Garrison` at the `isHostile` choke point plus `combat/TargetRetentionHandler` plus a `combat/GarrisonDamageHandler` floor; and a rider's **movement goals still hold their flags**, so `StuckWanderGoal` and `SiegeBlockGoal` had to learn that a passenger is neither stuck nor able to walk anywhere. Who may board is a capability question, `entity/Organic`, so the rule names no race |

## Architecture sketch

Package root `net.bitflora.asteriskcraft`:

- `faction/` — Faction (side), Race (what an army is), FactionAttachments, WildKind, Cloaked/Cloaking
- `race/` — RaceProfile + Races (the one per-race table), UnitRoster
- `building/` — BuildingKitItem, BuildingTemplates, BaseBlock(Entity) (every race's base), GatewayBlock(Entity), CoreCensus, `PhotonCannonTargeting` (pure targeting rule), structure templates in `data/asteriskcraft/structure/`
- `entity/` — WorkerEntity (the shared harvest economy) + per-race ProbeEntity/DroneEntity, PhotonCannonEntity; `ai/` goals: FactionTargetGoal, RetaliateGoal, CommandedMoveGoal, SiegeBlockGoal, CannonFireGoal
- `command/` — CursorItem (held marker), CommandInputPacket + client input handler, CommandInputResolver (server), PlayerSelection attachment, CommandOrder attachment + `ai/CommandedMoveGoal`/`ai/CommandedAttackGoal`
- `director/` — AiDirector (server tick handler, race-agnostic) over the pure `script/` interpreter
- `game/` — GameAttachments (bootstrapped/MatchSetup/game-over/interpreter cursor) + world bootstrap. Implemented as first-player-join placement rather than server start (see Status note below) — no slash commands anywhere in the MVP.

Key technical notes:
- Units marching across the map need **chunk tickets** attached while they hold an active order — otherwise they freeze in unloaded chunks. **V3 sidesteps this** by placing the AI's bases ~110 blocks away (inside typical simulation distance) so wave units and Drones path through already-loaded chunks; chunk tickets (for R5.10 and a more distant base) remain an open spike — see [R5-command-plan.md](R5-command-plan.md).
- All game logic server-side; wand selection UI feedback via glowing outline effect (vanilla `Glowing` works for MVP).
- "Non-destructive mining": harvested blocks switch to a depleted blockstate (visual dim) with a regen cooldown, never removed from the world.

## Costs (wood/cobble/iron economy; amounts get a balance pass in V4)

The whole economy runs on vanilla resources Probes/Drones can harvest non-destructively: **wood** (logs, `#minecraft:logs`), **cobblestone** (from stone), and every ore in the ground — **iron, coal, copper, gold, redstone, lapis, diamond, emerald** (via the matching `#minecraft:*_ores` tags), each yielding its usual smelted/refined form (e.g. iron ore → iron ingot, coal ore → coal) directly, with no separate smelting step. Zerg costs no longer mirror Protoss exactly: Protoss stays picky about which resource pays for what, while every Zerg unit accepts **any item** in the shared Hive bank toward its flat cost (whatever mix of resources the Drones happen to have delivered).

| Protoss | Cost | Zerg equivalent | Cost |
|---------|------|------------------|------|
| Probe | 50 wood **or** 50 cobblestone | Drone | 50 of any resource |
| Zealot (Zombie, melee) | 50 wood **and** 50 cobblestone | Zergling | 25 of any resource |
| Dragoon (Skeleton, ranged) | 100 wood **and** 50 cobblestone | Hydralisk | 100 of any resource |
| Scout (air) | 150 cobblestone **and** 20 iron | Mutalisk (air) | 100 of any resource |
| Pylon kit | 100 wood **or** 100 cobblestone | — (the swarm's prerequisite is creep, not a buildable structure — see the creep prerequisite below the table) | — |
| Gateway kit | 150 wood **or** 150 cobblestone | Spawning Pool (baked into Hive for MVP) | — |
| Dark Templar (cloaked melee) | 75 cobblestone **and** 50 wood **and** 2 iron | Lurker (cloaked while burrowed) | 100 of any resource |
| Photon Cannon kit | 150 wood **or** 150 cobblestone | Sunken Colony | 150 of any resource (`BaseBlockEntity.BUILDING_COST`); one is also pre-placed per Hive |
| — | No Protoss anti-air-only structure (the Cannon shoots both) | Spore Colony (anti-air only) | 150 of any resource (`BaseBlockEntity.BUILDING_COST`); one is also pre-placed per Hive |
| — | No Protoss mobile detector (the Cannon is rooted) | Overlord (flying detector, no attack) | 100 of any resource; one is also handed to each Hive at world start |
| Nexus kit (expansion) | 400 cobblestone only (no wood alternative) | Hive kit (expansion) | 400 of any resource (`BaseBlockEntity.BASE_KIT_COST`) |

The Terran are a third column: an SCV costs 50 wood **or** 50 cobblestone (the Probe's price exactly — what a race differs in is what it builds with its economy, not what staffing that economy costs), and a **Marine costs the same 50**, which makes it the cheapest combat unit in the mod and is the base of the race's shape — it pushes with counts. A **Firebat costs 50 cobblestone _and_ 25 wood**, the race's one bundled cost, and it is deliberately the exception that says specialist: twice a Marine's price for a unit that is useless on its own and worth several Marines against anything massed. A **Bunker costs 100 cobblestone** — the cheapest structure in the mod, and priced that way because an empty one does nothing: what a player really pays for it is the four Marines they have to put inside. All three combat units are trained at the **Barracks** rather than at the base, which is the Gateway's arrangement and not the Hive's: the Terran build a building before they build a soldier. A **Command Center kit costs 400 wood *or* 400 cobblestone** — the same 400 an expansion Nexus or Hive costs, but payable in either resource rather than in cobblestone alone, which is the same Wood/Stone choice the race's own SCV button offers — and is bought off the Command Center's own card exactly as the other two are. Terran costs follow the Protoss convention of naming a real resource rather than the Zerg "any item" one, which `UnitStatsTest` pins.

Building-kit costs are still authored apart from the balance table — they are constants on `building/BaseBlockEntity` (`BUILDING_COST`, `BASE_KIT_COST`, `PYLON_COST`, and one per building sold on a card) rather than rows in `unit_stats.csv`, because a kit is not a unit — but they are `UnitCost`s, paid and rendered through exactly the machinery a unit's cost is. They have to be: a building's price is the same shape a unit's is. **Barracks: 75 wood *and* 75 cobblestone. Stargate: 150 cobblestone *and* 150 wood *and* 10 iron** — the priciest thing on any card, and the second cost in the mod to send a player underground. **Spawning Pool: 200 of any resource. Spire: 250 of any resource *and* 10 iron**, the one Zerg cost that names a specific resource alongside the flat pile, which is why `UnitCost.bankCosts` pays the specific lines first (`Resource.ANY` matches the very iron the iron line still needs). **Command Center kit: 400 wood *or* 400 cobblestone** — the same 400 an expansion Nexus or Hive costs, but payable in either, which is the one place a second base is *not* the same purchase whoever makes it.

A card gives one button per cost alternative, exactly as it does for a worker, so a cost that is a bundle gets a single button and a cost that is a choice gets a pair. That is the whole rule behind why the Barracks and the Stargate have one button each while the Gateway and the Command Center kit have two.

Code: `stats/UnitStats` is the single source of truth for these numbers (and every unit's combat stats); this table is the design intent they're checked against, not the other way around.

The numbers themselves are no longer Java. They are one row per unit in `src/main/resources/asteriskcraft/balance/unit_stats.csv`, read at `UnitStats` class-init — because a balance pass is a question about a *column* ("what does every ranged unit cost per point of damage?") and a builder chain per unit could only be read a unit at a time. Sort it in a spreadsheet, save, relaunch; nothing recompiles, and an installed build takes an override at `<gamedir>/config/asteriskcraft/unit_stats.csv`. [docs/balance-table.md](balance-table.md) is the per-column reference for that file — units, groups, cost syntax. `UnitStats.java` keeps the named constant every call site reaches for and the rationale for why a number is what it is — the design prose above and the grid below it are the two halves, and `UnitStatsTest` still checks one against the other.

## Slices (each ends demo-able)

**V1 — Mod skeleton + Nexus + Probe economy. `[DONE]`** MDK setup for NeoForge 26.1; faction core (A1); world bootstrap places the Nexus, seeded with starting resources, on first player join (no slash commands — moved off server-start after testing showed the heightmap isn't settled that early); Nexus block entity + GUI queue; Probe entity that non-destructively harvests wood/stone/iron ore (each worker assigned to one resource and mining only that, waiting out the regen when its nodes are spent) and delivers a flat 3 per trip straight into the Nexus; Probe costs 50 wood or 50 cobble from the Nexus's own inventory. Unit tests cover faction rules, the building site-prep geometry, and economy constants. *Demo: create a new world, find the Nexus standing near you, queue a Probe, watch it mine and deposit into the Nexus.*

**V2a — Gateway + Zealots/Dragoons. `[DONE]`** Warp-in kit framework (A2); Gateway production (A6) of Zealots (zombies, 50 wood + 50 cobble) and Dragoons (skeletons, 100 wood + 50 cobble); rally points. *Demo: craft Gateway kit, warp it in, produce a mixed squad.*

**V2b — Command Crystal: select + orders (R5).** The A8 command scheme — held Command Crystal enables command mode; left-click select (plain / Shift-toggle / Ctrl-type-in-radius / Ctrl+Shift-toggle-type), right-click order (enemy=attack, block=move, air=move-toward-look). Client input capture → `CommandInputPacket` → per-player selection attachment + `CommandOrder` attachment read by commanded goals on units; selection glow; chunk-load ordered units. Detailed plan: [R5-command-plan.md](R5-command-plan.md). *Demo: hold the Crystal, click-select a mixed squad, right-click a Hive to send them attacking; Ctrl-click one Zealot to grab the whole group.*

**V3 — Zerg AI + win/lose. `[DONE]`** 3 Hives placed at first join ~110 blocks east of the Nexus (inside simulation distance — no chunk tickets needed, see the technical note below), each seeded with resources + a surface resource garden + starter Drones. Per-Hive Drone mining loop (`HiveBlockEntity`); `ZergDirector` (`ServerTickEvent.Post`) runs an escalating **mixed Zergling + Hydralisk** wave schedule, spending pooled Hive resources and attack-moving the wave at the Nexus with an "under attack!" ping. Win/lose is reached through combat: all combat units (Zealot/Dragoon/Zergling/Hydralisk) carry a `SiegeBlockGoal` that batters down enemy `FactionCore` blocks (Nexus + Hives, which have siege HP) and digs through obstructing blocks; a core's removal fires the outcome via `preRemoveSideEffects` — victory on the last Hive razed, defeat on the Nexus razed. Unit tests cover the Zerg cost mirror, wave-escalation curves, and the win/lose decision. *Demo: full playable game loop, both outcomes reachable.*

**V4 — Photon Cannon + real costs.** Cannon kit + auto-targeting (A7); wire all production/kit costs to actual item consumption (R7); first balance pass on wave scaling. *Demo: cannons repel a wave; production halts when the chest is empty.*

**V4b — Sunken Colony (R9). `[DONE]`** The Zerg answer to the Photon Cannon: a rooted `SunkenColonyEntity` (150 HP, no movement goals, `FactionTargetGoal` + `RetaliateGoal`, deliberately not commandable) planted beside every Hive by `GameBootstrap`. Its `SunkenSpikeGoal` whips the tentacle every 32 ticks and drives a single `SunkenSpikeEntity` — an `EvokerFangs` subclass — out of the ground under a target up to 11 blocks away, for 20 damage. Vanilla fangs hardcode 6 damage and only spare vanilla-team allies, so both the damage and the faction filter are applied in `combat/FangStrikeDamageHandler` (see docs/neoforge-api-notes.md); the trade for hitting that hard is that the strike lands ~8 ticks later at a fixed spot, so a moving target can walk out of it. Ally/enemy spawn eggs included for testing. *Demo: walk into a Hive and get impaled; the spikes leave the Hive's own Drones untouched.*

**V4c — Mutalisk, the first air unit (R10). `[DONE]`** A `MutaliskEntity` (60 HP, 4.5 damage, 9-block range, 0 armour, 100 of any resource) that cruises 6 blocks above the terrain. Flight is two pieces neither of which any combat goal knows about: a vanilla `FlyingMoveControl` plus an `entity/ai/HoverFlyingNavigation` that lifts every destination to `ground + 6` **before** pathing — the altitude has to be baked into the path itself, because `PathNavigation.followThePath` only advances a node when the mob is within 1 block of it on Y, so a flyer over a ground-hugging path would thrash forever (see docs/neoforge-api-notes.md). Because every movement goal in the mod reaches the world through `getNavigation().moveTo(...)`, the existing `RangedAttackGoal`/`CommandedMoveGoal`/`GuardGoal`/`SiegeBlockGoal` all fly at altitude unchanged; `SiegeBlockGoal` only gained a per-unit reach so an air unit can batter a core from where it hovers, and an `entity/ai/HoverGoal` holds altitude in the gaps between orders. Melee ground units (Zealot, Zergling) genuinely cannot answer it — only ranged units and the Photon Cannon can, which is the intended counter-play. Its shot is a bouncing glave: `HitscanAttacks.fireChained` hits the primary target then chains to up to two more enemies within 5 blocks of the enemy just hit (not of the Mutalisk itself — `combat/BounceChain` resolves the chain from hop to hop, so it can walk past the Mutalisk's own 9-block range), each hop dealing half the last one's damage (4.5 → 2.25 → 1.125). Single-target damage is unchanged, so the V4d air duel against the Scout is untouched — the bounce is pure upside against a massed group, which is the intended anti-clump role. The enemy build script fields one from the fifth wave on. *Demo: a Mutalisk swings over the tree line, your Zealots mill uselessly beneath it, a Dragoon brings it down.*

**V4d — Scout, the Protoss air unit (R10). `[DONE]`** The answer to the Mutalisk: a `ScoutEntity` (75 HP behind 50 shields, 11 damage, 9-block range, 30-tick cadence, 0.5 armour) trained at the Gateway for 150 cobblestone **and** 20 iron — the first cost in the mod paid in refined metal, which works with no new economy plumbing because Probes already deliver iron ore as ingots into the shared `ArmyBank`. It reuses V4c's flight stack **verbatim** — `FlyingMoveControl` + `HoverFlyingNavigation` at the same `HOVER_HEIGHT` of 6, `HoverGoal` holding altitude between orders, `SiegeBlockGoal` given its attack radius as reach — so not one line of the goal library changed to make a second flyer. It deliberately shares the Mutalisk's whole envelope (altitude, reach, cadence) so the two meet on even terms and the duel is decided by staying power and punch, both of which the Scout has; a Photon Cannon (50 HP behind 50 shields, 10 damage, 14-block range, 20-tick cadence) still out-ranges it at 14, keeping static defence the counter to air on both sides. Shields come from the `Shielded` marker alone. Ambient barks are the four ported "what" lines, Dragoon-style (no hurt/death clips exist). Ally/enemy spawn eggs included. *Demo: a Mutalisk comes over the tree line, you queue a Scout, and it goes up and takes the sky back.*

**V4e — Zerg attacks stop being predictable, and stuck units unstick. `[DONE]`** Three changes to how the director attacks. **Where a wave comes from:** a batch's staging building is rolled once when the batch starts and carried on the persisted `InterpreterState.Batch`, instead of being re-rolled per unit — so a wave masses at one Hive and leaves as a group from a direction the player can't predict, rather than trickling out of all three at once. The same applies to a `Defence` batch: a batch is one group produced in one place, and whether it is a `Wave` only decides whether it marches afterwards. **What it attacks:** the target is picked at launch out of `CoreCensus.standing(level, PROTOSS)`, so every standing Nexus is a candidate and an expansion warped in from a kit is no longer invisible to the AI — `GameAttachments.NEXUS_POS`, a single position written once at bootstrap, survives only as the fallback for a world whose census is empty. Both choices go through the pure interpreter's `DirectorWorld` seam (`pickStagingSite`/`pickAttackTarget`), so they are unit-tested against the fake world rather than only observable in-game. **Units that stop getting anywhere:** `entity/ai/StuckWanderGoal` (with its testable `StuckClock`) watches displacement through the world, and after 40s of a Zerg combat unit not moving it takes over and wanders to random nearby points for up to 10s before handing control back. It has to sit at priority -1 to do that at all — `GoalSelector` skips `canUse()` on any goal whose flags a higher-priority goal is holding, so at any other priority its clock would freeze exactly while the unit was pinned (see docs/neoforge-api-notes.md). It leaves the unit's order and target alone: this is a shove, not a desertion. Standing still while fighting doesn't count — `swinging` covers a melee unit and a unit battering a building, and a target inside attack range with line of sight covers a ranged unit, which vanilla's `RangedAttackGoal` holds perfectly motionless. *Demo: two waves in a row come at you from different Hives and aim at different Nexuses; a Zergling wedged behind a wall shakes itself loose instead of grinding there forever.*

**V4f — Cloak + detectors (R11). `[DONE]`** The mechanism; the Dark Templar in V4g is what uses it. Everything is shape A10 above: a server-side targeting gate in `FactionAttachments.isHostile` and a per-viewer render decision in `client/CloakRenderStateModifier`, sharing one synced per-faction bitmask and nothing else. Both **detectors** are rooted defences — Photon Cannon and (as this slice shipped) Sunken Colony sweep 16 blocks once a second and reveal for three, so each side owned the answer before anything asked the question. The Zerg half moved in V4h: detection is the Spore Colony's job now and the Sunken carries none, so each race has one identifiable building an attacker can snipe to go blind. The spike ran with the Zealot and Hydralisk carrying cloak, which proved the mechanism and then made the case against leaving it on a line unit: an undetected attacker cannot be retaliated against at all, which is far too much at a Zealot's price. Cloak came back off both, and stays opt-in and rare. Three findings worth not rediscovering the hard way: vanilla invisibility is useless as a cloak, since `TargetingConditions` floors an invisible unit's acquisition range at 2 blocks rather than hiding it; `UnitGlowLayer` needed an invisibility guard of its own, because `EyesLayer` carries none and would otherwise draw a full-bright silhouette of the body that isn't being drawn; and the shadow and name tag are extracted *before* any render-state modifier runs, so hiding a unit means clearing them by hand. *Demo: see V4g.*

**V4g — Dark Templar, the unit cloak was built for. `[DONE]`** A Gateway melee assassin (40 HP behind 20 shields, 1 armour, 20 damage, 75 cobblestone + 50 wood + 2 iron, 50s) and the only unit in the mod that implements `faction.Cloaked` — which is the entire implementation of its cloak, since the gate lives in `isHostile` and the rendering in `CloakRenderStateModifier`. It carries a `warp_blade` damage type of its own, per the one-type-per-attacker rule. **The trade is deliberately lopsided at both ends:** while undetected it cannot be acquired, splashed or even swung back at, so it walks through an unguarded flank and one-shots Drones; but it is the most fragile thing the Gateway makes, and a Hive is covered by a Spore Colony detecting at 16 blocks next to a Sunken Colony hitting for 20 — so it is revealed well before it arrives and half of it goes on the first spike. Every Hive already has one, which is why this needed no new Zerg work. Model is a Zealot's frame with three changes — a hood, a two-panel cloak that trails with movement, and one 13-long warp blade on the right arm with nothing in the left hand, an asymmetry that survives the 15%-alpha ghost the cloak renders it as. Because it is *permanently* cloaked it is never seen at full opacity by anyone, which is why `UnitGlowLayer`'s guard was relaxed to fire on "body not drawn" rather than "invisible": the glowing blade is most of what a player actually sees. Skin, GUI portrait and spawn eggs are generated by `tools/gen_dark_templar_texture.py` and `tools/gen_dark_templar_items.py` onto the packed UV layout, ready to be repainted in Blockbench. Ambient and death barks ported from the SC1 clips; no hurt or attack clip exists, so those keep vanilla's. *Demo: build one, walk it into a Zergling pack that never fights back, then watch it light up red as it enters a Spore Colony's reach and die on the Sunken Colony beside it.*

**V4h — Spore Colony, the anti-air the Zerg were missing. `[DONE]`** The Sunken Colony's sibling, planted beside every Hive by the same `GameBootstrap` loop (placing the second one exposed a latent bug in `building/SpawnSpots`: its ring search is deterministic and only ever tested *blocks*, so the Spore was handed the exact block the Sunken already stood on — a spot occupied by an `entity/Rooted` unit now counts as taken, the new marker existing because "can this thing step aside?" is the real question and mobile units shoving apart within a tick is why nothing had noticed): a rooted `SporeColonyEntity` (200 HP, 7.5 damage, 11-block range, one shot a second) that also carries `Detector` on the shared envelope, and is the Zerg's *only* detector: the Sunken Colony's was removed in the same pass, so detection is one identifiable building per race rather than a property every rooted thing happens to have — which matches StarCraft and gives an attacker something specific to snipe. It closes the asymmetry the Photon Cannon had opened — a Cannon shoots air and ground alike, so a Mutalisk flock over a Nexus was answered while a Scout flock over three Hives was not. **The interesting part is what "air" means.** It is deliberately *not* the `entity/Flyer` marker but a positional rule (`entity/Altitude.isAirborne`): four or more blocks of clear space above solid footing, probed four blocks down with the same `isFaceSturdy(UP)` test `SunkenSpikeGoal` uses to find ground. So a Mutalisk that drops to tree height stops being a target mid-engagement, and a Zealot knocked off a cliff briefly becomes one. That rule reaches targeting through one new seam and no more: a second `FactionTargetGoal` constructor taking a predicate that may only ever *narrow* what `FactionAttachments.isHostile` already allowed, so the cloak gate stays in its single choke point. `SporeFireGoal` re-checks the same rule every tick, which is what actually stops the shots when a target descends, since the target selector only re-runs on its own cadence. It carries **no `RetaliateGoal`** — unlike the Sunken — because retaliation would hand it a ground attacker it must then refuse to shoot, and being helpless against ground is the trade the unit makes. `Flyer.isAir` is untouched and still drives the Scout's anti-air bonus: a unit-type question, not a positional one. Its `seeker_spores` damage type follows the one-type-per-attacker rule, and its model is built to the reference art — a squat purple body under a black carapace on four stone claws, with a fat orange chimney flaring open above it and one white eye on the throat — every rounded shape in that art rendered as a stepped stack of boxes, which is how a cube model reads as round at this resolution. The Sunken Colony is now the exact complement, closing the half of the split V4h left open: it takes the negation of the same predicate, because a spike erupting from the ground was never able to reach the air anyway — it only looked like it could, planting nothing while the colony sat locked on a flyer it would never hit. `RetaliateGoal` grew the same optional filter `FactionTargetGoal` has and the Sunken passes it there too, which is what the Spore solved by dropping retaliation entirely: a colony pinned by a strafing Mutalisk must not stop answering the Zealots walking in underneath it. `SunkenSpikeGoal` re-checks altitude every tick for the same reason `SporeFireGoal` does. *Demo: fly a Scout over a Hive and watch it get shot out of the sky; walk a Zealot up to the same colony and it never so much as turns — then check the Sunken beside it does the exact opposite, ignoring the Scout even while being shot by it.*

**V4i — Lurker, and cloak that comes and goes (R11b). `[DONE]`** The Zerg cloaked unit, and the hole the V4g cost table left open. A spider-framed Hydralisk (63 HP, 1 armour, 100 of any resource, 40s) that has to **burrow** to fight: three seconds to dig in, three to climb out, and it is cloaked and armed only at the bottom of that and mobile only at the top. Caught halfway it is visible, immobile and unarmed at once — which is the entire price of the mechanic, and it lands without anything checking a direction because the state is *one number*. `entity/zerg/BurrowClock` holds a depth from 0 to 60 and the intent it is walking toward; surfaced, digging and burrowed are just that number's two ends and its middle. The entity syncs the depth (following `PhotonCannonEntity`'s warp countdown, which is the established shape for a timed transition every goal and the renderer both read) and persists it, so a Lurker that was buried when the world was saved comes back buried.

**What made this more than a second Dark Templar** is that both marker interfaces it needs were static. `faction/Cloaked` and `entity/Rooted` were bare `entity instanceof X` tests; each grew a single default method (`isCloakActive()`, `isRootedNow()`) that every existing implementor takes unchanged, and because the cloak gate lives in `FactionAttachments.isHostile` and the render decision in `client/CloakRenderStateModifier` — both reaching it through `Cloaked.isCloaked` — turning the Lurker's cloak on and off at the bottom of a dig is the *whole* implementation: acquisition, retaliation and splash chains follow with nothing written for them. `Rooted` matters for a duller reason that would have been a real bug: Lurkers are produced at a Hive and dig in where they stand, so without it `building/SpawnSpots` would hand the next unit off the Hive the exact block a buried one is standing in — the V4h Sunken/Spore collision again, in a new costume. One latent bug came with the change: `combat/DetectionHandler` only expired a reveal on entities that were cloaked *right now*, so a Lurker that climbed out while revealed would stop counting down and come back up already lit, anywhere on the map; the guard now follows the mask rather than the cloak. A second, deeper one surfaced in play: **cloak was only ever gating acquisition.** `TargetGoal.canContinueToUse` — inherited by every vanilla target goal — never re-runs the `TargetingConditions.Selector` that `canUse` acquired through, so a Lurker that burrowed while something was already hitting it kept being hit indefinitely. V4f could not have caught this: the Dark Templar is cloaked permanently, so it is never acquired and there is never a target to hold. `combat/CloakTargetHandler` (renamed `combat/TargetRetentionHandler` in V6e, when garrisoning turned out to need exactly the same two halves) closes it with two listeners — a `LivingChangeTargetEvent` veto that rewrites an unseeable target to null (and fires continuously, because `canContinueToUse` re-asserts through `setTarget` every tick), and a tick sweep for the one path nothing re-asserts, our own `RetaliateGoal`. `CommandedAttackGoal` was gated at the same time, since it re-set its target every tick with no hostility check at all — a standing order was otherwise the one way to keep hitting something that had cloaked.

**No goal in the library learned what a burrow is.** The arbitration is the priority ladder and nothing else: `LurkerBurrowGoal` holds `MOVE` and `JUMP` and sits *below* every goal that needs the unit walking (`SiegeBlockGoal`, `CommandedMoveGoal`, the new `LurkerApproachGoal`), so — given that `GoalSelector` only calls `canUse()` on a goal whose flags it can claim, and hands a held flag over only to a strictly lower priority number — it simply never starts while something more important wants the unit, and being preempted is what surfaces it. Its `canContinueToUse` deliberately asks a weaker question than its `canUse` (a target in range, *or no target at all*), which is what makes an idle Lurker dig in and wait rather than a statue, and what makes it climb out the moment it acquires something it would have to walk to. `LurkerApproachGoal` does none of the digging itself — it sets the intent and paths, and the entity refuses to move until fully surfaced, so "dig out, walk, dig in" falls out with no state machine. Two goals did need telling, and both for one reason: **a unit that stops its own navigation makes "standing still" stop meaning "stuck"**. `StuckWanderGoal` would have judged a burrowed Lurker stuck every 40s and dug it out to wander; `SiegeBlockGoal`'s obstruction branch, which keys off "navigation done and not arrived", would have surfaced it to chew through the first lip of terrain between it and a target it could already shoot over. Both took the same kind of optional predicate `FactionTargetGoal` and `RetaliateGoal` grew in V4h — one that may only ever *add* patience — and the digger's suppresses its dig branch alone, so a Lurker parked beside an enemy core with nothing alive to shoot still brings the core down.

**A Lurker will not be lured out of the ground.** The same priority-ladder arbitration settles the target selector too. Retaliation pins the target on any attacker inside follow range, and a target it cannot hit from where it lies is exactly what `LurkerApproachGoal` climbs out to close — so a Hydralisk plinking from across the field could pull a Lurker out of a working ambush, costing it its cloak, its immobility and six seconds, while the Zealots it was killing walked past. `LurkerHoldGroundGoal` sits *above* retaliation, the only thing that does, and holds the `TARGET` flag for as long as anything strikeable stands in reach: while it runs nothing can retarget the unit at all, and the moment the near fight ends it lapses and retaliation acquires the sniper on the next tick. **Holding the target flag was only a third of it**, though, because two other things dig without asking the target selector anything. `LurkerApproachGoal` decides to walk from *its* view of the target, so it now refuses to start at all while anything is in reach, whoever set that target; and `LurkerBurrowGoal` surfaces the unit through its own `stop()` when `canContinueToUse` sees an out-of-range target — no other goal involved — and would then refuse to re-bury it, leaving a Lurker standing in the open doing nothing. All three now ask one question, `LurkerReach`: *is there anything I could shoot from right here?* The first attempt scoped that question to the approach goal's inner distance, to keep the two goals from arguing over a target on the boundary, which left a 1.5-block ring where the Lurker could shoot something and still dig out to chase a sniper — the bug itself, in miniature. It is the full spine range and nothing shorter; the goals cannot argue because nothing is both in reach and worth walking to. The second attempt found the other edge of the same mistake: `LurkerHoldGroundGoal` held its claimed target 1.5 blocks *past* spine range, hysteresis against the claim flapping at the boundary, and since the goal owns the `TARGET` flag while it runs, a target drifting a block too far sat there unshootable while acquisition of the enemy next to the Lurker stayed blocked — burrowed, targeted, silent. **A goal that monopolises targeting owes the unit a usable target every tick**, so the claim is now re-picked rather than held, and the goal runs on "is anything in reach" rather than on the fate of one enemy. The flapping it was guarding against cannot arise: a claim is only ever dropped for another target already in range, or because there is nothing left to shoot. A player's order still outranks it, both kinds: a move order for the reason every targeting goal honours one, and a focus-fire order because ordering *that* one dead is precisely when the player means to spend the dig.

**The attack is a row, not a shot.** `LurkerSpineGoal` latches the bearing to its target and plants six `LurkerSpineEntity`s a block apart, one every two ticks, marching out to its full 6-block range; each is footed independently, so the row follows a step and loses the spines that run off a ledge. Every spine deals full damage, so a unit standing across two takes both and one walking up the line takes several — the payoff for a weapon that cannot fire at all until three seconds have been spent. The bearing is not re-read, so a target that runs perpendicular walks out of the row. It is ground-only for the Sunken Colony's reason, sharing `entity/Altitude`'s definition of air and applying it to both target goals. The Sunken's `EvokerFangs` machinery generalised to carry it: `entity/zerg/FangStrikeEntity` is the common base, each subclass naming its own damage type and damage, so `combat/FangStrikeDamageHandler` (was `SunkenSpikeDamageHandler`) no longer hardcodes one unit's numbers, and `entity/ai/zerg/GroundStrike` is the shared footing search. The damage types were made canonical while the seam was open: the Sunken's is now `subterranean_tentacle` (its real StarCraft weapon) and the freed `subterranean_spines` went to the Lurker, whose weapon it always was.

**The model is a vanilla Spider carrying a Hydralisk's head** — eight two-segment legs with knees standing above a plated thorax, a long abdomen behind it, and the Hydralisk's hood, brow, jaws and fangs transplanted whole and set low so the whole animal fits under 1.2 blocks. The renderer sinks it a block while burrowed and lets the terrain clip it, so there is no second model and the geometry alone decides what a buried one looks like: the top four pixels — hood horns, crest, spine rack — read as a low fringe of lit spikes. Skin and spawn eggs come off `tools/gen_lurker_texture.py` and `tools/gen_lurker_items.py` in the Hydralisk's own sampled palette. It is fielded as **defence**, not in waves: a Lurker walking with an attack spends the whole approach surfaced, visible and unable to fire. *Demo: walk toward a Hive and take a row of spines from a patch of ground with nothing standing on it; bring a Photon Cannon up and watch the same patch resolve into a red-outlined animal that dies without ever getting out of its hole.*

**V4j — Race-specific target priorities (R12). `[DONE]`** The neutral world is not one thing, and the two races were treating it as one. `FactionAttachments.isHostile` had a single boolean carve-out — "is the candidate a vanilla `Enemy`?" — so both races defended themselves against wild hostiles and neither noticed a village. Splitting it *without* putting a race check in targeting code took two pieces and no more: `faction/WildKind` classifies an unfactioned entity once (`HOSTILE` — vanilla's `Enemy` marker; `CIVILIAN` — villagers, wandering traders, golems; `PASSIVE` — the player, a cow, everything else), and `Faction.attacksWild` is a per-race table of which of those that race picks a fight with. Protoss `HOSTILE`, Zerg `CIVILIAN`, NEUTRAL nothing — so a swarm walks past a zombie and eats a village while a Zealot does the opposite, and adding a race or retuning what one hunts is an edit to that one table rather than to any goal. The choke point is unchanged and so everything that already flows through it follows for free: acquisition, retaliation, splash chains, attack orders and the Photon Cannon's own selector all changed only in that they pass a `WildKind` where they used to pass a boolean. Both of the carve-out's guards survive intact — it still only applies to a candidate that is actually `NEUTRAL` (the mod's own units are `Enemy` classes themselves), and NEUTRAL's own set is empty, which is now what makes "an unfactioned unit starts no fights" true rather than a separate condition. `HOSTILE` is tested first and wins ties, which keeps a `Shulker` — both `Enemy` and an `AbstractGolem` — a monster rather than Zerg prey. The classification is a fact about an entity's *class*, so it is exposed on `Class` as well as on `Entity` and the whole table is unit-tested without constructing an entity, which the JUnit bootstrap cannot do. *Demo: drop a Zergling and a Zealot into a village with a few zombies in it and watch them fight opposite halves of the same fight.*

**V4k — Infested Villager, the swarm's dividend on a village (R12b). `[DONE]`** V4j gave the Zerg villagers to hunt but nothing to show for it: a dead villager was just a dead villager. Now a Zerg kill on any `AbstractVillager` has a **75% chance of raising an Infested Villager**, a suicide bomber that walks to the nearest Protoss core and detonates for 250 in a three-block radius — the roster's first unit produced by *combat* rather than by a building, which is what ties it to the swarm actually pushing into settled ground instead of to its economy. `combat/Infestation` is the rule (killer faction x victim class x die roll, pure, so it is unit-tested without a world the way `WildKind` is) and `combat/InfestationHandler` is the world half. It is aimed the moment it stands up, via a new `CoreCensus.nearest` — deliberately *nearest* where a Zerg wave picks a core at random, because a wave spreads its attention across a player's expansions and a single body with a single detonation has nothing to spread.

Three things about it are worth writing down. **Its targeting is asymmetric on purpose**: acquisition is narrowed to `FactionAttachments.areEnemies` — strict cross-faction, which is exactly "units allied with the player" once you know `GameBootstrap` tags the player PROTOSS on login — so alone among the swarm it walks past the village it was born in; but `RetaliateGoal` is left *un*narrowed, which is what implements "unless attacked". That breaks the standing rule that a unit narrowing one narrows both, and legitimately: that rule exists for units narrowed by **capability** (a Spore Colony pinned by a ground attacker it can never reach stops fighting the flyers it can), and this one is narrowed by **doctrine** — it can blow up an iron golem perfectly well, it just does not go looking for one. **Its blast is the one thing in the mod that does not resolve hostility**: `SuicideBlast` leaves `ExplosionDamageCalculator.shouldDamageEntity` at its default, so friendly Zerg and the player alike are caught in it. That is not a hole in the choke point but a statement that a detonation is not targeting — nothing is being *chosen*; hostility still decides everything up to the moment it goes off, including which buildings get charged. **Its damage is flat across the whole radius**, which is a correction: a linear falloff was tried first and left a Zealot taking about 42 at the rim against 80 effective HP, so the thing walked out of a bomb it was standing next to and the unit did nothing. A bomber that can be survived by backing up one block is a formality, not a threat. Flat also means the outer cull has to be written by hand — vanilla hands the calculator entities out to *twice* the radius and leans on its own curve having decayed by then — so `damageAt` clamps on distance itself and a test pins it. Cover still applies, since vanilla's `exposure` term is pure occlusion. **And buildings cannot ride on the explosion**: a building's health lives on its block entity, not its blocks, so the 250 is charged explicitly through `SiegeTarget.damageBuilding` while the blast itself uses `ExplosionInteraction.MOB` for the crater. The core blocks carry 1200 blast resistance, so no detonation can delete one out from under `BuildingDefense` and hand `GameOutcome` a free win.

The fuse is vanilla's creeper in shape and none of it by inheritance — `SwellGoal` takes a `Creeper` in its constructor, the same trap `ZombieAttackGoal` carries — so `entity/ai/zerg/InfestedSwellGoal` reimplements it, holding `MOVE` from above every other goal so a lit fuse cannot be walked off its target, and arming on an enemy `SiegeTarget` block as well as on a live target (without that, a bomber reaching an *undefended* Nexus would stand against it doing nothing, since a building is not a target and this unit has no swing). The renderer borrows the creeper's swell and white flash deliberately rather than inventing a tell: 250 damage in three blocks needs a warning nobody has to learn. *Demo: point a Zergling at a village, then watch what walks out of it toward your Nexus.*

**V5a — Faction/race split: the AI stops being the Zerg. `[DONE]`** Groundwork for race selection and PvP, done as a decoupling rather than a feature. **Side vs race:** `faction/Race` is new and holds the cheap traits (shields, HP regen, infestation, what a race hunts in the wild, moved off `Faction`); `faction/Faction` keeps hostility and carries the race its side plays. `game/MatchSetup` — a level attachment written once at bootstrap — says which side the human commands and which the computer plays, and `command/ControlledFaction` finally has a body (the player's own synced faction attachment, so it is per-player already and works client-side). **The table:** `race/RaceProfile` + `race/Races` hold everything registry-bound per race — base core block and template, base HP/shield/warp numbers, bank size, `race/UnitRoster` (which names the race's worker), the base's command card, the AI build-script path, and the world-gen flavour (ground cover, support fill, static defence, starting bank). It is the only place that knows a Hive is a Zerg base. **The merges:** `building/BaseBlockEntity` is now every race's base (the old Nexus/Hive split made "player plays Zerg" mean reimplementing production on the Hive), with the command card driven by `ProductionKind.Action` data so a second race's card is an enum entry; `entity/WorkerEntity` is the whole harvest economy with `ProbeEntity`/`DroneEntity` as thin subclasses (the Drone used to *extend the Probe* from inside the Protoss package); `director/AiDirector` replaces `ZergDirector` and reads its side from the match and its roster from the profile. **Two asymmetries fell out:** base positions now come only from `CoreCensus` (the bootstrap-written `NEXUS_POS`/`HIVE_POSITIONS` pair was blind to kit-warped expansions), and `GameOutcome.decide` is symmetric — a side is out when its *last* base falls, so an expansion Nexus buys the player a life the way a second Hive always bought the swarm one. Build scripts are per race at `build_scripts/<race>.txt`; a Protoss one ships alongside the Zerg one, so an AI Protoss opponent is a match-setup change and no code. *Demo: unchanged play — but `RacesTest` fails the build the moment a race is added half-configured.*

**V5b — Pylons: the first prerequisite (R13). `[DONE]`** Until now a kit could be warped in anywhere its footprint fit, so a player's base sprawled wherever they walked and there was nothing to take from them short of a core. The **Pylon** is a cheap Protoss building (100 wood **or** 100 cobblestone, bought at the Nexus like the expansion kit rather than crafted) that powers the ground within 10 blocks of it; every other Protoss building — the Gateway and the Photon Cannon today — may only be placed on powered ground. A Nexus and a Pylon itself are exempt, so an expansion can always be founded and the power can always be extended. The player starts with one Pylon kit alongside the Gateway and Cannon kits they already had, which makes placing it the opening move.

Three decisions are worth writing down. **The rule lives in exactly one place**, `building/PsiField`, the way hostility lives in `FactionAttachments.isHostile` — and, deliberately, it *names no building*. Which buildings are exempt is a `requiresPylon` flag on the placing item, so a Nexus and a Pylon simply never ask. That mattered immediately, because there turned out to be **two** placement call sites rather than one: the Photon Cannon is a building that happens to be an entity, so it is placed by `entity/FactionSpawnEggItem` and not by a `BuildingKitItem` at all. Both now ask the same function and nothing else.

**"Is this Pylon online" is a blockstate, not a block-entity field**, and that is the whole reason the client placement outline can be trusted. `client/KitPlacementPreview` exists so "it says blocked and I can't see why" is answerable by looking, and a second, invisible refusal reason would have undone it — so the preview's boolean became a three-way verdict with its own amber colour for *clear but unpowered*. Getting the client the same answer as the server took no packet: blockstates sync to everyone holding the chunk, so `PylonBlock.ONLINE` is read identically on both sides, and it doubles as the light switch (a warping Pylon is dark prismarine, a finished one a lit sea lantern). The one respect in which the preview is more permissive is Pylon *ownership*, which lives on the block entity — unreachable today, since nothing but the player places one.

**Colouring one square was not enough, though.** The outline answers "may I build *here*", but the question a player walking around actually has is "where may I build at all", and answering it by sweeping the crosshair over the terrain hunting for the colour to change is exactly the tedium the outline was meant to remove. `client/PsiFieldOverlay` paints the powered ground while a gated item is held: a translucent square on every surface column a click would be allowed on, with a brighter contour along the boundary. The contour falls out of the same grid — an edge is drawn only between a powered square and an unpowered one, so overlapping Pylons produce one outline around their union rather than a circle each, and edges at the drawn window's own border are skipped, since that is where the *drawing* stops and not where the power does. It asks `PsiField` per column, at the height `MOTION_BLOCKING_NO_LEAVES` reports — which *is* the block a click on that surface resolves to — so the paint and the refusal cannot drift apart. Finding the Pylons is what made this affordable and is why `PsiField.onlinePylons` is its own step: sweeping blocks answers about one position for the cost of a cube of reads, while one walk over the block entities of the surrounding chunks hands back every Pylon and then answers a thousand columns for free. The range test is written out rather than left to `BlockPos.closerThan`, which is strictly less-than and would have made "within 10 blocks" quietly mean 9. What the overlay keys off is `building/PsiDependent` rather than "is this a kit", because the two placing items share no supertype but `Item` — and the Photon Cannon is the one that needs it, since the volume outline is a kit's feedback and a spawn egg has none.

**The flag is driven off the warp countdown every tick rather than flipped once when it ends.** A structure template carries both the blockstate and the block-entity NBT captured in the *design* world, so a stamped Pylon can arrive claiming it is already online with a spent countdown — the same trap that makes kit placement call `BuildingDefense.beginWarpIn` explicitly. Reflecting the live defence state each tick covers kit placement, a hand-placed core and a reload with one identical machinery. A Pylon is a `SiegeTarget` but not a `FactionCore`: razing one costs the player the ground it was powering, not the match. *Demo: try to warp in a Gateway on open ground and watch the outline go amber and the placement refuse; drop a Pylon, wait out its half-minute, watch it light up and the same outline go green.*

**V5c — Race selection: the player can be the swarm. `[DONE]`** V5a decoupled everything so that "the human plays Zerg" would be a match-setup change and no code. This is that change, plus the two things the decoupling could not have known were missing.

**Where the choice is made.** `asteriskcraft:player_race` is a game rule (`game/AsteriskCraftGameRules`), registered on `Registries.GAME_RULE` — game rules are a registry in 26.1 — and picked with a `CycleButton` that `client/RacePickerOverlay` adds to the world-creation screen. A rule rather than a config, because the choice is per *world* and has to be made before the world exists: the create-world screen already holds a live `GameRules` that flows into the level it builds, so one carrier is set at creation, saved with the world, readable server-side before the first login finishes, and settable on a dedicated server where no creation screen ever runs. `ScreenEvent.Init.Post` is the only seam into `CreateWorldScreen` — its three tabs are private inner classes with no NeoForge hook — so the widget belongs to the screen rather than to the Game tab it visually sits in, and has to be made to act like a member of it: it follows the Allow Commands button for its position and width (located by the translation key inside its message, not by its rendered text), and hides itself whenever that anchor is no longer among the screen's children, which is precisely when another tab is open. That check runs every frame from `ScreenEvent.Render.Pre`, since `AbstractWidget.extractRenderState` is final and never runs for a hidden widget. The button stores nothing of its own, so it and More → Game Rules can never disagree. `GameBootstrap` freezes the answer into `MatchSetup` at bootstrap rather than reading it live, because everything downstream has to keep agreeing with it for the life of the world.

**The Hive needed a command card.** This is what V5a left as a seam and it was load-bearing: `Races.ZERG.productionKind` was null, so a Zerg player got four Drones and no way to train a fifth. `ProductionKind.ZERG_BASE` fills it, and it is deliberately not a copy of the Nexus's. The swarm has no factory building, so the Hive morphs every combat unit itself — which meant `BaseBlockEntity`'s worker-only counter had to become a real mixed queue, of roster ids so a saved queue survives a card being reordered, with each unit taking its own build time (a save from before this reads its bare `Queued` count back as that many workers). The new `Action.TrainUnit(rosterId)` names units the same way a build script does, and `RacesTest` fails the build if a card names one its own roster cannot resolve. The card's shape differs from the Nexus's for a real reason rather than by accident: every Zerg cost is a single "any resource" alternative, so each button is one button where the Protoss get Wood/Stone pairs. A `hive_kit` item joins it, so the swarm can expand the way the Protoss always could.

**The swarm hunts differently when you are standing in it.** `Race`'s wild-target table grew a second column: what a race hunts, and what it hunts *under human command*. "Ignore monsters" is right doctrine for a scripted opponent parked across the map and plainly wrong for the army you are commanding, where it means a creeper walks into your Hive — so commanded Zerg add `HOSTILE` to the `CIVILIAN` they already overrun, while the Protoss answer is unchanged either way. This stays a table rather than becoming a branch at the choke point: `FactionAttachments.isHostile` gained a `commanded` argument and no race check, and command may only ever *widen* the wild carve-out. Which side is commanded is a level attachment in `faction/` holding `MatchSetup.playerFaction()` — a deliberate projection, since that package may not import `game/`.

**Two asymmetries fell out, both of them old bugs the Protoss AI would have been the first to hit.** The player's starting bank and inventory were hardcoded oak logs, cobble, a Pylon kit and a Cannon kit; they are now `RaceProfile.playerBank` and `playerKit`, and the Command Crystal stays in `GameBootstrap` as the one race-generic item. And a pre-placed AI base never called `skipWarpIn()` — invisible while the swarm's warp duration was zero, but a Protoss AI would have opened every match with three Nexus at half HP and shields for two minutes. *Demo: create a world, set Race to Zerg, and play the mirror of the match you already know — a Hive that trains and morphs, three enemy Nexus, and Zerglings that answer a creeper.*

**V5d — Creep: the Zerg prerequisite. `[DONE]`** V5b gave the Protoss a reason to place a Pylon before anything else; the swarm had no equivalent, so a Zerg player's Sunken and Spore Colonies (sold from the Hive's own command card once V5c gave it one) could go down anywhere on the map. `building/CreepField` is the Zerg mirror of `building/PsiField`, deliberately its own class rather than a generalisation of it: a Zerg building may be placed within `CreepField.RADIUS` (20 blocks, core to core, same sphere-not-box geometry as psi) of *any* creep source — a Hive, or a Sunken or Spore Colony, tagged with the new `entity/CreepSource` marker — or standing outright on the race's own creep block, mycelium, which is left unowned on purpose so a razed base's creep stays buildable for whoever reaches it. Both clauses are deliberately faction-blind, unlike psi: creep is shared territory rather than an army-specific resource, so an enemy-side colony egg checks and paints against creep any faction spread, not only its own. It reaches the same two placement call sites psi does through a sibling flag, `building/CreepDependent#requiresCreep`, rather than a second field on `PsiDependent`: the two mechanisms happen to share a shape today but neither may name the other's race. Only the four colony spawn eggs are gated so far — the Hive kit stays exempt, the way a Nexus is exempt from psi — and `client/CreepFieldOverlay` paints the buildable ground exactly like `client/PsiFieldOverlay` does, the two now sharing their grid/rendering mechanics through `client/GroundGridOverlay` while keeping their own coverage rule and colours (psi purple, creep mycelium-toned). Colonies already spread mycelium in a matching 20-block circle on placement (`GameBootstrap.spreadCreep`), which is what lets a chain of colonies push the buildable frontier outward instead of a Zerg base being capped at one ring. *Demo: place a Sunken Colony at the edge of a Hive's creep, then chain a Spore Colony off the fresh mycelium it spreads — then try to place one out in open field and get refused with nothing painted on the ground until you're back in range.*

**V5e — Overlord, detection that moves. `[DONE]`** Every detector in the mod until now was rooted — the Photon Cannon and, since V4h, the Spore Colony — so an army could only see cloaked units where it had already built. That was survivable while the Dark Templar was something the *computer* walked into a Hive's static defence; V5c made the player Protoss by default, and a Zerg AI with no mobile detector simply has no answer to one met in the field. The Overlord is that answer: 100 HP, 100 of any resource, 40s, hovering 7 blocks up, and **no attack at all** — the only unit besides the two workers with none. One is handed to every Hive at world start, on both sides.

**Being a detector cost nothing, and that was the point of A10.** `combat/DetectionHandler` sweeps off a detector's live position from a global tick handler, so the mod's first *mobile* detector needed no machinery a rooted one didn't — `implements Detector` plus a `.detector(16, 20, 60)` envelope, and acquisition, reveal and expiry all followed. What did need saying is what an unarmed unit *isn't*: it extends `PathfinderMob` rather than `Monster` (the shape `entity/WorkerEntity` already had) and carries no `FactionTargetGoal`, no `RetaliateGoal` and no `SiegeBlockGoal`, because a target it can never act on is worse than none — holding one blocks re-acquisition and buys nothing. It takes move orders through a bare `CommandedMoveGoal` for the same reason, rather than `CommandableGoals.install` and the `CommandedAttackGoal` it could never honour. Flight is V4c's stack reused verbatim with a different hover height and nothing else.

**"One per Hive" needed a new `RaceProfile` field rather than the obvious one.** `baseDefences` looked like the hook — it is already a per-race list of units planted with a base — but it is walked only on the AI base path, because the human's starting base deliberately plants no static defence and gets `playerKit` instead. A rule about the *race* has to hold for whoever is holding it, so `baseEscort` is a sibling list walked on both paths; the Protoss declare an empty one. `UnitStatsTest` moved with it: "only the two workers lack attack damage" was a rule about workers, and is now one about non-combatants, while the flyer stand-off invariant learned to skip a flyer that has no weapon to stand off with. Model is a Zergling's skull — cranium, horns, eyes and two-hinge jaws lifted wholesale — on a Ghast's body, one 16-unit cube with a nine-tentacle fringe, rendered at 4x so it fills its four-block hitbox; the head stays at Zergling scale on purpose, since a small head is what makes the sac read as enormous. *Demo: on a Zerg start, find the Overlord over your Hive, order it out to meet a Dark Templar in open ground, and watch the assassin light up red where a Spore Colony would never have reached.*


**V5 — Polish + extensibility groundwork.** Unit groups on the Cursor `[DONE]` — an earlier Ctrl/Shift+numpad hotkey scheme was thrown out (undiscoverable, unrebindable, and silent about whether an assignment landed) and replaced by an overlay: with the Cursor held, **C** opens ten blocks in 2 columns of 5 (numbered 1-5 down the left, 6-9 then 0 down the right) and picking one assigns the current selection to it; **V** opens the same grid and picking an assigned block makes its units the selection, while picking an empty one assigns to it. Blocks are picked by click or by the number key they carry, and both keys are rebindable `KeyMapping`s in a `*Craft` category. Each assigned block states what it holds (`1Z 3D`), which needs the mod's first server→client payload: groups live server-side, so `UnitGroupSync` pushes a composition snapshot on login, on change, and on a once-a-second sweep that keeps labels honest as grouped units die. Whether picking a block assigns or recalls is decided server-side against the real groups, never from the client's cache. **Mineral fields `[DONE]`** — the AI's resource garden (9 scattered nodes) and unbroken stone ring are gone, replaced by one `game/MineralField` per base: a third of a circle at radius 8-9, filled with 1-3-high columns each of a single material, wood or stone, facing a direction rolled off the world seed and the base's own coordinates. Every bootstrap-placed base gets one — the player's too, which previously had to scavenge whatever the terrain happened to leave inside a worker's search radius — and the computer player's one edge is a single 3-high iron column planted in the middle of its arc. A kit-warped expansion still stamps no terrain around itself. The shape is planned pure and stamped by `GameBootstrap`, so `MineralFieldTest` covers it end to end. Still to come: per-player client-only selection glow (replacing V2b's shared server glow); unit team-color visuals, sounds, particles; faction/race registry `[DONE]` (see below); optional start on tactical map GUI. *Demo: comfortable command UX in a full match.*

**V6a — The Terran: a Command Center and SCVs. `[DONE]`** The claim V5a's decoupling made — that a third race is an entry in `race/Races` plus its assets, and no change to the AI director, the base block entity, world generation or targeting — had never been cashed. This slice cashes it with the smallest honest army: a **Command Center** (325 HP, no shields, no warp-in) and an **SCV** (the Probe's numbers with the shields taken off, 50 wood or 50 cobblestone). No combat units, no factory, no prerequisite of the Pylon/creep kind. The claim held: `building/BaseBlockEntity`, `game/GameBootstrap`, `building/ArmyBank`, `director/AiDirector` and every targeting rule took the new race with no edit at all, and the only compile error outside the tables was `entity/TeamColors`' exhaustive switch, which is exactly the kind of "you forgot something" a switch is for.

**What a third race did break is the opponent.** `MatchSetup.forPlayerRace` derived the AI's side as "the faction that isn't yours" — a two-race trick its own javadoc flagged. Rather than a cleverer derivation, the opponent became a choice: a second game rule (`asteriskcraft:ai_race`) and a second `CycleButton` beside the race picker, which is the same shape V5c chose and for the same reason (the answer has to exist before the world does). The pair shipped carrying one invariant between them — the two sides may not be the same race, since `building/ArmyBank` keyed one bank per race and `Faction.isEnemy` is strictly cross-faction, so a mirror match would have had both armies spending one pool and neither shooting the other. V6b removed the invariant by removing what forced it (below).

**Two deliberately cheap answers, both reversible.** The Command Center's structure template is a 1×1×1 `.nbt` holding just the core block, generated by `tools/make_core_template.py` rather than exported from a design world — the building has no shape to design yet, and the generated file is byte-compatible with a real export, so re-exporting a designed Command Center over it is the whole upgrade path. And the SCV baked `PROBE_LAYER`: one model class, one UV layout, one entry in the model tests, and a Terran renderer that named a Protoss render state because `ProbeModel` is an `EntityModel<ProbeRenderState>`. Its textures were its own files from day one, which is what made repainting it a self-contained job. **That half is now redeemed (V6c below); the generated template is not.** *Demo: create a world with Race: Terran and Enemy: Zerg, mine with four SCVs, train more off the Command Center's card, and lose the game when the swarm brings the one block down.*

**V6b — Mirror matches: a side stops being a race. `[DONE]`** V6a's second picker left one thing you could pick and not get: setting both to the same race was shoved apart by the pickers and re-derived by `MatchSetup.forRaces`. The invariant was never really about matchups — it was a symptom of `Faction` carrying a `Race`, which made "the Protoss side" a thing that could only ever be one army. So the enum stopped naming races: **`Faction` is now `NEUTRAL`/`BLUE`/`RED`, a pure side, and `isEnemy` is the whole of what it means.** What an army *is* rides beside its side, on a new synced entity attachment (`FactionAttachments.RACE`), written together with the faction wherever a unit is spawned; `game/MatchSetup` holds the two races and hands out the two fixed sides. Everything that used to ask a faction for its race now asks the unit in hand (`raceOf`) or the match (`MatchSetup.raceOf/sidePlaying`), which is also why it is synced — `combat/ShieldAttachments.maxShieldFor` runs client-side for the Jade tooltip, and the creep overlay wants the same answer the server is about to give (`command/ControlledRace`, the sibling of `ControlledFaction`). `building/ArmyBank` keys one bank per **(side, race)** pair, so two swarms bank separately; `entity/TeamColors` is a colour per *side*, which is what tells two identical armies apart on the beacon beams. The pickers now write their own rule and nothing else. The choke points held: `FactionAttachments.isHostile` grew one parameter (the attacker's race, for the wild carve-out) and no new branch, and `SiegeBlockGoal`, `RetaliateGoal`, `CoreCensus`, `GameOutcome` and the director needed nothing — they were already keyed on the side. **Save compatibility is deliberately not kept**: the faction names in existing worlds (`protoss`, `zerg`) no longer decode, so a world from before this slice comes back with its armies unfactioned. *Demo: create a world with Race: Zerg and Enemy Race: Zerg, and fight a swarm that is your mirror — blue beams over your Hives, red over theirs, two banks, and Zerglings that tear into each other.*

**V6c — The SCV, finished. `[DONE]`** V6a's placeholder made good on every axis at once: its own geometry, its own voice, its own icon, and — the one real design move — its own weapon. **The model is the part with a rule in it.** An SCV is a mech, not a person in armour, and three things carry that: it has *no head* (the top of the model is two shoulder pods with nothing between them), its *arms are booms* bolted to the hull that project straight forward and hold their pose through the walk rather than counter-swinging, and *the pilot sits in an open recess in the middle of the chest*, leaning out through the opening. That last is what makes a villager head legible on a machine at all — it reads as a cockpit, not a face, and only while the recess reads as a hole. **The pilot is vanilla's own baby villager head, not a copy of one**: `client/terran/ScvPilotLayer` bakes `ModelLayers.VILLAGER_BABY` and draws its `head` — cranium, hat, wide straw brim, stub nose — off vanilla's `villager_baby.png`, hung on an empty `pilot_mount` container part in `ScvModel`. It is a second draw rather than geometry because **the texture is the reason**: a model part can only be painted from its own model's texture, so owning the head would have meant hand-copying villager pixels into `scv.png` and keeping them in sync forever. `client/zerg/InfestedVillagerModel` copies villager *proportions* for the opposite reason — it needs a body it can then infest — but nothing here modifies the head, so nothing here owns one.

**And the SCV is the first worker in the mod that fights.** 30 HP and 3 damage from a welding torch (`asteriskcraft:fusion_cutter`, the first damage type a non-combat unit has ever needed), paid for with double the Probe's build time. What keeps it a worker is not the absence of a weapon but the absence of a `FactionTargetGoal`: it carries `RetaliateGoal` and a `MeleeAttackGoal` and nothing else, so an SCV crew mines straight past an enemy army until one of them lands a hit. The goal sits at priority 2 — above harvesting, below a move order, which is the same doctrine `RetaliateGoal` already applies to a retreat — and ties with `DeliverGoal`, so a loaded SCV finishes its drop before turning around. `UnitStatsTest.isNonCombatant` lost an entry, which is the executable form of the claim. *Demo: create a world with Race: Terran, train an SCV off the Command Center's card and watch it walk — booms out front, villager riding in the chest — then punch it and get welded for your trouble, and walk away to watch it go straight back to mining.*

**V6d — The Marine: the Terran get an army. `[DONE]`** V6a shipped a race that mines and never attacks, and its own build script said so in its header. This slice ends that with one unit and no new machinery: a **Marine** (20 HP, 3 damage, a 5-block rifle on a 1-second cadence, 50 wood or 50 cobblestone, 24 seconds), which is the frailest combat unit in the mod and the cheapest — everything about the numbers says *bring more of them*. The Zerg escalate a wave by adding a kind; the Terran escalate one by adding bodies, and `build_scripts/terran.txt` is now a real escalating build order rather than a single `Workers: 9`.

**Nothing new was needed to make it fight**, which is the executable form of V5a's claim holding a second time: the Marine is the Hydralisk's goal ladder verbatim (`StuckWanderGoal`/`FloatGoal`/`SiegeBlockGoal`/`RangedAttackGoal` over `RetaliateGoal`/`FactionTargetGoal`, plus `CommandableGoals.install`), firing through `entity/ai/HitscanAttacks` with its own damage type (`asteriskcraft:gauss_rifle`, in `#minecraft:no_knockback` with every other hitscan, so massed rifles don't kite what walks at them). The edits outside the tables were a roster line, a command-card button and a `UnitLabels` letter.

**The one design decision is the model, and it is the opposite of the SCV's.** V6c's rule was that an SCV is a mech and must not read as a person in armour. A Marine is the reverse: it is **vanilla's villager, dimension for dimension** — same torso, same inflated robe, same legs on the same hips, same arms folded across the belly — wearing a helmet with *no faceplate*. Four separate plates (crown, back, two ear covers) rather than one shell is what leaves the front open; a single enclosing cube would have been the cheaper build and would have thrown away the only thing on the model that says who these soldiers are. The rifle is therefore **carried, not aimed**: it lies across the crossed forearms, butt by the right hip and barrel angled forward-left, because a villager's arms do not come up. It counter-rotates `+0.75` against the arm group's tilt so the weapon sits level while the arms keep vanilla's pose.

**And the face is vanilla's, texture and all.** `client/terran/MarineHeadLayer` bakes `ModelLayers.VILLAGER` and draws its `head` off vanilla's own `villager.png`, hung on an empty `head` container in `MarineModel` that the helmet plates also hang from — so the borrowed face and the mod's helmet turn as one head. It is a second draw rather than geometry for the reason `ScvPilotLayer` already established: a model part can only be painted from its own model's texture, so owning the head would mean hand-copying villager pixels into `marine.png` forever. The straw hat is hidden with `visible = false` rather than avoided, since `VILLAGER_NO_HAT` clears the whole head recursively and would leave no face at all. **Both of these are now stated as defaults in CLAUDE.md** — borrowing a vanilla model means borrowing its texture, and the folded-arm villager pose is the Terran starting point — which is the real output of this slice: `client/zerg/InfestedVillagerModel` was the precedent for copying the frame, and a second unit taking it is what turns "the Terran are villagers" into a convention rather than a one-off.

**What the race still cannot do is deliberate.** Nothing Terran detects, so a Dark Templar or a burrowed Lurker walks through a Marine army untouched; nothing Terran reaches a flyer hovering at 6 or 7 blocks, since a rifle stops at 5. Their base guard is a pair of live Marines rather than a structure — the other two races plant something rooted — so a Terran base is held more loosely, and can be pulled off to fight elsewhere. Those are real holes in a one-unit roster, left standing rather than papered over. *Demo: create a world with Race: Zerg and Enemy Race: Terran, and get attacked — waves of rifles that grow in size rather than in kind. Then create one with Race: Terran, queue a Marine off the Command Center's second column, and watch it walk out on a villager's gait with the rifle up.*



**V6e — The Bunker: the Terran get somewhere to stand (R14). `[DONE]`** V6d shipped the Marine and said out loud what the race still could not do; the entry it left open was the one in V6a's own table, where the Terran are the only race whose base guard is *people* rather than something rooted. The Bunker fills it, and it fills it differently on purpose: a Photon Cannon and a Sunken Colony **are** guns, while a Bunker is a **container for guns the player already owns**. 175 HP, 1 armour, 30 seconds to build, 100 cobblestone, four seats — and no attack whatsoever. An empty one is a wall.

**The mechanism is vanilla passengers, and the surprise was how much of it came free.** Verified against the decompiled 26.1.2 source rather than guessed at, because nothing in this mod had ever ridden anything: `Mob.serverAiStep` is `final` and contains no passenger check, and `LivingEntity.isImmobile` — the one gate on the AI step — is `isDeadOrDying()` and nothing else, so **a riding Mob runs its full goal and target selectors**. "Marines shoot from inside" is therefore not a feature that was implemented; it is what happens if you put a Marine inside something and change nothing. Persistence is the same story: `Entity.saveWithoutId` writes passengers as a nested `Passengers` list and `EntityType.loadPassengersRecursive` re-seats them with `startRiding(v, true, false)`, so a loaded Bunker comes back loaded with no save code at all, and `Entity.setRemoved` already dismounts everyone, so a destroyed one spills its garrison without being asked. Seating four is declarative — `passengerAttachments(Vec3...)` on the `EntityType` plus a `canAddPassenger` cap, which is the Happy Ghast's entire multi-seat implementation; boats are the *wrong* precedent here, since they override `getPassengerAttachmentPoint` outright and only need to because their seats depend on the passenger's class.

**Three things were not free, and each is worth knowing before the next transport.** First, **the first `Mob` passenger becomes the vehicle's driver** (`Mob.getControllingPassenger`, opted out of only by `#minecraft:non_controlling_rider`, which holds two slimes) — which switches the vehicle's own goal flags off *and* re-routes the rider's `getNavigation()`/`getMoveControl()` onto it, so a garrisoned Marine's ranged goal would have spent its life trying to steer a building at its target. One override returning null. Second, **riders stay individually targetable and hittable**: `LivingEntity.getHitbox` merely clips a rider's box up to its ride position, and nothing anywhere routes damage from a vehicle to its passengers or protects them. Third, **a rider's movement goals still hold their flags** — physics cannot move it, but a goal holding `MOVE` above the firing goal still silences it, which for the Marine is `StuckWanderGoal` at -1 and `SiegeBlockGoal` at 0. Both learned that a passenger is neither stuck nor able to walk up to a wall, which is a fact about riding rather than about Bunkers.

**The protection is the shape V4i already established, and this is the second instance of it rather than a new idea.** `faction/Garrison` is a marker on the *vehicle* consulted through `isHostile`, sitting in `faction/` for the same leaf-package reason `Cloaked` does; `combat/CloakTargetHandler` became `combat/TargetRetentionHandler` and grew a second condition, because a Marine that boards while being shot at has *exactly* the problem a Lurker that burrows while being shot at has — a `TargetingConditions.Selector` is asked once, at acquisition, and never again. Naming the class for the shape rather than for cloak is the real output: the next rule that can start applying mid-fight now has somewhere obvious to go. Underneath both sits `combat/GarrisonDamageHandler`, because **targeting is not the only way damage arrives**: a suicide blast deliberately resolves no hostility at all, fang strikes hit a spot rather than a target, and a vehicle propagates its own fall damage to its riders. It cancels rather than zeroing, at `HIGHEST`, so the shield and regen handlers never see a hit that did not land.

**Who may board is a capability, not a race.** `entity/Organic` joins `Flyer`/`Rooted`/`Detector`/`CreepSource` as a bare marker, carried by the Marine and the SCV, so the boarding rule asks "is this something that can climb inside" and names no race and no unit class — a Firebat boards by adding one `implements`. The whole rule lives at the door, on `BunkerEntity.boardable`, so there is one place to read it.

**The one thing that genuinely cost code is the +1 range.** A firing slit is worth a block of reach, which is what makes being inside better than standing beside it — and vanilla's `RangedAttackGoal` takes `attackRadius` into a private final field that both `canUse` and `tick` read, so there is nothing to override. `entity/ai/UnitRangedAttackGoal` is vanilla's goal with a live radius, read once per tick; only the Marine is on it, because only the Marine is both `Organic` and ranged. Swapping goals in and out of a running `GoalSelector` as a unit boards was the alternative, and expressing a stat change by mutating the goal ladder is exactly what the ladder exists to avoid.

**The command scheme took one branch at each end.** Right-clicking a friendly Bunker with a selection stamps a new `CommandOrder.Kind.LOAD` on everything it would take — and only those, since the rest of the selection is left alone rather than marched at a door it cannot use — which `entity/ai/BoardGoal` walks. LOAD joins MOVE as a *march* for the focus window, since a squad ordered into cover has to be able to disengage to reach it; GUARD deliberately stays out of that set, because a station is held rather than marched to. At the other end, **any order given to a Bunker unloads it** — it cannot march and cannot shoot, so an order aimed at it can only ever have been meant for its garrison — and the ejected units take `MoveFormation` slots or the attack order exactly like any other squad. A garrisoned unit is dropped from every selection and cannot be re-picked, which also stops a click meant for the Bunker landing on the Marine standing inside its hitbox. Selecting the Bunker itself needed no code at all: it is a `Mob` with a faction, which is the same reason a Photon Cannon has always been selectable.

**The model is a squat concrete blockhouse** — foundation slab, hull stepped in from it, roof slab overhanging that, four corner posts proud of every face, and a near-black slit band at chest height. The CLAUDE.md villager pose is a rule about Terran *people*; the right precedent here is the Photon Cannon's square-slab-and-square-step reasoning about sitting in Minecraft rather than looking imported. **The four barrels are the whole occupancy display and the model's only animation**: one shown per unit inside, because a Bunker's stat line says nothing about how dangerous it is and a player has to be able to read a loaded one from across the field. It costs no sync — the vehicle-passenger link is vanilla's, so the client counts passengers directly. The building rises out of the ground as it is built, the Lurker's sink trick run backwards, so there is no scaffold geometry and no second model. A Terran base now opens with a Bunker and its two guard Marines already inside it; a Terran player opens with a Bunker kit, which is an opening move that does nothing at all until they have built something to put in it — the race's whole shape restated as an opening. *Demo: create a world with Race: Terran, place the kit, watch it rise out of the ground; queue three Marines and right-click the Bunker with them selected — they walk in, vanish, and three barrels come out. Then walk a Zergling up: the Marines shoot it from a block further than they could outside, the Zergling chews on the Bunker, and the Marines take nothing. Detonate an Infested Villager on it and they still take nothing. Select the Bunker, right-click open ground, and all three march out in formation.*

**V6f — The Firebat: the Terran stop pushing with one unit. `[DONE]`** V6d said the Terran "escalate a wave by adding bodies" and `build_scripts/terran.txt` said the same thing in its own header — which was true, and was also the whole of the race's answer to anything. Every Terran wave was Marines, and a defender who massed cheap melee simply walked through the rifles. The Firebat is the counter to that shape and nothing else: **25 HP, 1 armour, 8 damage on a 1.5-second cadence, and a reach of two blocks** — worthless alone, vicious against a clump. 50 cobblestone **and** 25 wood, the first Terran cost that is a bundle rather than a choice, which is what says specialist rather than body. The build script now escalates by *kind* from its third wave on, which is what the race could not do before.

**The attack is the mod's first multi-target hit that is neither a bounce chain nor an explosion**, and it needed a fourth attack helper: `entity/ai/FlameAttacks`, beside `HitscanAttacks`, `MeleeAttacks` and `SuicideBlast`. The interesting half is that it **resolves hostility** like the first two rather than skipping it like the third — candidates go through `FactionAttachments.isHostile`, so cloak, garrison and the per-race wild carve-out all applied to a sweep with nothing written for them. `SuicideBlast` catching friendly Zerg is a statement that a blast is not targeting; a flamethrower *is* aimed, so it is not that.

**The geometry is where the work was, and the obvious implementation is wrong.** `combat/FlameCone` is pure and registry-free (the `BounceChain` split again) so it is unit-testable, and it decides what a wedge covers by **separating axes** against the target's footprint rectangle, with the vertical as an independent slab. The first attempt cut the axis into boxes and asked whether the target overlapped any — which is cheap, obvious, and silently makes the cone about a block longer than its own reach and a block wider than its own nozzle, because an axis-aligned box sized by the local spread extends that spread *forwards* too. A unit standing safely past the mouth burned anyway, and so did one at the attacker's own shoulder. `FlameConeTest` caught it, which is the argument for pulling the geometry out as a type in the first place. `flame_thrower` also joins `#minecraft:no_knockback` and moves that tag's rule off "melee versus ranged" onto **"does the attack need its target to stay put"** — it is a melee-range weapon, but shoving its victims pushes them out of the attacker's own cone, which is the bumper problem arriving from the other end.

**Nothing else about the unit is new, and that is the point twice over.** Its goal ladder is the Marine's verbatim, `UnitRangedAttackGoal` and all, because a two-block flamethrower is a stand-off weapon with a very short stand-off — the one addition is a distance guard in `performRangedAttack`, since that goal fires on cadence at any range and a cone would otherwise belch flame across the map at nothing. And it is `entity/Organic`, so it rides in a Bunker: V6e predicted this exact unit — *"a Firebat boards by adding one `implements`"* — and that is what it cost.

**The model is the Marine's frame with the head swapped and nothing over it.** Same villager torso, same inflated robe, same folded arms, weapon cradled the same way — because the folded-arm villager pose is the Terran default and this unit had no reason to leave it. What differs is a **pillager** head, borrowed the way the other two are: `client/terran/FirebatHeadLayer` bakes `ModelLayers.PILLAGER` and draws its `head` off vanilla's own `pillager.png`, keeping the `nose` (half of what makes it read as a pillager) and hiding the `hat` (an inflated shell that would swallow the face — vanilla's own `IllagerModel` hides it for the same reason). Crucially **no helmet is hung over it**: the Marine's four plates are what says "Marine", and plating this head would bury the one feature that says this is not one. Red plate, brass fuel tank, twin glowing pilot lights. That makes `ScvPilotLayer`/`MarineHeadLayer`/`FirebatHeadLayer` three instances of the same move, which is what turns "borrowing a vanilla model means borrowing its texture" from a convention into a habit. *Demo: create a world with Race: Terran, queue a Firebat off the Command Center's second column, and walk it into a pack of Zerglings — one sweep, the whole pack takes 8 and burns, and none of them is shoved out of the cone. Then stand a Marine behind it and confirm it takes nothing. Then create one with Enemy Race: Terran and let the waves get big enough to arrive mixed.*

**V6g — The Ghost: reach, and a cloak that is a reaction. `[DONE]`** V6d and V6f both closed with the same admission — the Terran are out-ranged. A rifle stops at 5 and a flamethrower at 2, so every Terran engagement was fought at whatever distance the *other* army chose. The Ghost is the answer and it is deliberately not a better Marine: **23 HP, no armour at all, 5 damage on a 1.5-second cadence at 7 blocks** — worse damage per second than a rifle, and the flimsiest thing either army fields. What it buys is the two extra blocks, and the price is the steepest in the race: 25 cobblestone, 75 wood **and 3 iron** — the first cost in the mod naming three resources and the only one that sends a player underground — over 50 seconds. A Ghost is a decision, not a body.

**Its cloak is the first reactive one, and it cost no combat code.** The Dark Templar is cloaked always and the Lurker while burrowed; a Ghost cloaks for **one minute the moment it takes damage**, then cannot cloak again for **two**. `entity/terran/CloakClock` holds that as a single signed int — positive is cloak remaining, negative is lockout remaining, zero is armed — which is `BurrowClock`'s "one number, everything falls out of it" move a second time, and means the whole state syncs as one `EntityDataAccessor<Integer>` (it must sync: the gate runs on the server and the render decision on the client). The entity is one override of `hurtServer` over it and one line in `isCloakActive()`. **Everything else was already there**: `FactionAttachments.isHostile` gates acquisition, `combat/TargetRetentionHandler` drops a target whose cloak comes up *after* it was picked, `combat/DetectionHandler` expires the reveal, and `client/CloakRenderStateModifier` decides what each viewer sees. That middle one is the payoff of naming it for the shape in V6e rather than for cloak: a Ghost's cloak arrives at exactly the moment a Lurker's does, so the third instance of that shape needed nothing written for it. Two rules were written down rather than left implicit — a hit while already cloaked does **not** refresh the minute (a Ghost pinned under a detector would otherwise hide forever), and the lockout is charged on *coming out* rather than on going in, so the cost lands where the unit is vulnerable.

**The head is the first time the mod paints two vanilla headgear textures onto one borrowed head.** Verified against the decompiled source rather than assumed: `VillagerProfessionLayer` adds no geometry for a profession — it re-submits the *same* villager model with `profession/<name>.png` — so vanilla's **armorer welding mask** and **cartographer eyepiece** are texture overlays on the head's own `hat` and `head` cubes, and `client/terran/GhostHeadLayer` draws both by submitting one baked `ModelLayers.VILLAGER` head three times. That is a face no real villager could ever wear (it has one profession), for the cost of two more draws and no mesh. It also inverts `MarineHeadLayer` on one point for a reason worth recording: **the hat stays visible here**, because the mask lives almost entirely on that inflated shell and `villager.png` is fully transparent across its whole UV region — only the nested `hat_rim` is hidden.

**The three eyeholes are the one place the mod paints over borrowed vanilla pixels, and it is six texels.** The mask has two slits (transparent in `armorer.png`, at v=10, above the villager's own eyes because it is a raised visor) and the eyepiece has one lens (opaque blue at v=14, landing on the right eye). `ghost_visor.png` is a mod-owned PNG laid out on **vanilla's** UVs, transparent except those six pixels, drawn **twice** — cutout first so the lens reads solid green rather than additive-green-over-blue, then through `RenderTypes.eyes` so all three ignore world light. `tools/gen_ghost_visor.py` carries the coordinates and where they were measured from, since nothing enforces them if vanilla ever retouches either texture.

**Everything else is the Marine's, on purpose.** Same frame dimension for dimension, same folded-arm villager pose, same cradled weapon with the `+0.75` pitch cancellation — only the barrel runs further out and carries a scope instead of iron sights, and there is no helmet, for the reason the Firebat wears none: the mask *is* the unit, and plating over it would bury it. Grey where the Marine is blue-steel and the Firebat red, with a slim comms slab on the back as its one break from the villager outline. The goal ladder is copied verbatim, and it is `entity/Organic`, so it rides in a Bunker — the one place its cloak does nothing, since a garrison already hides a rider from everything. The edits outside the tables were a roster line, a card button (its own column, since a column holds two), a `UnitLabels` letter and a damage type. **What the race still cannot do is unchanged**: nothing Terran detects, and nothing Terran shoots at a flyer that stays high. *Demo: create a world with Race: Terran, queue a Ghost off the Command Center's third column, and look at its face — a villager behind a welding mask and a monocle with three green eyes burning through them. Walk it at a Hydralisk and win the range fight. Then punch it: it vanishes for a minute, whatever was shooting at it immediately gives up, and it is still a faint ghost to you. Punch it again the moment it reappears and nothing happens — it owes two minutes first. Then do the whole thing again in front of a Photon Cannon and watch it stay lit and outlined the entire time.*

**V6h — The Missile Turret: the Terran finally look up. `[DONE]`** V6d, V6f and V6g all closed with the same two-clause admission — *nothing Terran detects, and nothing Terran shoots at a flyer that stays high*. One building closes both. **100 HP, no armour, 20 damage a second at 14 blocks**, kit-bought for 75 cobblestone and 30 seconds to stand up, on the same 16 / 20 / 60 detection envelope the Photon Cannon and the Spore Colony already share.

**It is the Spore Colony's opposite number, not its copy.** They agree on the rule — the only legal target is an *airborne* one, and "airborne" is `entity/Altitude`, positional and re-checked every tick, so a Mutalisk that lands stops being a target mid-fight — and disagree on everything else. The Zerg answer is a wall that dribbles (200 HP, 7.5 a shot); this is a gun with a thin skin, the hardest-hitting static defence in the mod and the flimsiest of the four. That is what makes the Terran base defence read as a **pair**: the Bunker is a wall the player has to crew and the turret is a gun they do not, the turret takes the air and the infantry inside the Bunker take the ground, and neither covers for the other. The Protoss answer both layers with one Photon Cannon; the Zerg split it across two colonies; the Terran split it across a wall and a gun. No `RetaliateGoal`, for the Spore Colony's reason: retaliation hands an air-only unit a ground attacker its fire goal must then refuse.

**The gameplay cost outside the tables was almost nothing, which is the point.** `combat/DetectionHandler` sweeps every `entity/Detector` off `EntityTickEvent.Post`, so the race's first detector is one `implements` and one CSV column group. `FactionTargetGoal` already takes a narrowing predicate, so air-only is one method reference. `race/Races.TERRAN` gained one `BaseDefence` line and `ProductionKind.TERRAN_BASE` a second button in the column the Bunker already had. The one real edit was `building/PrePlaced`: the Bunker's "world generation placed this, so nobody built it" skip had been an `instanceof BunkerEntity` in `GameBootstrap`, and a second building that counts itself up made it a named seam instead — a third needs no edit there.

**It is the first time the mod borrows a vanilla model that is not a head, and the first time borrowed pixels land on mod geometry.** `client/terran/MissileTurretGolemLayer` bakes `ModelLayers.IRON_GOLEM`, hides `right_arm` and `left_arm`, and draws the rest off vanilla's own `iron_golem.png` into an empty container part — `MarineHeadLayer`'s move, scaled up from a head to a body. The new part is that **the racks that replaced the arms are drawn from that same texture**: they are new cubes, but they are still the golem's arms, so painting them out of `missile_turret.png` would have been the hand-copy CLAUDE.md's rule exists to prevent. Each rack is `3 x 29 x 7`, and both halves of that are forced. **Which dimension reads as "tall" is decided by the pitch, and it is not the long one**: at 30 degrees above horizontal the box's length swings almost flat and it is its *depth* that swings almost vertical, so an upright plate has to be narrow in x and deep in z — authoring it the other way round lays it flat however long it is, which is exactly what the first attempt did. And a `3 x 29 x 7` box has a box-UV footprint of exactly the 20x36 texels vanilla's arm occupies, so `texOffs(60, 21)` and `texOffs(60, 58)` land **every** face inside real plating with not one texel off the edge of it — which also fixes the length at 29, since depth and length trade against each other inside one island. The three missiles are stacked up the plate rather than laid across it, for the same reason. **The shells are drawn twice rather than hidden between the draws**, and the failed attempt is worth recording: `SubmitNodeCollector.submitModelPart` stores a *reference* to the `ModelPart` and copies only the pose, so `visible` is read long after `submit` returns and flipping it back drops the part from the frame it was just submitted to. Instead `missile_turret.png` is simply blank at those two islands, the model's own cutout pass discards them, and the layer paints them from vanilla's texture. That leaves `missile_turret.png` covering six cubes: the three missiles standing out of each muzzle, which are the only thing here that is genuinely the mod's. The racks are held **30 degrees above horizontal** and pivoted a third of the way along, so the breech counterweights behind the shoulder and the whole unit stays inside the golem's own 2.7-block height rather than towering over it. Vanilla's golem already stands with its soles at `y=24`, which is the space the mod's models are authored in, so nothing had to be repositioned.

**The attack sound is the first `.wav` in `import/`.** Every clip before it was an `.oga` that was byte-identical Ogg and only needed renaming; Minecraft loads Ogg Vorbis only, and there is no ffmpeg on the dev machine, so `tools/wav_to_ogg.py` is the transcode step (`soundfile`/libsndfile, which the texture tooling's environment already has). *Demo: create a world with Race: Terran, buy a turret off the Command Center's structure column and watch it grind up out of the ground over thirty seconds — hit it while it does and it takes double. Then fly a Mutalisk over it and be shot out of the sky at 14 blocks, land the survivor and watch the turret lose interest instantly. Walk a Zergling up and chew on it: it will not fight back, ever. Then bring a Dark Templar inside 16 blocks and watch it light up red.*


**V6i — Somebody has to build it. `[DONE]`** V6e and V6h both shipped a Terran structure that put *itself* up: a kit went down and a countdown started, with nobody involved. That is the Protoss move — a Nexus warps a building in from across the map — and it is the wrong one for the race whose defining loop is a worker walking over with a cutting torch. Now a Bunker or a Missile Turret **calls the nearest idle SCV within 32 blocks**, refuses to be placed at all if none answers, and does not lay a single block until that SCV arrives; while it is there it stands welding, in white smoke; and if it is killed before the structure is finished, the structure goes with it.

**The rule sits above both construction mechanisms, which is the whole reason it is its own object.** `building/ConstructionSite` is the single answer to "may this structure make progress this tick", the way `building/PsiField` is the single answer to "may this be placed here" — and it names no race and no building. It had to, because the mod has *two* things that count down: a building that is blocks runs its warp inside `BuildingDefense.tickWarpIn`, while a building that is an entity (`PrePlaced` — the Bunker, the Missile Turret) counts down in its own `tick()`. Both now own one of these and both consult it first, so the future `bunker.nbt` that turns one into a template building needs nothing new. Who needs a builder is a flag on the *placing item* (`building/BuilderDependent`, the third sibling of `PsiDependent`/`CreepDependent`), and who may *be* one is `entity/WorkerEntity` rather than an SCV — so a Protoss kit could opt in later with no edit to the rule.

**The interesting part of the rule is what it does when the worker is not there, and it is three different answers.** Before it arrives, nothing happens at all — no pane, no tick of the countdown, no particle; the site is a hole in the ground. Once it has arrived, the build runs to completion **whether or not it stays**, so pulling an SCV off with a move order is a redirection rather than a cancellation. And a dead builder razes the structure at any point before it is finished. "Dead" is deliberately *"gone for forty consecutive ticks"* rather than "gone this tick": `ServerLevel.getEntity` answers null for an entity whose chunk has not caught up, so razing on the first miss would demolish every site in progress across a world reload. The whole table is a pure `decide` with no world in it, which is what `ConstructionSiteTest` exercises.

**The worker side is one field and one goal, and the goal knows nothing.** `WorkerEntity` carries a nullable build site beside its pending node, and `ConstructGoal` is `AwaitRegenGoal` almost verbatim — walk there, stop, hold, holding `MOVE` so the economy cannot shuffle the worker off the spot. It sits at priority 1 *registered after* `CommandedMoveGoal` and `BoardGoal`, since equal priorities resolve to whichever was added first: an explicit player order preempts the walk, while building outranks delivering and mining. It emits nothing and it never clears its own assignment. Whether the worker has *arrived* — and so whether the plume plays and the countdown runs — is decided in one place, off the building's tick, and the building is what releases the worker when it finishes or dies. A goal that answered the same question a second time is exactly how the two halves drift apart.

**One thing was measured rather than assumed.** `geyser_base` is a Bedrock particle name and does not exist in Java Edition 26.1.2 — no `assets/minecraft/particles/geyser*.json` in the client jar, no `GEYSER*` field in the decompiled `ParticleTypes`. The plume is `WHITE_SMOKE`, thrown from the SCV's own arm along its look vector, which also reads as welding beside the `SMOKE` the two structures already puff while they go up. *Demo: create a world with Race: Terran, buy a Bunker kit and place it beside the mineral line — an SCV breaks off, walks over, and only then does the Bunker start rising; kill it halfway and the Bunker comes apart. Then walk every SCV to the far side of the base and try to place a Missile Turret: refused, and the kit stays in your hand.*

**V6j — The Drone becomes the building. `[DONE]`** V6i gave the Terran a builder and closed by saying the rule named no race, which the Zerg are what proves. The swarm gets the same call-a-worker requirement on all three of its structures — Hive, Sunken Colony, Spore Colony — with one substantive difference: **a Drone does not put a building up, it *is* the building.** It walks to the site, dies there, and the structure grows out of it with nobody left on the hook.

**That difference is one branch, and `decide` never learned about it.** `faction/Race` gained a fourth cheap trait beside `shields`/`regen`/`infests` — `consumesBuilders()` — and `building/ConstructionSite.tick` reads it **off the resolved worker**, the way `FactionAttachments.isHostile` reads a race off the attacker. So neither placement call site changed, no flag was threaded anywhere, and the transition table is byte-for-byte the one V6i shipped: on arrival a consuming race kills its worker and drops the UUID, which lands the site back in exactly the not-required state world generation has always used. The invariant that makes it safe is worth naming — **the UUID has to go in the same tick the worker dies**, because a dying entity stops answering `isAlive()` and a site that kept it would count past its forty-tick tolerance and raze the colony the Drone just paid for. It is `kill` rather than `discard` on purpose: the Drone should visibly die, and it is safe to route through a real death because `combat/InfestationHandler` needs both a killer entity and a villager victim.

**It belongs on the race and not on the item, which is the opposite of where `requiresBuilder` lives, and both are right.** *Which* buildings need somebody varies inside a race — a Pylon needs no Pylon, a Nexus needs no builder — so that is a flag on the placing item. *Whether the builder survives* does not vary at all: it is the worker's own doctrine, and putting it on the item would mean every Zerg structure ever added has to remember to repeat it.

**Most of the work was that none of the three Zerg structures had a construction phase to gate.** The colonies spawned finished at full HP — not `PrePlaced`, no counter, nothing — so they took `BunkerEntity`'s wiring almost verbatim: a synced `BUILD_TICKS_REMAINING`, `WarpInVulnerability`'s halved starting pool, `skipConstruction`, save/load, and the same three-branch switch in front of the countdown. Twenty seconds rather than the Terran thirty, because a colony also costs a whole Drone. They rise out of the ground as they grow (the Bunker's trick, which is the Lurker's sink run backwards) and refuse to fire while they do, both gated at the one choke point each fire goal already had. The seam held where it was supposed to: `GameBootstrap`'s `baseDefences` loop already called `PrePlaced.standUp`, so the AI's world-generated colonies stand up finished with **no edit there at all** — that line was written for exactly this and had never been exercised by a second race.

**The Hive needed a warp duration it had deliberately never had, and that exposed a constant that should always have been a table.** `Races.ZERG` declared `baseWarpTicks = 0` with a comment saying the Hive is pre-placed rather than raised from a kit — true when it was written and stale ever since `HIVE_KIT` shipped, and the reason `BuildingKitItem`'s `isWarping()` guard would have silently swallowed a Drone. It is now the Nexus's two minutes. But a Hive filling itself in out of **light-blue stained glass** reads as the wrong army's building, so `WarpScaffold.PANE` stopped being a static: the pane is `RaceProfile.scaffold`, handed in at `beginWarpIn` and then **saved on the scaffold**, because `collectSmashed` tests against it on every five-tick sweep and a two-minute warp routinely outlives a reload. Purple for the swarm, still glass, still smashable for the same penalty. *Demo: create a world with Race: Zerg, buy a Sunken Colony off the Hive's card and plant it on creep near the drone line — a Drone breaks off, walks over, dies in a puff of souls, and only then does the colony grind up out of the ground; walk a Zergling at it while it grows and it will not fight back. Kill the Drone while it is still walking and the colony comes apart. Then place a Hive kit and watch it fill in purple.*

**V6k — Five buildings get kits. `[DONE]`** Five hand-authored `.nbt` templates landed — `command_center`, `barracks`, `stargate`, `spawning_pool`, `spire` — and this slice is only the placement half of them: a kit item each, its footprint declared and pinned to its template, and the right ground rule in front of it. **The Command Center's is the finished one.** Its template stopped being the 1x1x1 `tools/make_core_template.py` emitted (the core is now on the floor of a 5x5x5 export, which the anchor-on-the-core-column rule absorbed with no code change) and its core has been a real `BaseBlockEntity` since V6a, so `command_center_kit` warps in, scaffolds, banks and produces like any other base — and it takes the fifth column of `ProductionKind.TERRAN_BASE`, which is what finally lets the Terran expand the way the other two races always could.

**The other four are gated but inert, and the split is worth stating rather than papering over** (closed by V6l below). `stargate_core`, `barracks_core`, `spawning_pool_core` and `spire_core` are still the visual-only blocks V6a staged — no `BlockEntity` — so a kit stamps the layout and the building simply stands there: no warp countdown, no scaffold, no owner, no siege HP. What *is* live is every prerequisite, and each of the three mechanisms is exercised by one of them: the Stargate needs psi, the Spawning Pool and Spire need creep, the Barracks needs an idle SCV. Wiring the buildings themselves is a `BlockEntity` per core plus a `ProductionKind` card — the Gateway's shape — and it changes nothing about these kits.

**The creep prerequisite got its client half in the process.** `client/KitPlacementPreview` had checked only `requiresPylon()`, with a comment saying no kit required creep — true when V5d shipped it, since only the colony spawn eggs were gated, and false the moment the Spawning Pool's kit existed. It now has a `Verdict` for creep beside the psi one, asked through `CreepField` off the kit's own `placingRace`, so a Zerg kit's outline says which rule refused rather than reading clear right up to the server's no. *Demo: create a world with Race: Terran, buy a Command Center kit off your base's card and found an expansion — it fills in behind glass and starts training SCVs. Then take a Spawning Pool kit out past the creep line and watch the outline go purple before you click.*

**V6l — The other four buildings stop being scenery. `[DONE]`** V6k shipped five kits and said out loud that four of them stamped inert blocks: no countdown, no scaffold, no owner, no siege HP, and no way to buy one that did not involve the creative tab. This slice closes both halves. **Every kit is now sold at its own race's base**, and each of the four cores stands behind a real block entity, so a kit that goes down spends a build time going up and can be battered down afterwards. **Barracks and Spawning Pool: 80 seconds. Stargate: 70. Spire and the Command Center kit: 120** — the two-minute tier being what an army commits its time to, which is why an expansion base has always been there.

**The four buildings share one class, and that is the whole slice.** `building/StructureBlock` plus `building/StructureBlockEntity` is the Pylon's shape with the one thing that made a Pylon special (its `ONLINE` blockstate) taken out, so a building that is only "stands up, then can be knocked down" is a line of numbers at the registration site rather than a class: whose it is, what it takes to raze, and its build time. A structure that later gains a command card graduates off it to the Gateway's shape — that is a building acquiring behaviour, not this table growing a case for it. Everything already built around a warp-in came for free: the glass scaffold filling in over the countdown, `WarpInVulnerability`'s halved pools, and — for the Terran and the Zerg — `ConstructionSite`, so the Barracks calls an SCV and the Spawning Pool and Spire each eat a Drone with no code written for either.

**The prices are what forced the one real refactor.** A kit's cost had been an amount and a single `Resource`, which can say "150 wood" and cannot say "75 wood *and* 75 cobblestone" or "250 of anything *and* 10 iron". `ProductionKind.Action.GiveKit` now carries a `UnitCost` and an alternative index — the same pair a worker button already carried — so a kit is priced, paid and rendered through the machinery a unit's cost uses, and a card gives one button per alternative for a building exactly as it does for a Probe. Two smaller things fell out of it: `Resource.ANY` matches iron, so `UnitCost.bankCosts` emits the flat-pile line **last** or the Spire's 250 would swallow its own 10 iron; and `ResourceBank.extractAll`'s affordability check now *simulates* the removals instead of totalling each line independently, because two lines matching the same stack made it say yes to a bank that could only cover one and then charge less than the price. *Demo: create a world with Race: Terran, buy a Barracks off your Command Center's building column, place it, and watch an SCV walk over before a single block is laid — then smash the glass while it goes up and pay for it twice. Then create one with Race: Zerg, buy a Spire, and watch the Drone die into it over two minutes. Then one with Race: Protoss and put a Stargate down off psi: refused, kit still in hand.*


**V6m — The Barracks starts building the army. `[DONE]`** V6l stood the Barracks up and left it with nothing to do: the Terran army still came off the Command Center's card, which made the building the player had just paid 150 resources and 80 seconds for entirely optional. **Marine, Firebat and Ghost now train at the Barracks**, and the Command Center is left with the SCV and the four buildings it sells — which is the Nexus's shape, not the Hive's, and is now true of the race in the same way it has always been true of the Protoss: you build a building before you build a soldier. The swarm stays the exception on purpose, since a Hive morphs its own.

**The shared piece is the queue, not the building.** `building/UnitQueue` is what a base and a factory both have in the works — a line of roster ids, the countdown on the head of it, and its save/load, including the legacy bare-count a pre-mixed-queue world still reads back as workers. `BaseBlockEntity` gave it up rather than a second copy being written, so the two producing buildings now agree on what a queue *is* by construction. On top of it, `building/FactoryBlockEntity` is a `StructureBlockEntity` that also produces: it resolves every button against its own race's `UnitRoster` by the id the card names, so it names no unit class and no race, and `building/FactoryBlock` is the structure block plus a `ProductionKind` — a second factory (a Stargate, one day) is a card and a registration.

**`GatewayBlockEntity` was deliberately left alone.** It predates the roster and dispatches its four buttons positionally through an enum of Protoss units, so folding it into the factory is a real merge with its own save-compatibility question, and doing it as a side effect of moving three Terran buttons would have buried it. Nothing here is written twice for it; it is simply still the old shape. *Demo: create a world with Race: Terran and try to build a Marine — there is no button for one. Buy a Barracks kit off your base's building column, let an SCV weld it together, then right-click it: Marine, Firebat and Ghost, spending the same bank the Command Center does. Raze it with a Zergling pack and watch the race lose its army production without losing the game.*


**V6n — The Scout moves to the Stargate. `[DONE]`** The Protoss half of the same problem V6m solved for the Terran: V6l gave the Stargate a build time, siege HP and a 150-cobblestone/150-wood/10-iron price, and then left it with nothing to do — the Scout still came off the Gateway, so the priciest building on any card was scenery you paid for and never used. **The Scout now trains at the Stargate**, and the Gateway is left with the Protoss ground army: Zealot, Dragoon, Dark Templar. Air costs a building, which is what it costs the swarm (a Spire, for the Mutalisk) and is now the only way the race can answer one.

**This is the slice V6m predicted, and it cost what V6m said it would.** `PROTOSS_STARGATE` is a `ProductionKind` with one button on it, and `stargate_core` registers as a `FactoryBlock` rather than a `StructureBlock` and moves from `STRUCTURE_BLOCK_ENTITY`'s list to `FACTORY_BLOCK_ENTITY`'s. No new class, no edit to `FactoryBlockEntity`, `UnitQueue`, `ProductionMenu` or `ProductionScreen` — and no new test either: `FactoryCardTest`, `StructureBlockEntityTest`, `ProductionCardLayoutTest` and `ProductionIconResourceTest` all walk the registry or the enum, so the new building was already covered the moment it existed.

**Two things it deliberately did not do.** The Scout is *not* gated in the Protoss `UnitRoster` behind `stargate_core`, which is the Barracks' answer rather than the Spire's: the Gateway's units aren't roster-gated either, so gating this one would make the Scout the only Protoss unit whose prerequisite is written twice, and it would strand the computer — the AI opens no command card, so its script's Scouts would go `UNAFFORDABLE` forever unless a Stargate were also added to the Protoss `techBuildings`. The card is the whole gate, and it gates the player, who is the only one with a card. And `GatewayBlockEntity` still isn't folded into the factory: it went from four positional buttons to three, which is the merge getting smaller rather than the merge happening. The one cost of that is a save break — its queue serializes `UnitType` by name, so a world with a Scout in a Gateway queue reads that queue back empty. At most five units in progress, against a dead enum constant nothing could produce. *Demo: create a world with Race: Protoss, right-click your Gateway — Zealot, Dragoon, Dark Templar, no Scout. Buy a Stargate off the Nexus's building column, put it down in psi range, wait out the 70 seconds, then right-click it and take the sky back with the same bank the Gateway spends.*

## Verification

- `./gradlew test` for deterministic logic (faction rules, site-prep geometry, economy constants) — tags and item components aren't bound in the JUnit bootstrap, and structure templates need a running server's resource manager, so tag-dependent behavior (e.g. block→item yield mapping) and template placement aren't unit-testable and need the checks below instead. `BuildingTemplatesTest` covers what it can by reading the `.nbt` files as raw NBT.
- `./gradlew runClient` per slice; execute each slice's demo script manually.
- `./gradlew runServer` at V3+ — all logic must be server-side safe (dedicated-server crash is the classic modding failure).
- V3 end-to-end: play one full match to victory (raze every AI base) and one to defeat (let the AI raze your last one).
- Chunk test: order units to attack-move from outside simulation distance of the AI's bases and confirm they arrive.
